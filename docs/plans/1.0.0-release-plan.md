## 0. 一句话结论

**当前 0.9.0 的发行产物（`dist/pluma-0.9.0.zip`）与仓库源码严重脱节 —— 它不是"少了 PGC"，而是"少了整个主世界脚本与响应改写能力"。**
1.0.0 的**首要目标不是加功能，而是让发布产物第一次等于源码**。在此基础上修 6 个 bug、补 3 条自动化守卫。

### 1.3 由此推翻的两条既有文档结论

> **规范要求：每件事只有一个权威位置。** 下面两条是文档与事实不符，必须在 1.0.0 落地时改正，否则下一个接手的人会被误导。

| 文档现说法 | 实测事实 | 应改成 |
| --- | --- | --- |
| `README.md` L32：「番剧 / 国创 / 电影：源码已支持，随下一版发布」 | 成立，但**0.9.0 缺的远不止番剧** —— 它连 `world: 'MAIN'` 的注入方式都没有，用的是 2026-10-28 已被删除的 WAR 方案 | 发 1.0.0 时整段摘掉（届时产物已含 PGC） |
| `MEMORY.md` / 交接记录：「`dist/pluma-0.9.0.zip` 构建于 10-27，早于全部 PGC 提交」 | 只说了「早于 PGC」，**低估了差距**：还缺图标、缺 MAIN world 入口、且带着已废弃的 WAR 配置 | 记录为「0.9.0 产物基于 10-27 的旧架构（WAR 注入 + 无图标），与当前源码存在结构性差异」 |

**为什么这件事严重**：用户下载 0.9.0 安装后，`main-world.js` 是通过 `web_accessible_resources` 暴露的**资源文件**、而 manifest 里**没有任何脚本去加载它**（`content_scripts` 只有 ISOLATED 那条）。按当前源码的架构（`main-hook.content.ts` 用 `world:'MAIN'` 注入），产物里那个 1862 行的 `main-world.js` **实际上没人会执行**。也就是说：**0.9.0 的用户装到的扩展，主世界 hook 大概率根本没跑**，表现为会员标识挡路、切高清弹充值页、画质对比永远不显示。

> ⚠️ 这一条需要**真机确认**才能写进 CHANGELOG / Release 说明（用 0.9.0 的 zip 装一次，看 `__PLUMA_MAIN__` 是否存在）。**文档里不写未验证的结论**。验证步骤见 §5.2 B-01。

## 2. 架构分析与任务分工建议

### 2.1 模块依赖现状

分层与 `docs/04-project-structure.md` §2 一致，`verify` 的 `boundaries` + `design` 两项守住了静态边界：

```
entrypoints/*  ──→  src/background、src/content  ──→  src/core  ──→  src/shared
                            │
                            └──→  src/platform  ──→  src/shared
```

| 层 | 规模 | 现状评价 |
| --- | --- | --- |
| `entrypoints/` | 7 个入口，`content.ts` 1295 行、`popup/main.tsx` 614 行 | ⚠️ `content.ts` 偏大，承担报到 + 观测 + PGC 编排 + 缓存注入四件事 |
| `src/content/main-world.js` | **2989 行纯 JS** | ⚠️ 唯一无法进 `tsc`/`eslint`/`prettier` 的文件，行为测试是唯一手段（`main-world-{real,pgc}.test.ts`，65 例） |
| `src/platform/http/dnr.ts` | 420 行，零单测 | 🔴 最高风险，只能靠 `poc/verify/*.cjs` 回归 |
| `src/core/` | 7 个模块，纯函数 | ✅ 测试最充分（`popup-state` 47 例、`summary-view` 46 例、`router` 36 例） |
| `src/shared/` | 类型 + 常量 + 纯函数 | ✅ 白名单单一真相源 |

### 2.2 测试覆盖的**结构性空洞**（这是质量判断的关键）

| 模块 | 测试 | 空洞 |
| --- | --- | --- |
| `core/*` | ✅ 充分 | — |
| `shared/utils/*` | ✅ 充分（`video-page` 38 例） | — |
| `main-world.js` | ⚠️ 行为测试 65 例 | 只覆盖被断言的路径；PGC 时序改动仍须真机日志 |
| `platform/http/dnr.ts` | ❌ **零单测** | 只能真机跑 `poc/verify/`（约 10 分钟） |
| `background/handlers/*` | ❌ **零单测** | `page.handler` / `tabs.handler` / `account.handler` 全部无测试 |
| `entrypoints/background.ts` | ❌ **零单测** | 消息路由靠 `check-messages.mjs` 对账类型，**不验行为** |
| `entrypoints/content.ts` | ❌ **零单测** | 1295 行编排层无测试 |

**结论**：`verify` 全绿的 641 个测试，覆盖率集中在**纯函数**上；**所有跨进程边界、所有浏览器 API 交互、所有编排逻辑**都没有自动化测试。这是 1.0.0 前必须正视的现实 —— 也是 §5 为什么把「补守卫脚本」和「修 bug」放在同等优先级的原因。

## 3. 1.0.0 目标与范围

### 3.1 版本号语义（依据 `docs/guides/versioning.md`）

`1.0.0` = **首个稳定版**。按该文档 §分段怎么涨：

- `MAJOR`：**用户能感知的行为不兼容** → 0.9.0 用户升级到 1.0.0 后，主世界 hook 开始真正工作、番剧页开始被支持。这是**能力上的不兼容升级**（行为变了），CHANGELOG 必须有「需要用户操作」说明（重新加载扩展 / 检查 InPrivate 权限）。
- 同时 `MINOR` 语义也满足（新增番剧支持）→ 但 MAJOR 优先。

### 3.2 目标范围（In Scope）

| # | 目标 | 对应缺陷 | 验收 |
| --- | --- | --- | --- |
| G1 | **产物 = 源码**：1.0.0 zip 含图标、两条 content_scripts、`world:'MAIN'` 注入、无 WAR、main-world 为 2989 行版本 | B-01 / B-08 | 解包比对脚本全过 |
| G2 | 修 6 个 bug（B-02 ~ B-07 中选 6） | — | 每个附「能复现旧 bug」的验证 |
| G3 | 补 2 个自动化守卫：`check-page-gate` 扩范围 + 新增「产物一致性」检查 | B-07 / B-08 | `verify` 项数 +1，故意改坏能变红 |
| G4 | PGC + 图标正式进发行版 | B-09 | README 🚧 摘除 |

| 不做 | 理由 |
| --- | --- |
| Firefox / v1.5 特性（长视频流刷新、多播放账号） | ADR 0007 / `04` §6「预留」 |

### 4.1 关键路径与缓冲

```
M0 ─→ M1 ─→ M2 ─→ M3 ─→ M4(不可压缩) ─→ M5 ─→ M6
                     ↑________↓
```

## 5. 各角色职责

> 本项目管理以「单人 + AI 辅助」为现实前提。角色不是组织架构，而是**职责分离**：同一人不同时间扮演不同角色，目的是防止「自己写、自己验、自己发」的三个盲区叠加。

| 角色 | 承担 | 具体职责 | 交付判据 |
| --- | --- | --- | --- |
| **交付总监（Qi）** | 用户 / 主理人 | 范围裁定、里程碑把关、风险处置、发布决策 | 每个里程碑门禁签字；不通过不许进下一阶段 |
| **产品（Xu）** | 用户 | 定义「用户能感知什么变了」；决定 CHANGELOG 措辞；裁定「不写未验证的结论」 | CHANGELOG 每条都能对应一条验收证据 |
| **架构（Gao）** | 主开发者（设计侧） | B-05 规则 ID 方案、B-06 主机同步方案、B-02 判据统一方案；ADR 是否新增 | 方案写进 ADR 或代码注释，不留「口头约定」 |
| **工程（Kou）** | 主开发者（实现侧） | 6 个 bug 修复 + 2 个守卫脚本 + 文档改正 | 每个修复附反例验证；`verify` 全绿 |

### 5.1 职责分离的三条硬规则

1. **写代码的人不判「验过了」**。Kou 完成修复后，必须由 Yan 角色视角重跑一遍反例验证（AGENTS §1.5：把关键判断反向改回去，测试必须变红）。
2. **改 ADR 必须 Gao 视角复核**。B-02 若决定「把 `parsePlayPage` 用进 background」，属于架构决策，须确认不违反 §4.3 路由表。
3. **发布决策不外包**。M6 由 Qi 执行，且必须现场跑 `releasing.md` §7 的三条核对命令。

## 6. Bug 治理流程（**本方案的核心方法**）

### 6.1 发现方式（按优先级排列）

| 手段 | 能发现什么 | 已有工具 | 缺口 |
| --- | --- | --- | --- |
| **① 产物解包比对** | 产物与源码脱节（B-01 就是这么发现的） | 无 | 🔴 **必须补脚本**（G3） |
| **② 静态规范核对** | 判据越界、常量不同步（B-02/06/07/10） | `check-*.mjs` 8 个 | 🔴 `page-gate` 范围不全（B-07） |
| **③ 真实登录态真机操作** | 时序、跨 world、DNR、播放器行为（B-04） | `bsk`（browser-skill） | 需要人工构造场景 |
| **④ 用户反馈复现** | 真实使用路径 | 诊断页日志 | 依赖用户描述准确性 |
| **⑤ 代码审查（读 diff）** | 语义不等价（B-03） | 人工 | 不可靠，易漏 |
| **⑥ 单测反例验证** | 已有逻辑的回归 | Vitest | 覆盖不到边界层（见 §2.2） |

**原则（AGENTS §1.5 原话）：「能实测就不要推理。」** 本次已定位的 8 条缺陷中，B-01 来自①、B-02/07/10 来自②、B-03 来自⑤+实测、B-04/05/06 来自⑤。**六次「读代码推理」里已经出现过一次误判**（B-04 的严重度），所以定级必须靠实测。

### 6.2 优先级判定规则

用**二维矩阵**（影响面 × 可发现性），不靠"感觉严重"：

| | **用户能立刻察觉** | **用户察觉不到（静默）** |
| --- | --- | --- |
| **影响核心功能**（画质/身份/凭据） | 🔴 **P0** | 🔴 **P0** |
| **影响辅助功能**（UI/统计/提示） | 🟠 P1 | 🟡 P2 |
| **影响开发流程**（检查/文档/产物） | 🟠 P1 | 🟡 P2 |

**判定依据三条**：

1. **「静默失效」自动升级一级**。`docs/03` §2 的原话：串号是「用错账号」（事后能发现），静默降级是「扩展没生效」（极难排查）。**能骗过用户的 bug 比报错的 bug 严重。**
2. **「界面说的和事实不一致」一律 P0/P1**。判据 5 的教训：popup 显示「已停用」而实际还在代理，是「最坏的一类不一致」。
3. **「说不出判据的测试等于没写」**。附带的规则：任何标 P1 以上的修复，必须留下**可复跑的判据**（脚本或明确的真机操作步骤 + 期望值）。

### 8.0 【已定论】DNR 并发回归的「无回显」是 PoC 假阳性，已修

> **2026-10-29 16:36 结案。以下保留完整推演过程，因为它是「怎么区分『被测对象坏了』和『测试工具让它看起来坏了』」的范例。**

**症状**（改动前的基线，连续两次同一形状）：

| 策略 | 第 1 次 | 第 2 次 | 说明 |
| --- | --- | --- | --- |
| `no-nonce-persistent` | 20 / **17** / **11** | 20 / **15** / **13** | ⚠️ 这就是项目实际采用的策略（ADR 0006） |
| `persistent-id` | 20 / 20 / **16** | 20 / 20 / **14** | |
| `pool-random-id` | 20 / 20 / 20 | 20 / 20 / 20 | 唯一始终满 |
| `single-shared` | 1 / 0 / 0 | 1 / 0 / 1 | 对照组 |

- **串号两次都是 0**，**残留两次都是 0**
- `missing` 的形状是 `echoed: null` + `error: null` —— 请求发出去了，没拿到回显

**为什么不能归因为「httpbin 抖动」**（推翻 `MEMORY.md` 的旧解释）：
① 直连 httpbin 自测 200 / 962ms 正常；② 若为外网抖动，S1 也该受影响，但 S1 两次都满；
③ S4 的 missing 随轮次**递增**（0→3→9），抖动不该是这种形状。

**真正机理**：S4/S2 是「同一规则 ID 重写内容」型，每轮开头
`updateSessionRules({removeRuleIds:[4001], addRules:[…]})` 之后**立刻**发 20 并发。
该 API 是**异步生效**的，规则表重建期间到达的请求匹配不到任何规则 → 请求照发但 Cookie 没被改。
**决定性对照**：S1 每请求用新 ID、响应后即删，从不需要"重建已有规则"，所以永远满 —— 差别只在这里。

**为什么不代表方案有问题**：真实运行里没有"装完立刻并发"这个时序。
`enableProxy()` 只在总开关切换时装一次，之后规则常驻；`installTabRule()` 专门先比对
cookie 与 urlFilter、相同就跳过重建（源码注释原话：「反复重建规则是"恢复标签页时卡一下"的直接来源之一」）。

**修法**：装完规则后用**单发探测请求**确认已生效（最多 10 次 × 120ms），命中才发并发批次；
始终不命中则给整批结果打 `rule-never-settled`，**不伪装成大面积 missing**。
（不用固定 `sleep(N)`：N 小了照样漏、大了拖慢整体，且最优值随机器负载变化。）

**修后结果（2026-10-29 · 两次运行）**：

| --- | --- | --- | --- |
| S4 `no-nonce-persistent`（实际采用） | **20/20/20** ✅ | **20/20/20** ✅ | — |
| S2 `persistent-id` | 20/20/**12** ❌ | **20/20/20** ✅ | 第 1 次跑时还没给 S2 加同样的等待 |

| **串号** | **0** | **0** | — |
| **L3 残留** | **0** | **0** | — |

**对 B-05 的结论**：
- ✅ **验收判据的核心项全部满足**：串号四次运行全为 0、残留全为 0、项目实际采用的 S4 修后稳定 20/20/20。
