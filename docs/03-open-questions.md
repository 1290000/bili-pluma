## 1. ✅ Q1：主账号未登录时，功能还能成立吗 — **已实测：不成立**

### 结论（**分两半，别混**）

| 半 | 问题 | 状态 |
| --- | --- | --- |
| **A** | 游客**不带**播放账号凭据时，能拿到什么 | ✅ 已实测：480P / 360P |
| **B** | 游客**带上**播放账号凭据（也就是本扩展的做法）能拿到什么 | ✅ 已实测（2026-10-26 20:41，InPrivate）：**用户拿不到高清** |

### B 的结论：两层相反，失败点不在 DNR

| 层 | 结果 |
| --- | --- |
| 网络层（服务端认 Cookie） | ✅ playurl 返回 **2160p · 19 条轨 · Hi-Res** |
| 播放器层（按本地登录态决策） | ❌ 只播 **360p** —— 手里有 2160p 也不选 |

**所以"游客模式"从用户视角不成立**：能拿到流，但播放器不用。
根因不是代理失败，而是**播放器按本地登录态决定可选画质**。
要突破它就得伪装"已登录"——那是比 vip 字段更大的谎，且会让评论/点赞以未登录身份失败。
**不做**（决策 4 / Q12 的边界）。

完整观测见 [`poc/verify/RESULT.md`](../poc/verify/RESULT.md) §六「补充实测 B」。

**产品侧的结论（已落地）**：

1. onboarding 要求登录主账号；§2.3 在未登录时说「未登录主账号，无对比基线」
2. **保留** `page/activate` 的游客分支（继续装规则）：全局路径规则本来就会代理，
   拒绝装 tab 规则并不能真的"不代理"，反而多一个 `document_start` 误判风险。
   分支注释已按实测改写

> ⚠️ 附带事实：**游客页不 SSR `__playinfo__`**，所以游客态主账号基线恒为"不存在"。

### 怎么复现这次实测

留作回归用（改了 `main-world.js` 或 `page.handler.ts` 时值得再跑一遍）：

1. 普通窗口打开视频页停留 60 秒 —— 不该再出现 `Out of Memory`（回环已修，见
   [guides/debugging.md](./guides/debugging.md) §8）
2. Ctrl+Shift+N 开 InPrivate（**别登录任何账号**），打开同一个 BV，等 10 秒
3. **在同一 InPrivate 窗口里**打开扩展选项页，先看 `无痕窗口数（当前分区可见）`
   —— 必须是 **1**，否则你打开的是普通实例的诊断页，结论无效
4. 读「当前页取流数据」四行

判据：`播放账号` 行是 2160p、但播放器只播 360p → 复现了"网络层成功、播放器层失败"。

### 为什么曾经以为它成立

三条观察都对，但结论推错了一步：

- `document.cookie` 里没有 `SESSDATA`，但通常有 `buvid3`
- 点赞/投币/评论/历史全部不可用（本来游客就没有这些）
- 「看视频」本身是游客可用的 → **但「能看」不等于「能看高画质」**

当时的设想是「游客 + 播放账号 B 取流 = 零成本解锁画质，用户不必交出主账号」——
这个产品机会**已被 A 否决**（游客只有 480P，且没有主账号就没有社交归属），
不要再拿它做定位论证。

## 2. ✅ Q2：DNR 临时规则在并发下的实际行为 — **已实测**

### 为什么重要

原设计用「`updateSessionRules` 加一条精确 nonce 的规则 → 立刻 fetch → 删规则」这个模式。它在**串行**场景下没问题，但真实场景是：

- 用户开了 5 个视频页
- 每个页面加载时都调 playurl
- 页面内可能同时有多个请求（预加载下一P、评论、推荐）

**MV3 的 DNR 规则是全局的，不是 per-request 的。** 如果两个请求同时用"同一个规则 ID"或"同一个 nonce"，或者规则还没删掉时另一个请求命中了它，就可能**用错账号的凭据**（严重）或**规则互相覆盖**（失败）。

### 实测结果（2026-10-25，Edge，20 并发 × 3 轮）

PoC：`poc/q2-dnr-concurrency/`，独立扩展、裸 JS、零依赖。用 `httpbin.org/anything` 做回声服务，**只留一个变量：DNR 在并发下会不会错配规则**。操作与判读见该目录 `README.md`。

| 策略 | 写法 | 对号 | 串号 | 无回显 | 判定 |
| --- | --- | --- | --- | --- | --- |
| **L1** 功能探测 | 单请求，`omit` / `include` 各测一次 | — | — | — | ✅ **两种模式都能改 Cookie 头** |
| **S1** `pool-random-id` | 每请求现加唯一 ID + 唯一 nonce 的规则，响应后删 | 60/60 | 0 | 0 | ✅ PASS |
| **S2** `persistent-id` | 规则 ID 常驻 + nonce，只替换内容 | 60/60 | 0 | 0 | ✅ PASS |
| **S3** `single-shared` | 全局单条规则反复改写（反例） | 3/60 | **0** | 57 | ⚠️ 每轮仅 1 个请求拿到凭据 |
| **S4** `no-nonce-persistent` | 一条常驻规则匹配整个路径，**不带 nonce**，值固定 | 60/60 | 0 | 0 | ✅ **PASS** |
| **L3** 回收 | 全部跑完后检查 session 规则残留 | — | — | — | ✅ **0 条** |

**三条结论：**

1. **DNR 并发安全，方案成立。** 180 个并发请求，串号数为 0。
2. **nonce 并非必需。** S4（不带 nonce 的常驻规则）同样 60/60。原因很直接：Pluma 的白名单请求全都该用同一个播放账号，规则的值在整个会话内全局一致，不存在"这条规则该给谁"的问题。**因此 `dnr.ts` 不需要规则 ID 池、不需要每请求 add/remove、不存在 S1 那一类并发风险。**
3. **S3 的失败方式值得记住**：nonce 被并发覆盖后规则对不上任何请求，于是 19/20 的请求**什么凭据都没拿到**，而不是拿错。也就是说 —— **nonce 让"串号"结构上不可能发生，代价是规则被覆盖时静默降级成未登录。** 这个失败模式比串号安全，但仍不可接受，所以也不能省到只剩一条全局规则。

### 二次复现（2026-10-25 21:10，`dnr.ts` 按 ADR 0006 重写后）

ADR 0006 要求「改 `dnr.ts` 必跑 Q2」。在把临时规则池改成**常驻规则**之后重跑了一次。

环境：Edge 156 / Windows / 扩展以未打包形式加载
配置：`concurrency: 20`、`rounds: 3`、回声服务 `httpbin.org`
结果：`poc/verify/result-q2-summary.json`（摘要入库）·
完整明细 `poc/verify/result-q2-auto.full.json`（110KB，已 gitignore，重跑即可复现）
执行：`poc/verify/run-q2-auto.cjs`（Playwright 自动跑，无需手动点击）

| 策略 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 串号 | 判定 |
| --- | --- | --- | --- | --- | --- |
| S1 `pool-random-id` | 20/20 | 20/20 | 20/20 | 0 | ✅ PASS |
| S2 `persistent-id` | 20/20 | 20/20 | 20/20 | 0 | ✅ PASS |
| **S3 `single-shared`** | **1/20** | **1/20** | **1/20** | 0 | ❌ 19 个无回显 |
| **S4 `no-nonce-persistent`（现行实现）** | **20/20** | **20/20** | **20/20** | 0 | ✅ **PASS** |

`leakedRulesAfter.count = 0` —— 跑完后零规则残留。

**与首轮结论完全一致**，S4 三轮全过。S3 的失败模式也稳定复现（每轮只有 1 个请求拿到凭据）。

> ⚠️ **S3 的危害比"串号"更隐蔽**：串号是"用错账号"，用户可能事后才发现；
> 而 S3 是**静默降级成未登录**，用户只以为"扩展没生效"，极难排查。
> 这是不能图省事只留一条全局规则的核心原因。

### 这次实测**没有**证明的事

诚实标注，别过度解读：

- **没测页面发起的请求。** PoC 的所有 fetch 都来自 Service Worker。DNR 的匹配条件是 URL + resourceType，与发起方无关，理论上等价，但没实测。
- **没测真实 B站 接口**（无登录态、无 WBI 签名、无 POST）。
- **没测"值在请求飞行途中被改"的情况。** S4 的值在一轮内固定。凭据刷新时改值会不会影响在途请求，没测。
- **没测规则数量上限**（`MAX_NUMBER_OF_SESSION_RULES`）。按路径建规则只有个位数，暂时不是问题。

### 决策影响

- ✅ **架构成立**，且比原设计简单 → 见 [`decisions/0006-no-per-request-nonce.md`](./decisions/0006-no-per-request-nonce.md)
- 退路（串行化 / `chrome.debugger` / 本地服务）**不再需要**，ADR 0002 里那节作废

## 3. ✅ Q3：播放页对 playurl 的调用次数与时机 — **已实测**

### 为什么重要

决定"代理是否够用"。三种可能：

| 情况                    | 含义           | 影响      |
| --------------------- | ------------ | ------- |
| 只调 1 次，返回所有画质         | 代理 1 次就够，最简单 | ✅ 理想    |
| 每切一次画质就调 1 次          | 需要代理每次切换     | 可接受     |
| 播放过程中周期性调（如心跳式刷新 URL） | 需要长期保持代理生效   | 注意流地址时效 |

DASH 的流地址通常带时效签名（`deadline` 参数），**如果播放中途地址过期，播放器会重新调 playurl**。这就意味着代理必须一直在线，且不能因为 SW 休眠而失效。

### 需要验证什么

1. 打开一个视频保持不变，观察 30 分钟内 playurl 被调用几次
2. 手动切换画质（1080P→4K→1080P），观察调用次数
3. 拖动进度条、暂停恢复，是否触发
4. 多P视频切P，是否触发
5. 番剧自动连播，是否每集触发

### ✅ 验证结果（2026-10-25）

| 场景 | 新增 playurl 请求 |
| --- | --- |
| 首次加载 | **1 次** |
| 静置 30 秒 | **0 次** |
| 切画质（480P → 360P → 480P） | **0 次** |
| 拖进度到 60% | **0 次** |
| 切 P（P4 → P5） | **1 次** |

**结论：低频。** playurl 只在**页面加载**和**切 P** 时调用；切画质、拖进度都不触发——播放器用同一份 dash 在本地切换。

两个推论：

1. **并发压力远低于原本担心的程度**（不是"5 个视频页 + 预加载 + 评论 + 推荐"那种洪水），实际上限 ≈ 同时加载的标签页数。
2. **但代理只有一次机会**：页面加载那一次 playurl 若没被成功替换，整页就锁死在主账号画质上——用户之后切 4K 也切不动，因为本地 dash 里没有那条轨道。**单次成功率比并发安全更关键。**

### 决策影响（已落定）

→ 不需要做"流地址缓存 + 提前刷新"（至少 70 秒视频内不刷新）。长视频中途是否刷新待补测。

验证脚本：[`poc/verify/q3-interaction.cjs`](../poc/verify/q3-interaction.cjs)、[`q3b-quality-switch.cjs`](../poc/verify/q3b-quality-switch.cjs)

## 4. 🔴 Q4：番剧"能播会员专享"的真实边界

### 为什么重要

这是最容易过度承诺的地方。用 B 的会员身份取流，能拿到 4K 视频流，**不等于能播放会员专享内容**。可能的情况：

| 场景            | 是否能播    | 原因                             |
| ------------- | ------- | ------------------------------ |
| 免费番剧的高画质档     | ✅ 能     | 只是画质权限问题                       |
| 会员专享番剧（付费内容）  | ❓       | 可能要求播放页本身有会员态，或需要额外的一次"播放授权"接口 |
| 仅限港澳台/特定地区的番剧 | ❌ 大概率不能 | 需要区域 IP，与本方案无关                 |
| 大会员专享电影/纪录片   | ❓       | 同付费内容                          |
| 付费课程（cheese）  | ❓       | 需购买，与大会员无关                     |

**关键疑问**：番剧播放页在加载时，前端会用当前登录态（A）判断"你有没有权限看"，若无权就显示"开通大会员"遮罩，**根本不会发起 playurl 请求**。这种情况下，代理 playurl 是无用的——因为请求压根没发出。

### 需要验证什么

1. 用**非会员账号 A** 打开一个会员专享番剧，观察前端是否发出 `pgc/player/web/v2/playurl` 或 `/ogv/player/playview`
2. 若发出 → 代理它，看是否返回可播流
3. 若不发出 → 需要额外手段（伪造 `pgc/view/web/season` 的权限字段，风险更高）
4. 试用/试看机制：会员番剧通常有"前 6 分钟试看"，代理后能突破到完整吗？

### 验证方式

非会员账号 + DevTools，看请求是否发生、以及遮罩出现的时机。

### 决策影响

- 若番剧付费内容代理不了 → **README 必须明确写"番剧仅解锁画质，不解锁付费内容"**，否则会成为 issue 区最大噪音源
- 若需要伪造 season 权限字段才能播 → 风险等级上一个台阶（这是真正的"绕过"而非"借用身份"），需要重新评估合规边界

## 5. ✅ Q5：到底需不需要主账号的 cookie — **已实测 + 已决策：申请 cookies 权限**

### 为什么重要

原判断是"完全不需要 `cookies` 权限"，理由是设备 cookie 能从 `document.cookie` 借、
主账号的 `SESSDATA` 本来就不需要。**这个判断在 P1 实装时被推翻。**

### 推翻的原因：播放账号凭据读不到

`cookies` 权限的真正用途**不是读主账号**，而是**读播放账号自己**：

| 要读什么 | 能用 `document.cookie` 吗 | 结论 |
| --- | --- | --- |
| 设备 Cookie（`buvid3` 等） | ✅ 能（非 httpOnly） | 不需要权限 |
| **播放账号的 `SESSDATA`** | ❌ **httpOnly，读不到** | **必须用 `cookies`** |
| 播放账号的 `bili_jct` / `DedeUserID` | ❌ 同上 | 必须用 `cookies` |

**扫码登录成功后，B站通过 `Set-Cookie` 下发凭据。** 而：
- `fetch` 读不到 `Set-Cookie`（forbidden response header）
- `document.cookie` 读不到 httpOnly 的 `SESSDATA`

**所以不用 `chrome.cookies` 就根本拿不到播放账号凭据，登录流程无法完成。**

### 决策：申请 `cookies`，但严格限定用途

```json
"permissions": ["cookies"],
"host_permissions": ["*://*.bilibili.com/*"]
```

**三条自律**（写进 README，让用户能核对）：

1. **只在扫码登录成功那一刻调用一次**，之后走 vault 加密存储
2. **只读 `www.bilibili.com` 的 `SESSDATA` / `bili_jct` / `DedeUserID` 三个**
3. **不读主账号、不读其他网站、不持续监听**

见 [ADR 0008](./decisions/0008-cookies-permission-for-playback-credential.md)。

### 对原"不需要"判断的说明

原分析里"设备 cookie 从 `document.cookie` 借"这一点**仍然成立**，实装时也确实这么做的。
被推翻的只是结论——漏考虑了"播放账号凭据本身怎么读"。

## 6. ✅ Q6：凭据加密的密钥从哪来 — **已决策（已简化）**

### 最终决策：只有一种模式 —— 随机密钥 + AES-GCM，密钥同存本地

原方案 C（随机密钥 + 可选启动时解锁）**经实装后推翻**，见 [ADR 0009](./decisions/0009-drop-passphrase-mode.md)。

### 为什么砍掉口令模式、也不做自动锁定

两条都推翻了：口令模式**防不住本机程序**（能读 `storage.local` 的人同样能读 cookie 库和 DPAPI）；
自动锁定只是清内存缓存，下次 `loadCredential()` 从磁盘重新 import，**攻击者执行一次就拿到明文**。
有安全外观、无安全实质的机制比没有更糟。

完整论证与"README 必须怎么诚实表述"见 [ADR 0009](./decisions/0009-drop-passphrase-mode.md)。

### 必须配套的 README 表述

见根 [`README.md`](../README.md)「凭据如何存储」。**绝对不要写"军事级加密""银行级安全""等同于系统级保护"。**

### 加密的到底是什么（别搞错对象）

**密钥用来加密播放账号的登录凭据，不是加密视频流、不是加密 cookie jar。**

要加密的字段：

| 字段 | 泄漏后果 |
| --- | --- |
| `sessdata` | **最严重**。等于拿到你的登录态，可以以你的身份发评论、点赞、看会员内容 |
| `bili_jct` | CSRF token，POST 类接口的通行证 |
| `dedeUserId` | 用户 mid。本身公开，但和 `sessdata` 配在一起就是完整身份 |

**为什么必须自己加密**：`chrome.storage.local` 在磁盘上是一个**明文** LevelDB 文件。Chrome 会用系统 DPAPI 加密 cookie 库，但**不加密扩展的 storage**。所以不加密的话，任何能读到这个文件的程序、任何备份同步工具、任何拿到你磁盘的人，都能直接看到 `SESSDATA` 明文。

**它防不住什么**（必须诚实）：

- 扩展自己要解密才能用，所以能在你的浏览器 profile 里执行代码的恶意程序，一样能拿到明文
- 密钥和密文在同一个 `storage.local`，能读到密文的人通常也能读到密钥
- 它防的是"顺手看到 / 备份泄漏 / 磁盘取证"，不是"针对性的本地攻击"

### 数据结构（实际实现）

```ts
// storage.local['pluma:vault:blob'] —— 密文
interface EncryptedBlob {
  v: 1;        // 格式版本，将来换算法靠它迁移
  iv: string;  // base64，每次加密随机生成，不复用
  data: string;// base64，密文（含 GCM 认证标签）
}

// storage.local['pluma:vault:key'] —— 随机密钥
// 数据密钥的 base64 raw 形式（32 字节，AES-256）
```

> 原设计里的 `alg` / `mode` / `wrappedKey` / `salt` / `iter` 字段**全部移除**——
> 单一模式下它们没有意义，留着只会让人以为还有别的模式。

### 密钥生命周期

| 时机 | 做什么 |
| --- | --- |
| 首次存凭据 | `crypto.subtle.generateKey({AES-GCM, 256})` → 导出 raw → base64 存 `pluma:vault:key` |
| 存 / 改凭据 | 每次生成**新的随机 IV**，AES-GCM 加密，写 `data` + `iv` |
| 读凭据 | 先确认 `pluma:vault:key` **存在**，再 import 解密 |
| 删除播放账号 | 同时删 blob 和 key，并清空内存缓存 |
| 卸载扩展 | Chrome 自动清空该扩展的全部 storage |

**⚠️ 读凭据时必须校验密钥存在，不能只看内存缓存。**

曾写过 `if (!cachedKey) { 读密钥 }`——结果缓存会掩盖"磁盘上的密钥已被删除"这个事实：用户清了 storage 后，扩展仍能读出凭据，表现为"清不干净"。

现在每次都校验 `pluma:vault:key` 是否存在，并用 `cachedMaterial` 比对"磁盘密钥是否被换过"。有回归测试钉死。

### 未来的正确方向

若要系统级保护，正确做法是 **Native Messaging + Windows DPAPI**，让凭据绑定 Windows 用户账户。但那需要本地可执行程序，与 [ADR 0001](./decisions/0001-use-mv3-pure-extension.md)「纯 MV3 扩展」冲突，属于 v2 范畴。

## 7. ✅ Q7：主账号的定义方式 — **已决策**

### 决策：方案甲 —— 扩展不管理主账号

**主账号 = 浏览器当前登录态。扩展不存储、不读取、不切换它。**

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| **甲：不管理主账号** | 主账号就是浏览器里登录着的那个，扩展完全不碰 | **✓ 采用** |
| 乙：多主账号 profile | 像 bilipai 一样在扩展内配置多个主账号 | ✗ v1 不做 |

### 理由

1. **这是权限最小化的核心**。一旦扩展要"管理"主账号，就必须存储主账号凭据，`cookies` 权限和"读取你的所有浏览数据"警告就躲不掉了（见 Q5）。
2. **风险归零**。用户最大的恐惧是"我的主账号会不会被这个扩展动了"。答案必须是"从技术上就不可能"——而不是"我们保证不会"。区别在于后者需要被信任，前者不需要。
3. **多主账号有天然的更优解**：Chrome/Edge 原生的多用户 profile。用户想同时挂两个主账号，开两个浏览器 profile 就行，这比扩展自己管安全得多，也不需要我们写任何代码。
4. **架构上更简单**。因为浏览器全程是主账号，所有社交行为（点赞/投币/评论/收藏/历史）天然归属正确，不需要任何身份切换逻辑。

### 对产品文案的影响
Onboarding 里必须出现这句话：**"主账号无需配置，自动沿用你浏览器当前的登录状态。"** 这是最强的信任信号，要放在显眼位置，不能藏在说明文档里。

2. **二分法探测 `fnval`**。用播放账号分别请求 `fnval` = 16 / 16+2048 / 16+256 / 4048 / 4304，对比返回的 `dash` 结构：
   - `dash.video[]` 里出现 `codecid=12`（AV1）→ AV1 位生效
   - 出现 `dash.dolby.audio[]` → 杜比音频位生效
   - 出现 `dash.dolby.vision[]` → 杜比视界位生效
   - 出现 `dash.flac.audio` → Hi-Res 位生效
3. **看 `accept_quality` / `accept_description` 数组**。它直接告诉你"这个账号对这个视频能拿哪些清晰度"，是判断权限边界的最佳信号。

1. Hi-Res 到底对应哪一位（我此前推测 `+256`，**未经核实**）
2. `dash.dolby.audio` 与 `dash.dolby.vision` 分别对应哪些位
3. `fnval=4048` 是否真的包含 Hi-Res（我推测不包含）
4. 是否有必要为不同场景发不同 `fnval`（全量请求 vs 保守请求）

**绝对不要照抄我给的数字。** 我给的 `4048` / `4304` 都是推算值，用官方前端抓包得到的值才是唯一可信来源。

## 11. ✅ Q11：浏览器支持优先级 — **已决策**

### 决策：v1 仅 Chrome + Edge

| 浏览器 | 决策 | 理由 |
| --- | --- | --- |
| **Chrome** | ✅ v1 支持 | 基准实现 |
| **Edge** | ✅ v1 支持 | 同为 Chromium 内核，DNR 实现一致，**几乎零额外成本** |
| Firefox | ⏳ v1.5 | MV3 实现细节不同（`declarativeNetRequest` 有差异、SW 用 Event Page 模型），适配成本不低，但用户占比低 |
| 国产浏览器（360/QQ/搜狗） | ⏸ 暂不承诺 | 多基于 Chromium，理论上可装，但不做官方支持和测试。README 里写"未测试，欢迎反馈" |

### 理由

1. **Chrome + Edge 共用一套代码**。两者都是 Chromium，manifest 和 API 行为一致，维护成本几乎为零。这是性价比最高的一步。
2. **Firefox 的 DNR 差异是真实成本**。Firefox 对 `declarativeNetRequest` 的支持是后加的，行为与 Chrome 不完全一致，尤其是 `modifyHeaders` 的能力边界。更重要的是，Q2（DNR 并发安全）在 Firefox 上可能表现不同——意味着要跑两遍验证。放到 v1.5 是合理的。
3. **国产浏览器不承诺但不禁用**。用户装得上的概率不低（内核版本够新就行），但我们没有测试资源。README 写明"未测试"即可，既不误导也不排斥。

### 对开发的影响
- 代码里不要用 Chrome 独有的 API（如 `chrome.offscreen`），用标准 MV3 子集
- 测试只需在 Chrome 做，Edge 做一次冒烟测试
- manifest 的 `minimum_chrome_version` 建议设为 **120**（保证 DNR 的 `modifyHeaders` 行为和 `storage.session` 可用性）

### 附带决策：不支持无痕模式

**manifest 不声明 `incognito` 字段，即扩展在无痕窗口中不运行。这是预期行为，不是 bug。**

| 选项 | 后果 | 结论 |
| --- | --- | --- |
| 不声明（默认） | 无痕窗口里扩展不存在 | ✅ **采用** |
| `incognito: split` | 无痕里是独立实例、独立 storage → **用户要在无痕里重新扫码登录播放账号** | ✗ 对一个"临时看个 4K"的场景是反体验 |
| `incognito: spanning` | 共享实例，DNR 规则和 storage 跨窗口共享 → **反而扩大出错面**，且无痕会话能读到持久凭据，语义混乱 | ✗ |

**理由**：无痕模式的设计意图是"不留痕迹"。我们往无痕会话里注入另一个账号的凭据，等于把两个身份绑进同一个无痕会话——语义上说不通。而这个产品是"日常看视频"的工具，不是隐私工具。

**配套动作**：
- 根 `README.md` 的「它不做什么」里写明

## 12. ✅ Q12：伪装会员标识到底做不做 — **已决策**

### 决策：v1 不做

**删除 Dual Account Helper 里的那 7 个 PATCH_PATHS。** 技术方案 §4.1 里"伪装路径"整节标记为"v1 不实现"。

### 理由

1. **收益很小**：只是让播放器里的进度条颜色、画质菜单的"开通"标记看起来顺眼一点。用户真正的诉求（能看 4K/Hi-Res）已经满足了。
2. **风险实在**：前端显示"大会员"但账号实际不是，这种不一致是风控最容易捕捉的信号之一。为了视觉一致去触发风控，性价比极低。
3. **伦理问题**：用户看到"大会员"标识，会误以为自己真的开通了，可能去客服投诉或产生账单误解。开源项目不该制造这种困惑。
4. **维护成本**：这 7 个路径的响应结构比取流接口更复杂、变化更频繁，维护它等于给自己挖坑。

### 如果将来要做
必须是**显式的高级选项**，默认关闭，开关文案写明"仅修改界面显示，不改变账号实际权益"，且在设置里用 warning 色标注。**v1 阶段连这个开关都不放**——没有足够用户需求时，不主动引入风险。

### 对 UI 的连带影响
UI 设计规范里 popup 的"伪装会员标识"开关**在 v1 中移除**，popup 只剩"自动接管取流"一个开关。这反而让 popup 更简洁。

**为什么不用 `La Pluma`（明日方舟角色名）**：
1. 那是鹰角网络的知识产权，项目做大后有商标风险

**为什么名字不自解释**：用户接触项目时几乎从不只看到名字——GitHub 搜索结果有描述、商店有一整行描述、README 有副标题。名字唯一无法被替代的作用是**被记住、被复述**。`bili-*` 前缀在 GitHub 上极其拥挤（同类项目几十个），恰恰因为没有区分度。

### ✅ Q13 协议部分：已定 —— GPLv3 + 第 7 条额外条款

**决策：GPL-3.0-only，并附 GPLv3 第 7 条允许的额外条款。**

理由、律师函背景、与 MIT 的逐条对比、附加条款原文、"参考设计 ≠ 可以抄代码"的澄清，
**全部在 [ADR 0003](./decisions/0003-gplv3-with-additional-terms.md)**。本节只留三条结论：

1. **许可证挡不住律师函**——B站已对 PiliPala / bilibili-API-collect / downkyi 发函。
   MIT 不会更安全，GPLv3 也不会更危险。真正的风险控制在于**分发方式**。
2. **选 GPLv3 是为了防商业化**——最大滥用风险是"改名包装成付费软件卖会员权益"，
   GPLv3 强制衍生作品开源，能堵住这条路；MIT 允许闭源商用。
3. **附加条款落在 [`ADDITIONAL-TERMS.md`](../ADDITIONAL-TERMS.md)**，不在本文重复。

> 分发渠道（只发源码 / 不上架 / 不发预编译包）是 **Q16** 的职责，本节不重复。

#### README 里关于许可证的写法

**不要在 README 首屏宣传许可证。** 首屏应该是：项目名 + 副标题 + 免责声明 + 合规提示。许可证放在最后，一行带过：

> 本项目采用 GPLv3 许可证，详见 [LICENSE](../LICENSE) 与 [附加条款](../ADDITIONAL-TERMS.md)。

把协议放显眼位置，会给用户"这是个正经商业项目"的错觉，反而放大风险感知。

## 15. ✅ Q15：是否接远程配置 — **已决策：不做**

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 远程拉取白名单 | 接口变了不用发版 | 引入网络依赖、隐私面、供应链风险 | ✗ 否决 |
| **本地版本号 + 提示升级** | 零网络依赖 | 用户可能延迟升级 | **✓ v1 采用** |

**决策理由**：为了省一次发版，去引入"从网络拉配置"这个新的安全与隐私面，是把简单问题复杂化。而且本项目分发方式是**只发源码**（Q16），用户本来就每次都要自己构建，"远程配置"收益更小。

用户抱怨"某个场景没生效"时，先查本地白名单版本号，提示"有新版本可更新"即可。

## 16. 🔴 Q16：分发渠道与收到律师函的预案 — **待落实**

### 为什么这条是 🔴 而不是 🟢

前面所有决策都在回答"怎么做"，这条在回答"**做出来之后能不能存在**"。B站已经实锤对同类项目发函并导致关停（见 Q13 背景表），这不是低概率风险，而是**这个品类的必遇事件**。

**必须提前想清楚，否则辛苦做出来的东西可能在发布第一周就消失。**

### 分发决策

| 渠道 | 决策 | 理由 |
| --- | --- | --- |
| GitHub 源码仓库 | ✅ **唯一的正式发布渠道** | 只放源码 + 自行打包说明，不发预编译包 |
| Chrome / Edge 商店 | ❌ **v1 不上架** | B站投诉后必下架；且商店审核对"修改请求头"类扩展本就严格 |
| 预编译 zip / crx | ❌ **不发** | 减少"你在分发软件"的观感，也更难被指控"提供可用的侵权工具" |
| 网盘 / 社区转发 | ⚠️ 无法控制 | 不主动提供，也不阻止用户自行打包 |

**一个反直觉但重要的判断**：不发预编译包、不上架商店，看起来像是"让用户更难用"，实际上是在**降低你的暴露面**。bilibili-API-collect 只删文档就过关了；downkyi 被打的核心是"提供下载功能"。两者的差别不在代码，在**你提供了什么能力**。

### 收到律师函的预案（做成 checklist，提前准备）

1. **不要慌，也不要公开发泄**。PiliPala 和 downkyi 的作者处理都很克制，反而保留了社区同情。
2. **第一步：停止更新**，仓库设为 archived（**不要删除**——删除会被解读为心虚，archived 是体面的处理）。
3. **第二步：README 换成一封说明**，写清"因收到权利方通知，本项目停止维护"，保留原代码供已下载者参考。
4. **第三步：不发对抗性言论**。不要在 issue 区号召"大家快去 fork"——这会让事情升级。
5. **第四步：评估是否需要法律意见**。如果对方主张的是"不正当竞争"而非"著作权侵权"，性质较轻；如果同时主张著作权，需要认真对待。

### 预防性措施（现在就能做）

| 措施 | 作用 |
| --- | --- |
| README 首屏放免责声明 | 表明非官方、非商业、使用者自负风险 |
| 定位措辞用"管理工具"不用"解锁" | 见 Q10。措辞会影响对方如何定性 |
| 不提供任何"绕过付费"能力 | 见 Q4。这是能否站住的关键分界线 |
| 不做中文 SEO 优化 | 不主动推广，降低被发现概率（但别指望有效） |
| **先想好"如果明天就被关停，这个项目还值得做吗"** | 如果答案是"不值得"，说明动机有问题 |

### 诚实的结论

**这个项目的生命周期可能很短。** 接受这一点不是悲观，是现实。所以：

- 把它当作**技术实践项目**，价值在于你学会了 MV3、DNR、请求级代理、账号隔离这一整套东西
- 而不是当作"要长期运营的产品"
- 若真想做长期项目，应该选一个不依赖特定平台灰产的题目

**这个判断不影响继续做，但影响你怎么投入。** 别为它辞工作，也别指望它带来收入（Q10 已定 v1 不商业化）。

### 2026-10-25 实装阶段的三次翻案

> 以上三行是**决策当时的记录**，保留作历史。实装后发现前提不成立：

| 原决策 | 推翻原因 | 新决策 |
| --- | --- | --- |
| 不申请 `cookies` | 只分析了主账号，**漏了播放账号**：`SESSDATA` 是 httpOnly，`document.cookie` 读不到，`fetch` 也读不到 `Set-Cookie`。不申请就完不成登录 | **申请**，限定域名与用途（[ADR 0008](./decisions/0008-cookies-permission-for-playback-credential.md)） |
| 不支持无痕模式 | 基于"无痕里扩展不生效"的错误假设，**实测完全能跑**。且登录播放账号必然覆盖主账号登录态（Cookie 按域名唯一），隔离窗口是唯一解法 | **用 `incognito: "split"`**，在无痕分区登录（[ADR 0012](./decisions/0012-isolated-window-login.md)） |
| Q6 只做 `mode: local` | 口令模式防不住"本机程序"（能读扩展存储的人同样能读 cookie 库），自动锁定也只是清缓存、下次自动重新 import。**两者都只有安全外观、没有安全实质** | **单一模式**，`mode` 字段整个删掉（[ADR 0009](./decisions/0009-drop-passphrase-mode.md)） |

**这三条的共同教训**：决策阶段的威胁模型分析，必须在实装时用真实代码再验证一遍。纸面上的"不需要""不支持""够用了"，都可能在写代码时被推翻。
