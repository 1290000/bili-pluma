## 1. ✅ Q1：主账号未登录时，功能还能成立吗 — **已实测：不成立**

| 半 | 问题 | 结果 |
| --- | --- | --- |
| **A** | 游客**不带**播放账号凭据时能拿到什么 | 480P / 360P |
| **B** | 游客**带上**播放账号凭据（本扩展的做法）能拿到什么 | 网络层 2160p · Hi-Res，但**播放器只播 360p** |

**结论：游客模式从用户视角不成立。** 能拿到流，播放器却按**本地登录态**决定可选画质，手里有 2160p 也不选。
根因不在 DNR 代理，而在播放器层；要突破它就得伪装"已登录"——那是比 vip 字段更大的谎，且会让评论/点赞以未登录身份失败，**不做**（决策 4 / Q12 的边界）。

产品侧已落地两条：

1. onboarding 要求登录主账号；未登录时面板只说「未登录主账号，无对比基线」
2. **保留** `page/activate` 的游客分支（继续装规则）：全局路径规则本来就会代理，拒绝装 tab 规则并不能真的"不代理"，反而多一个 `document_start` 误判风险

附带事实：游客页不 SSR `__playinfo__`，所以游客态的主账号基线恒为"不存在"。

完整观测见 [`poc/verify/RESULT.md`](../poc/verify/RESULT.md) §六「补充实测 B」。

## 2. ✅ Q2：DNR 临时规则在并发下的实际行为 — **已实测：并发安全，不需要 nonce**

**180 个并发请求，串号 0、规则残留 0。** 现行实现是「一条常驻规则匹配整个路径、不带 nonce、值固定」，不需要规则 ID 池，也不需要每请求 add/remove（[ADR 0006](./decisions/0006-no-per-request-nonce.md)）。

**一句为什么**：实测里被放弃的"全局单条规则反复改写"方案，失败方式是 nonce 被并发覆盖 → 请求**什么凭据都没拿到**。
那是静默降级成未登录（极难排查），比串号（能用错账号，事后能发现）更隐蔽。

证据：逐轮数据与被放弃的方案见 [ADR 0006](./decisions/0006-no-per-request-nonce.md) §理由；可复跑的 PoC 见 `poc/q2-dnr-concurrency/`；自动化并发回归见 `poc/verify/run-q2-auto.cjs`。

⚠️ **改 `dnr.ts` 必须重跑那两个脚本**（并发 + 关开关清零），见 AGENTS.md §4.3。单测测不到 DNR。

## 3. ✅ Q3：播放页对 playurl 的调用次数与时机 — **已实测：低频**

| 场景 | 新增 playurl 请求 |
| --- | --- |
| 首次加载 | **1 次** |
| 静置 30 秒 / 切画质 / 拖进度 | **0 次** |
| 切 P（P4 → P5） | **1 次** |

playurl 只在**页面加载**和**切 P** 时调用；切画质、拖进度都不触发——播放器用同一份 dash 在本地切换。两个推论：

1. **并发压力远低于担心**：实际上限 ≈ 同时加载的标签页数
2. **代理只有一次机会**：页面加载那一次若没换成功，整页就锁死在主账号画质上（用户之后切 4K 也切不动，本地 dash 里没有那条轨道）。**单次成功率比并发安全更关键**

决策影响：不需要做"流地址缓存 + 提前刷新"。脚本见 [`poc/verify/q3-interaction.cjs`](../poc/verify/q3-interaction.cjs)、[`q3b-quality-switch.cjs`](../poc/verify/q3b-quality-switch.cjs)。

## 3a. ✅ 流地址时效（Step F）— **已实测闭合，且不需要做防护**

从已加载的 `bilivideo.com` 资源里读 `deadline`：**地址有效期 116 分钟**（绝对时间戳，从加载那刻算）。
过期后播放器重新调 playurl，而那时**代理仍然生效**——路径规则是常驻 `sessionRules`，不是一次性替换。

**为什么不需要做防护**：DNR 规则的生命周期**长于流地址**，所以"地址过期 → 重新取流"这条路上没有空窗。
全局路径规则（ID 10000 段）在总开关开启时由 `enableProxy()` 装上，SW 重启时 `rebuildRulesIfEnabled()` 重建，
且不带 `tabIds`，标签页休眠不影响命中；标签页规则（20000 段）只影响 4K 画质，不影响"能不能拿到流"。
**v1 不需要任何"提前刷新地址"的机制**——把复杂度推给浏览器，而不是自己造缓存。

| 边界场景 | 结果 | 处理 |
| --- | --- | --- |
| 单集 ≤ 116 分钟 | 完全正常 | 不需要 |
| 单集 > 116 分钟（长电影、3 小时直播回放） | 到点重新取流，代理仍在，**理论上正常** | v1.5 观察项，不是 v1 阻塞 |
| 浏览器休眠超过 116 分钟再唤醒 | 同上，走重新取流 | 同上 |

⚠️ **诚实标注**：后两行是**从机制推导**的，不是实测（没有任何自动化手段能稳定复现"116 分钟后重新取流"）。
**不要**在任何文档里写成"已验证长视频没问题"。

## 4. ✅ Q4：番剧的真实边界 — **已实测，结论分两半**（2026-10-28 修正）

**原结论只覆盖了一半场景**，它把"页面不发 playurl"误读成"代理架构对番剧完全无效"，于是判定 v1 不支持番剧。实际两条路：

| 场景 | 页面发什么请求 | 怎么支持 |
| --- | --- | --- |
| **整页加载 / 刷新** | 零请求：取流结果由服务端写进 HTML 的 `__playinfo__` | P2 缓存 + `__playinfo__` setter **同步注入**完整流（[ADR 0020](./decisions/0020-pgc-sync-injection-and-reload.md)）。改一个变量，不需要拦请求 |
| **SPA 切集** | **`GET /ogv/player/playview`** | 主世界拦**响应**、换完整集 dash（[ADR 0023](./decisions/0023-intercept-playview-durl-swap.md)）。**绝不能开 DNR**——一开就灰屏 |

⚠️ **两条路的判据不能混**：切集时 `__playinfo__` **完全不赋值**（cid 停在上一集），所以任何"在 setter 里处理切集"的代码都是死代码。

为什么它曾是最大未知数：这是**最容易过度承诺**的地方——用播放账号取流能拿 4K，**不等于**能播放会员专享内容。
当时设想过"代理那个 playview **POST** 请求就能解锁"，那条假设三处都错：它是 **GET**；只在 SPA 切集时出现；
而且进了 DNR 会因"换了 Cookie 后服务端返回完整集 dash、与播放器按 durl 准备的管道冲突"而灰屏（两次事故）。

**对合规结论的意义**：实测确认**不涉及绕过付费墙**——没有伪造 season 权限字段，也没突破试看限制。
换流用的是播放账号**自己**的权益，改的只是"播放器拿哪条 URL、在哪一秒停"。Q10 那句"不破解、不绕过付费墙"因此站得住。

## 5. ✅ Q5：到底需不需要主账号的 cookie — **已实测 + 已决策：申请 `cookies` 权限**

**结论：需要，但用途与直觉相反**——不是读主账号，而是**读播放账号自己**（[ADR 0008](./decisions/0008-cookies-permission-for-playback-credential.md)）。

一句为什么：扫码成功后 B站通过 `Set-Cookie` 下发凭据，而 `fetch` 读不到 `Set-Cookie`、`document.cookie` 读不到 httpOnly 的 `SESSDATA`
（`bili_jct` / `DedeUserID` 同理）。**不用 `chrome.cookies` 就根本拿不到播放账号凭据，登录流程无法完成。**
设备 Cookie（`buvid3` 等）仍从 `document.cookie` 借，那部分原判断成立。

**三条自律**（写进 README，让用户能核对）：① 只在扫码登录成功那一刻调用一次，之后走 vault；② 只读 `www.bilibili.com` 的 `SESSDATA` / `bili_jct` / `DedeUserID` 三个；③ 不读主账号、不读其他网站、不持续监听。

## 6. ✅ Q6：凭据加密的密钥从哪来 — **已决策：随机密钥 + AES-GCM，单一模式**

口令模式与自动锁定都经实装推翻（[ADR 0009](./decisions/0009-drop-passphrase-mode.md)）。
一句为什么：口令模式**防不住本机程序**（能读 `storage.local` 的人同样能读 cookie 库和 DPAPI）；自动锁定只是清内存缓存，
下次 `loadCredential()` 又从磁盘重新 import。**有安全外观、无安全实质的机制比没有更糟。**

**加密对象别搞错**：加密的是**播放账号的登录凭据**，不是视频流、不是 cookie jar。所以必须自己加密——
`chrome.storage.local` 在磁盘上是**明文** LevelDB，Chrome 不加密扩展 storage。
它**防的是**顺手看到 / 备份泄漏 / 磁盘取证，**防不住**针对性的本地攻击（扩展自己也要解密，密钥与密文同存 `storage.local`）。

⚠️ **README 措辞**：见根 [`README.md`](../README.md)「凭据如何存储」。**绝对不要写"军事级加密""银行级安全""等同于系统级保护"。**
数据结构、密钥生命周期等实现细节以 `src/platform/storage/vault-storage.ts` 与 [ADR 0009](./decisions/0009-drop-passphrase-mode.md) 为准，本文不复述。

若要系统级保护，正确方向是 **Native Messaging + Windows DPAPI**，但那需要本地可执行程序，与 [ADR 0001](./decisions/0001-use-mv3-pure-extension.md) 冲突，属 v2 范畴。

## 7. ✅ Q7：主账号的定义方式 — **已决策：扩展不管理主账号**

**主账号 = 浏览器当前登录态。扩展不存储、不读取、不切换它。** 多主账号 profile（bilipai 式）v1 不做。

一句为什么：这是**权限最小化的核心**——要"管理"主账号就必须存主账号凭据，`cookies` 权限与"读取浏览数据"警告就躲不掉。
更大的收益是**风险归零**：答案是从技术上就不可能，而不是"我们保证不会"——后者需要被信任，前者不需要。
多主账号也有天然更优解：Chrome/Edge 原生多 profile。且浏览器全程是主账号，社交行为天然归属正确，不需要任何身份切换逻辑。

**对产品文案的影响**：onboarding 里必须有这句话——**"主账号无需配置，自动沿用你浏览器当前的登录状态。"** 放显眼位置，不能藏进说明文档。

## 8. ✅ Q8：白名单覆盖面是否完整 — **已验证（v1 范围，2026-10-26）**

**判据不看路径、看结果**：主账号是非会员（1080P 上限），所以任何入口下**能播到 1080P 以上**，就证明那条路径被白名单覆盖了，不需要知道它走哪个接口。
（不抓 playurl 是因为 `bsk network` / `bsk debug requests` 都是小容量环形缓冲，视频页一加载就被 `.m4s` 分片挤掉，见 [guides/browser-skill-setup.md](./guides/browser-skill-setup.md)。）

| 入口 | 结果 |
| --- | --- |
| 直接打开视频页 | ✅ 2160p（基线） |
| 多 P（`?p=1` / `?p=2`） | ✅ 2160p |
| **互动视频**（分支取流） | ✅ **4096×2048**（非会员该档是 1920×960，2048 高即 4K 档） |
| **移动 UA**（`m.bilibili.com`） | ➖ **不适用**：移动站没有网页内播放器，**不是没覆盖** |
| 番剧 / 国创 / 电影 | ✅ **已支持**（见 §4） |
| 稍后再看列表直接播放 | 🟡 **未测，风险低**：点开即跳 `/video/`，与基线同路径 |
| hover 高清预览 | ➖ **放弃**：预览画质本身极低，"能否 1080P+"判据不适用 |
| 直播 / 课程 | ➖ **不在范围**：`routes.ts` 里 `enabled: false`。**这是"决定不支持"，不是"忘了测"** |

漏一个就等于"某个场景下画质没生效"，而用户不会来报 bug，只会觉得插件没用。

## 9. ⏸ Q9：`fnval` 的精确取值 —— **不再是前置**

> **2026-10-26 更新**：画质体检表被砍（[ADR 0016](./decisions/0016-drop-quality-report-page.md)），
> `fetchPlayurlAsPlayback` / `playurlQuery` 一并删除 —— 我们**不再自己发 playurl**，
> 页面请求用的是 B站 自己的 `fnval`，天然正确。

### ⚠️ 前置坏消息：原定参考源已失效

**bilibili-API-collect 已于 2026-01-28 永久关停**（因原作者的停止维护决定），仓库已 `archived`，内容被清空至 README 说明。这意味着原计划的"去翻它的 fnval 位表"这条路**已经走不通**。

现有的替代选项：

| 来源 | 可用性 | 风险 |
| --- | --- | --- |
| 原仓库 GitHub | ❌ 已 archived，内容已删 | — |
| 各 fork（如 `peritot/bilibili-api-collect`） | ⚠️ 部分 fork 可能保留快照 | **同样已停止维护的内容**，参考它等于接力传播，风险与原作者相同 |
| 各类镜像站 | ⚠️ 不稳定，随时消失 | 同上 |
| **Blackboard / 官方 UA 观察 + 自己抓包** | ✅ 合法且可靠 | 无 |

### ✅ 决策：不再依赖第三方文档，改为自证

**Q9 的验证路径改为纯实测：**

1. **从浏览器实际请求里读参数**。打开任意视频页，DevTools Network 过滤 `playurl`，看 B 站自己的前端发了什么 `fnval` / `qn` / `fourk`。**这是最权威的答案**——官方前端发什么，就说明什么值有效。
2. **二分法探测 `fnval`**。用播放账号分别请求 `fnval` = 16 / 16+2048 / 16+256 / 4048 / 4304，对比返回的 `dash` 结构：
   - `dash.video[]` 里出现 `codecid=12`（AV1）→ AV1 位生效
   - 出现 `dash.dolby.audio[]` → 杜比音频位生效
   - 出现 `dash.dolby.vision[]` → 杜比视界位生效
   - 出现 `dash.flac.audio` → Hi-Res 位生效
3. **看 `accept_quality` / `accept_description` 数组**。它直接告诉你"这个账号对这个视频能拿哪些清晰度"，是判断权限边界的最佳信号。

### 需要确认的具体项

1. Hi-Res 到底对应哪一位（我此前推测 `+256`，**未经核实**）
2. `dash.dolby.audio` 与 `dash.dolby.vision` 分别对应哪些位
3. `fnval=4048` 是否真的包含 Hi-Res（我推测不包含）
4. 是否有必要为不同场景发不同 `fnval`（全量请求 vs 保守请求）

**绝对不要照抄我给的数字。** 我给的 `4048` / `4304` 都是推算值，用官方前端抓包得到的值才是唯一可信来源。

### 连带影响
原计划中"致谢 bilibili-API-collect"这一项**建议删除**——它已关停，致谢它对你没有好处，反而会让你的项目在关键词上产生关联。

## 10. ✅ Q10：合规表述怎么写 — **已决策**

## 12. ✅ Q12：伪装会员标识到底做不做 — **已决策：v1 不做**

**删掉 Dual Account Helper 的那 7 个 PATCH_PATHS。** 一句为什么：收益只是让进度条颜色、"开通"标记顺眼一点；
代价是前端显示"大会员"而账号实际不是——**这种不一致是风控最容易捕捉的信号之一**，还会让用户误以为自己真开了会员。

⚠️ **2026-10-26 例外**：不改 vip 字段会导致**切高清时弹充值页**，所以授权了三个接口的**精确字段改写**
（`status` / `type` / `due_date`，禁改 `mid` / `rights`），见 [ADR 0013](./decisions/0013-patch-player-info-response.md)。
那是"让播放器别挡路"，不是"让用户以为自己有会员"。其余路径（如 `/pgc/view/web/season`）仍不做。

**v1 阶段连这个开关都不放**——将来若无用户需求就不引入风险；真要做必须是默认关闭的高级选项，且文案写明"仅改界面显示，不改变实际权益"。

## 13. ✅ Q13：项目命名、开源协议、仓库归属 — **已决策**

| 层 | 名称 | 一句为什么 |
| --- | --- | --- |
| **项目名** | **Pluma** | 西语"羽毛"，兼具笔尖意象；5 字母双音节，念一次就记住 |
| **仓库名** | **`bili-pluma`** | GitHub 已验证可用（`pluma`/`plume` 纯词均被占用） |
| **副标题** | **B站双账号画质助手**（后经 ADR 0032 / 0034 改为 B站助手 · 画质与净化） | 承担全部解释成本，名字不必自解释 |

**为什么不用 `La Pluma`**：那是鹰角网络的知识产权（商标风险），且搜 `La Pluma` 全是游戏内容，项目会彻底搜不到。
**为什么名字不自解释**：用户接触项目时很少只看到名字；名字唯一无法被替代的作用是**被记住、被复述**。`bili-*` 前缀在 GitHub 上极其拥挤，恰恰因为没有区分度。

**协议：GPL-3.0-only + GPLv3 第 7 条允许的额外条款。** 理由、与 MIT 的逐条对比、附加条款原文全部在 [ADR 0003](./decisions/0003-gplv3-with-additional-terms.md)，此处只留三条结论：

1. **许可证本身不构成防护**——同类项目已因平台政策变化停止维护；真正的风险控制在于**分发方式**（Q16）
2. **选 GPLv3 是为了防商业化**——最大滥用风险是"改名包装成付费软件卖会员权益"，强制衍生作品开源能堵住；MIT 允许闭源商用
3. **附加条款落在 [`ADDITIONAL-TERMS.md`](../ADDITIONAL-TERMS.md)**，不在本文重复

README 写法：**不在首屏宣传许可证**（会给用户"正经商业项目"的错觉，反而放大风险感知），放在最后一行带过。

**致谢只谢思路不谢代码**：Dual Account Helper（请求级身份代理机制思路，无 LICENSE，**绝不可复制代码**）、
bilipai（多账号配置与播放账号绑定的设计参考，GPLv3，**绝不可复制代码**）。末尾加一句"如有异议请联系删除致谢"。

## 16. ✅ Q16：分发渠道与停止维护预案 — **已落实（1.0.0 发布时执行，2026-10-29）**

为什么这条是 🔴：前面所有决策回答"怎么做"，这条回答"**做出来之后能不能存在**"。
同类项目已因平台政策变化停止维护（见 Q13），这不是低概率风险，而是**这个品类的必遇事件**。

| 渠道 | 决策 | 一句为什么 |
| --- | --- | --- |
| GitHub 源码仓库 | ✅ **正式渠道（主路径）** | 源码 + 构建说明 |
| Release 的 zip | ✅ **允许**（2026-10-27 起） | 但**必须同时提供带源码的版本**，见 [ADR 0018](./decisions/0018-ship-built-artifacts.md) |
| Chrome / Edge 商店 | ❌ **v1 不上架** | B站投诉后必下架；且审核对"改请求头"类扩展本就严格 |
| crx | ❌ **不发** | 商店签名之外的 crx 浏览器直接拒绝，发了只会制造"装不上" |

不发 crx、不上架商店看起来是"让用户更难用"，实际是在**降低暴露面**——差别不在代码，在**你提供了什么能力**。发 zip 让暴露面略增，这个代价已由用户权衡接受，但**不改变**下面「生命周期可能很短」的判断。

**诚实的结论**：这个项目的生命周期可能很短。当作**技术实践项目**（价值在学会 MV3 / DNR / 请求级代理 / 账号隔离），
不是长期运营的产品。**这不影响继续做，但影响你怎么投入。**

**2026-10-29 执行情况**：`v1.0.0` 已发布，附件 `pluma-1.0.0.zip` + `pluma-1.0.0-with-source.zip`（sha256 见 Release）；
仍不上架商店、不发 crx；archived 预案待命（决定停止维护 → 停止更新 → 仓库 archived 不删除 → README 换成说明）；GitHub issues 已禁用。

## 17. ✅ Q17：为直播间加 `host_permissions` 是否可接受 — **已决策：接受**

**问题**：隐藏直播页水印需要 `live.bilibili.com/<房间号>`，它**不匹配** `*://*.bilibili.com/*`。
**唯一代价**：装包时的权限提示从「bilibili.com」变成「bilibili.com 和 live.bilibili.com」——1.1.0 唯一改变用户可见权限的改动。

**结论：接受**。理由与边界见 [ADR 0031](./decisions/0031-page-level-visual-cleanup-boundary.md)：
换取的能力**仅限样式层**（隐藏水印），不换 Cookie、不发取流请求；`routes.ts` 里两条直播取流路径**仍 `enabled: false`**。
「支持直播页」≠「支持直播取流」。

**未采纳备选**：动态权限（`permissions.request()`）——本项目从未用过该机制，属新增机制且要用户点两次。若将来用户对权限提示反弹再考虑。

## 18. 🟡 Q18：直播水印若烧进视频流，CSS 方案是否失效 — **部分实测**

### 问题

「删除直播水印」的实现是 3 条 CSS 选择器（隐藏 DOM 元素），抄自 Bilibili-Evolved。
**若 B站 把水印烧进视频画面（canvas / 流内像素），CSS 必然无效**——此时功能静默失效，用户只会觉得"这开关没用"。

### 已实测（2026-10-31）

房间 5440（跳转至 `/1`，1920×1080，`readyState=4`）上：

| 选择器 | 是否存在 | 有我们的样式 | 移除样式后 | 结论 |
| --- | --- | --- | --- | --- |
| `.player-ctnr .web-player-icon-roomStatus` | ✅ | `display:none` | **`block`** | 是 DOM 元素，CSS 有效 |
| `.live-player-ctnr .web-player-icon-roomStatus` | ✅ | `display:none` | **`block`** | 同上 |
| `.bilibili-live-player-video-logo` | ❌ 本场景无 | — | — | **未验证** |

**这个对比是决定性的**：移除我们的 `<style>` 后元素立刻变回 `block`，
说明隐藏确实是我们造成的，不是 B站 本来就藏。

### 未验证（不许当成已验证）

1. **第 3 个选择器**（`.bilibili-live-player-video-logo`）在验证的房间不存在，
   需另找使用该结构的直播间（通常是自定义挂载图 / 电商勾选的房间）
2. **其它直播形态**（付费直播、赛事直播、竖屏）是否也是 DOM 水印
3. 目前**1 个房间、1 次会话**的样本，不足以代表全部

### 若将来实测发现水印已烧进画面

**不要试图用 CSS 硬解**。正确做法是：
把该功能**标注为不适用于该场景**并在诊断页显示"水印清理未生效"，
而不是加一堆猜测性选择器（那只会把"静默失效"变成"看起来在做但没做"）。

### 2026-10-25 实装阶段的三次翻案

> 这三条**当初都定过、后来都推翻了**。共同原因（**纸面威胁模型没在实装时复核**）比结论本身更值得记：

| 原决策 | 推翻原因 | 新决策 |
| --- | --- | --- |
| 不申请 `cookies` | 只分析了主账号，**漏了播放账号**：`SESSDATA` 是 httpOnly，`document.cookie` 读不到，`fetch` 也读不到 `Set-Cookie`。不申请就完不成登录 | **申请**，限定域名与用途（[ADR 0008](./decisions/0008-cookies-permission-for-playback-credential.md)） |
| 不支持无痕模式 | 基于"无痕里扩展不生效"的错误假设，**实测完全能跑**。且登录播放账号必然覆盖主账号登录态（Cookie 按域名唯一），隔离窗口是唯一解法 | **用 `incognito: "split"`**，在无痕分区登录（[ADR 0012](./decisions/0012-isolated-window-login.md)） |
| Q6 只做 `mode: local` | 口令模式防不住"本机程序"（能读扩展存储的人同样能读 cookie 库），自动锁定也只是清缓存、下次自动重新 import。**两者都只有安全外观、没有安全实质** | **单一模式**，`mode` 字段整个删掉（[ADR 0009](./decisions/0009-drop-passphrase-mode.md)） |

**共同教训**：决策阶段的威胁模型分析，必须在实装时用真实代码再验证一遍。纸面上的"不需要""不支持""够用了"，都可能在写代码时被推翻。
