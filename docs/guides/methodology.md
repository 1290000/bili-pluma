# 排查方法论：穷举法与"考虑周全"

> **这份文档回答两个问题**：
> 1. 症状出现后，**怎么最快找到根因**（穷举法）
> 2. 找到之后，**怎么保证没留下新坑**（考虑周全的七问）
>
> 硬规则「先实测，再动手」在 [AGENTS.md](../../AGENTS.md) §1.5；本文是它的操作细节。
> 工具怎么用看 [debugging.md](./debugging.md)；本文只讲**怎么想**。

---

## 1. 什么时候该用穷举法

**穷举法 = 把所有可能影响该现象的位置列全，逐个用真实数据判定，排除到最后剩下的就是根因。**

三个条件**同时满足**才用：

| 条件 | 判据 | 反例 |
| --- | --- | --- |
| 有**可观测的判据** | 能读出一个具体值（`audioFamily='FLAC'`），不是"感觉不对" | "角标看起来怪怪的" |
| 候选集**可枚举** | 影响这个值的代码路径有限，能 grep 全 | "网络偶尔慢" |
| 单次验证**成本低** | 跑一条命令、喂一组数据，秒级出结果 | 每次要真机抓包半小时 |

**三条里有一条不满足，就换方法**：

| 不满足 | 换什么 |
| --- | --- |
| 不可观测 | 先加日志把它变成可观测（`[角标输入]` 那行就是这么来的） |
| 不可枚举 | 缩小范围：先二分定位到模块，再穷举 |
| 验证太贵 | 换成"读能工作的实现"策略（规则见 AGENTS.md §1.5） |

> ⚠️ **穷举法不是"多试几次"**。它的价值在"候选集列全"这一步——
> 漏了一个候选，后面的实测再严谨也白费。

---

## 2. 怎么穷举：四步

### 第 1 步：建候选集（最容易偷懒的一步）

把**所有**能影响该观测点的位置写下来，一个都不许跳过。

```bash
# 例：Hi-Res 徽章闪烁，先列出所有能改它的地方
grep -rn "FLAC\|Hi-Res\|hiRes" src/ public/ | grep -v "^\s*\*"
```

输出要**逐条落到纸面**（写进回复或注释），不能只"心里过一遍"。
心里过的结果是：想起来的都验了，想不起来的永远想不起来。

### 第 2 步：逐个用真实数据判定

每个候选只有三种结论，**不许有"可能"**：

- ❌ **排除**（实测输出正常）
- ✅ **确认**（实测复现了症状）
- ❓ **无法判定** → 说明第 1 步的候选集粒度不对，拆细

**必须用真实数据。** 构造数据的坑：
"我构造一个 5 条音轨的数组，应该能复现" —— 构造时你已经把假设写进数据里了。

真实数据从哪来：扩展自己的诊断日志、`poc/probe/`、用户提供的日志。
**拿不到真实数据时，先去做一个能产出的工具**，别用构造数据往下走。

### 第 3 步：排除法收敛

被排除的候选要**写清"为什么被排除"**，否则下一轮会重复排查同一个地方。

### 第 4 步：改完跑全链路实测

单点验证通过不算完。要**从数据源一路走到最终输出**再验一次。

---

## 3. 真实案例：Hi-Res 闪烁（2026-10-26）

| 步 | 动作 | 结论 |
| --- | --- | --- |
| 1 | grep 所有影响 Hi-Res 的位置 | 两个源头：迟滞逻辑、`removeBadge` 的重置 |
| 2 | 实测 `audioFamily` 在 AAC 视频里的取值 | 稳定返回 `mp4a` → **排除数据源** |
| 3 | 实测 `buildBadge` 对各 family 的输出 | 正常 → **排除渲染层** |
| 4 | 用户给出 BV1jt421t7XH 的真实日志 | **推翻第 2 步**：该视频确实有 FLAC 且装载成功 |
| 5 | 实测时间戳 vs 3 秒窗口 | `flac(5.1s前)` > 3000ms → **定位 `SB_STALE_MS`** |

第 2 步错在哪：**样本选错了**。我拿一个 AAC 视频验证"数据源不会返回 FLAC"，
这只能证明"AAC 视频不返回 FLAC"，证明不了"FLAC 视频不会抖动"。
→ **候选集里每个候选，要用能触发它的场景去验，不是随便找个场景。**

第 5 步之后我以为修完了：把 `SB_STALE_MS` 从 3000 调到 15000。
用户说了一句「**这次你也考虑周全一点**」——然后才挖出真问题（见下一节）。

**另一个案例（候选集列全做得更好的）**：[ADR 0012](../decisions/0012-isolated-window-login.md)
「为什么 MV3 里没有第二条路」——把 5 条通道（`chrome.cookies` 建 store、CHIPS、
offscreen、SW 读 `Set-Cookie`、无痕分区）逐条实测列出，最后只剩一条可行。
它的结论句值得记住：**关键不是某个 API 缺失，而是 `Set-Cookie` 读不到**——
穷举的价值就在于它能逼出这种"真正的约束"。

## 4. 想清楚"改什么"（①–③）

找到根因只是及格。下面七条是"这次改动是否可靠"的检查表，按顺序问。
**①–③ 决定改哪里，④–⑦ 决定改完能不能收工。**

### ① 这是判据错了，还是参数调错了？

**信号：如果修复方案里出现"把 X 从 A 改成 B"，先停下来问一句"X 这个判据本身对不对"。**

Hi-Res 案例：`SB_STALE_MS` 3000 → 15000 是调参。但"多久没写入 = 轨是否在用"
这个**判据**本身是错的——缓冲填满后停止写入是正常状态。调多大都会在某个视频上失效。

**判据错的典型特征**：你需要为它解释"为什么是 15 而不是 12 或 20"，而答不上来。

### ② 该修在哪一层？

优先级：**数据层 > 展示层**。

展示层的补丁（迟滞、防抖、节流）会**掩盖**数据层的 bug，而且掩盖得不彻底——
Hi-Res 的迟滞原本就是为了压住抖动的数据，结果它自己变成了闪烁的原因之一。

**问法**：这个补丁是在描述事实，还是在掩盖事实？

### ③ 副作用面：还有谁依赖我改的东西？

改 `pickActive` 之后，`sbStats`（诊断日志）的"活跃轨数量"口径也必须跟着改，
否则日志说"音频 2/2 活跃"而角标说"只有 1 条"，排查时会互相误导。

```bash
# 改完一个函数，先查引用
grep -rn "函数名\|返回的字段名" src/ public/ entrypoints/
```

## 5. 想清楚"改完会不会翻车"（④–⑦）

### ④ 时序约束：是事件驱动还是定时轮询？

**这条最容易漏，而且只在真机上才暴露。**

主世界只在 **6s / 15s / 30s 和分辨率变化**时上报。所以：

- "连续 2 次确认" ≠ "2 秒后确认"，而是 **"第 15 秒才确认"**
- 30 秒后没有定时上报 → 中途丢一次，可能**再也不恢复**

**问法**：我依赖的"下一次"什么时候来？如果永远不来会怎样？

### ⑤ 反例验证怎么做

规则本身在 AGENTS.md §1.5（"把关键判断反向改回去，测试必须变红"）。**这里只写操作步骤**：

```bash
cp 改好的文件 /tmp/good.js
# 把关键判据改回旧实现
npx vitest run 相关测试      # 必须失败
cp /tmp/good.js 原路径       # 恢复
npx vitest run 相关测试      # 必须通过
```

Hi-Res 案例实测：换回旧逻辑后 **5 个用例失败**（含端到端），恢复后全过。

**为什么值得多花这 5 分钟**：不做这一步，你无法区分
"测试真的守住了行为"和"测试只是恰好通过"。

### ⑥ 规范一致性：逐条对照文档，别凭印象打勾

**"这个页面存在" ≠ "这个页面做完了"。**

判断阶段完成度必须**逐条对照规范章节**，不能看文件在不在。

本项目真实翻车两次，都出在这一步：

1. **漏看了核心区**：popup 的 5 种规范状态都做了，就被标成"界面完成"，
   而 `docs/02-ui-spec.md` §2.3「当前页解锁画质」——规范原文写着"整个 popup 唯一不能省的部分"——根本没做。
2. **规范本身是错的**：后来才发现代码里实际有 7 种状态，规范漏了 2 种（已停用 / 异常），
   而规范里那 1 种（非视频页）根本没实现。

**所以顺序是：先确认规范没落后于代码，再照规范打勾。** 两边都要核。

### ⑦ 改动安全性：大段代码怎么不误删

**不要用 `s.index(起点)` / `s.index(终点)` 做区间替换**，除非你能保证
两个 marker 之间只有你想删的东西。

真实事故：改 `main-world.js` 时用区间切片，起点和终点之间夹着
`sbDetail`、`trackSourceBuffer`、`noteCodec`、`reportHdrNow` 等**整段代码**，
一次性吞掉约 700 行。

安全做法（按优先级）：

1. 用精确字符串匹配（Edit 工具的 `old_string`），匹配不上就报错，不会误删
2. 必须用切片时，先断言 `end > start`，再打印中间内容的长度和首尾各 3 行，人工确认
3. 改完立刻做**函数清单比对**：

```bash
grep -o "function [A-Za-z_]*" 文件 | sort -u > /tmp/after.txt
# 和改动前的清单比，少了的必须能解释
comm -13 /tmp/after.txt /tmp/before.txt
```

**恢复源**：`public/` 下的静态资源在 `.output/chrome-mv3/` 有原样副本
（WXT 只拷贝不编译）。`git show HEAD:` 可能落后工作区很多，不一定是安全网。

## 6. 速查

**开始排查前**

- [ ] 有可观测的判据吗？没有就先加日志
- [ ] 候选集列全了吗？写下来，不是心里过
- [ ] 每个候选有能触发它的真实场景吗？
- [ ] 验证成本低吗？不低就换"读能工作的实现"

**宣布"修好了"之前**

- [ ] 是在修判据，还是在调参数？答不出"为什么是这个值"就是调参
- [ ] 修在数据层还是展示层？展示层补丁有没有掩盖真问题？
- [ ] 改的函数还有谁用？诊断日志的口径跟上了吗？
- [ ] 依赖的"下一次"什么时候来？永远不来会怎样？
- [ ] 把修复回滚，测试会变红吗？（没验证就是没写）
- [ ] 对照规范逐条核验了吗？不是"文件在就算完成"
- [ ] 大段替换有没有误删？函数清单比过了吗？
