# 排查方法论：穷举法与"考虑周全"

> **这份文档回答两个问题**：
> 1. 症状出现后，**怎么最快找到根因**（穷举法）
> 2. 找到之后，**怎么保证没留下新坑**（考虑周全的七问）
>
> 硬规则「先实测，再动手」在 [AGENTS.md](../../AGENTS.md) §1.5；本文是它的操作细节。
> 工具怎么用看 [debugging.md](./debugging.md)；本文只讲**怎么想**。

---

## 1. 什么时候该用穷举法

**穷举法 = 把所有可能影响该现象的位置列全，逐个用真实数据判定，排除到最后剩下的就是根因。**

三个条件**同时满足**才用：

| 条件 | 判据 | 反例 |
| --- | --- | --- |
| 有**可观测的判据** | 能读出一个具体值（`audioFamily='FLAC'`），不是"感觉不对" | "角标看起来怪怪的" |
| 候选集**可枚举** | 影响这个值的代码路径有限，能 grep 全 | "网络偶尔慢" |
| 单次验证**成本低** | 跑一条命令、喂一组数据，秒级出结果 | 每次要真机抓包半小时 |

**三条里有一条不满足，就换方法**：

| 不满足 | 换什么 |
| --- | --- |
| 不可观测 | 先加日志把它变成可观测（`[角标输入]` 那行就是这么来的） |
| 不可枚举 | 缩小范围：先二分定位到模块，再穷举 |
| 验证太贵 | 换成"读能工作的实现"策略（规则见 AGENTS.md §1.5） |

> ⚠️ **穷举法不是"多试几次"**。它的价值在"候选集列全"这一步——
> 漏了一个候选，后面的实测再严谨也白费。

---

## 2. 怎么穷举：四步

### 第 1 步：建候选集（最容易偷懒的一步）

把**所有**能影响该观测点的位置写下来，一个都不许跳过。

```bash
# 例：Hi-Res 徽章闪烁，先列出所有能改它的地方
grep -rn "FLAC\|Hi-Res\|hiRes" src/ public/ | grep -v "^\s*\*"
```

输出要**逐条落到纸面**（写进回复或注释），不能只"心里过一遍"。
心里过的结果是：想起来的都验了，想不起来的永远想不起来。

### 第 2 步：逐个用真实数据判定

每个候选只有三种结论，**不许有"可能"**：

- ❌ **排除**（实测输出正常）
- ✅ **确认**（实测复现了症状）
- ❓ **无法判定** → 说明第 1 步的候选集粒度不对，拆细

**必须用真实数据。** 构造数据的坑：
"我构造一个 5 条音轨的数组，应该能复现" —— 构造时你已经把假设写进数据里了。

真实数据从哪来：扩展自己的诊断日志、`poc/probe/`、用户提供的日志。
**拿不到真实数据时，先去做一个能产出的工具**，别用构造数据往下走。

### 第 3 步：排除法收敛

被排除的候选要**写清"为什么被排除"**，否则下一轮会重复排查同一个地方。

### 第 4 步：改完跑全链路实测

单点验证通过不算完。要**从数据源一路走到最终输出**再验一次。

---

## 3. 真实案例：Hi-Res 闪烁（2026-10-26）

| 步 | 动作 | 结论 |
| --- | --- | --- |
| 1 | grep 所有影响 Hi-Res 的位置 | 两个源头：迟滞逻辑、`removeBadge` 的重置 |
| 2 | 实测 `audioFamily` 在 AAC 视频里的取值 | 稳定返回 `mp4a` → **排除数据源** |
| 3 | 实测 `buildBadge` 对各 family 的输出 | 正常 → **排除渲染层** |
| 4 | 用户给出 BV1jt421t7XH 的真实日志 | **推翻第 2 步**：该视频确实有 FLAC 且装载成功 |
| 5 | 实测时间戳 vs 3 秒窗口 | `flac(5.1s前)` > 3000ms → **定位 `SB_STALE_MS`** |

第 2 步错在哪：**样本选错了**。我拿一个 AAC 视频验证"数据源不会返回 FLAC"，
这只能证明"AAC 视频不返回 FLAC"，证明不了"FLAC 视频不会抖动"。
→ **候选集里每个候选，要用能触发它的场景去验，不是随便找个场景。**

第 5 步之后我以为修完了：把 `SB_STALE_MS` 从 3000 调到 15000。
用户说了一句「**这次你也考虑周全一点**」——然后才挖出真问题（见下一节）。

**另一个案例（候选集列全做得更好的）**：[ADR 0012](../decisions/0012-isolated-window-login.md)
「为什么 MV3 里没有第二条路」——把 5 条通道（`chrome.cookies` 建 store、CHIPS、
offscreen、SW 读 `Set-Cookie`、无痕分区）逐条实测列出，最后只剩一条可行。
它的结论句值得记住：**关键不是某个 API 缺失，而是 `Set-Cookie` 读不到**——
穷举的价值就在于它能逼出这种"真正的约束"。

## 4. 想清楚"改什么"（①–③）

找到根因只是及格。下面七条是"这次改动是否可靠"的检查表，按顺序问。
**①–③ 决定改哪里，④–⑦ 决定改完能不能收工。**

### ① 这是判据错了，还是参数调错了？

**信号：如果修复方案里出现"把 X 从 A 改成 B"，先停下来问一句"X 这个判据本身对不对"。**

Hi-Res 案例：`SB_STALE_MS` 3000 → 15000 是调参。但"多久没写入 = 轨是否在用"
这个**判据**本身是错的——缓冲填满后停止写入是正常状态。调多大都会在某个视频上失效。

**判据错的典型特征**：你需要为它解释"为什么是 15 而不是 12 或 20"，而答不上来。

### ② 该修在哪一层？

优先级：**数据层 > 展示层**。

展示层的补丁（迟滞、防抖、节流）会**掩盖**数据层的 bug，而且掩盖得不彻底——
Hi-Res 的迟滞原本就是为了压住抖动的数据，结果它自己变成了闪烁的原因之一。

**问法**：这个补丁是在描述事实，还是在掩盖事实？

### ③ 副作用面：还有谁依赖我改的东西？

改 `pickActive` 之后，`sbStats`（诊断日志）的"活跃轨数量"口径也必须跟着改，
否则日志说"音频 2/2 活跃"而角标说"只有 1 条"，排查时会互相误导。

```bash
# 改完一个函数，先查引用
grep -rn "函数名\|返回的字段名" src/ public/ entrypoints/
```

## 5. 想清楚"改完会不会翻车"（④–⑦）

### ④ 时序约束：是事件驱动还是定时轮询？

**这条最容易漏，而且只在真机上才暴露。**

主世界只在 **6s / 15s / 30s 和分辨率变化**时上报。所以：

- "连续 2 次确认" ≠ "2 秒后确认"，而是 **"第 15 秒才确认"**
- 30 秒后没有定时上报 → 中途丢一次，可能**再也不恢复**

**问法**：我依赖的"下一次"什么时候来？如果永远不来会怎样？

### ⑤ 反例验证怎么做

规则本身在 AGENTS.md §1.5（"把关键判断反向改回去，测试必须变红"）。**这里只写操作步骤**：

```bash
cp 改好的文件 /tmp/good.js
# 把关键判据改回旧实现
npx vitest run 相关测试      # 必须失败
cp /tmp/good.js 原路径       # 恢复
npx vitest run 相关测试      # 必须通过
```

Hi-Res 案例实测：换回旧逻辑后 **5 个用例失败**（含端到端），恢复后全过。

**为什么值得多花这 5 分钟**：不做这一步，你无法区分
"测试真的守住了行为"和"测试只是恰好通过"。

#### ⚠️ 用脚本改代码验反例时，先断言命中次数（2026-11-10 实测踩过）

这一步最容易翻车的地方不是"忘了恢复"，而是**替换模式写宽了，同时改中了注释里的代码示例**：

```ts
// 文件里有两处：
//   :431  * const consistent = proxy.enabled;    ← 注释里的示例
//   :463  const consistent = proxy.enabled;      ← 真实代码

src.replace('const consistent = proxy.enabled;', '...旧判据...')   // ❌ 命中 2 处
```

改完测试红了，恢复时又只恢复一处 → **注释和代码对不上，而人以为是自己的改动有问题**。

**两条防护**（缺一不可）：

```js
// ① 改之前先数，命中数不是 1 就拒绝执行 —— 在改坏文件之前叫停
const hits = src.match(/^ *const consistent = /gm)?.length;
if (hits !== 1) throw new Error(`期望 1 处，实际 ${hits} 处，模式写宽了`);

// ② 用行首锚点排除注释：注释行以 ` *` 开头
src.replace(/^(\s*const consistent = )proxy\.enabled;/m, '$1...');
```

**别用裸 `String.replace` 改代码** —— 它不知道哪里是注释。

#### 🔴 往注释 / 字符串里插内容，先查有没有"容器的结束标记"（2026-11-11，一天踩三次）

上面讲的是"替换模式写宽了"。这一条是**更基础的一类**：**你插入的内容本身把容器提前闭合了。**

##### 真实经过（同一天，三次）

| # | 位置 | 插了什么 | 把什么提前闭合了 | 报错 |
| --- | --- | --- | --- | --- |
| 1 | `entrypoints/content.ts` 的块注释 | 一段新的 JSDoc | **`*/`** —— 原注释在插入点之前就结束了，新内容落在代码区 | `TS1109` / `TS1127`（一串 `Invalid character`） |
| 2 | `entrypoints/background.ts` 的探针注释 | 含 `*/` 的说明文字 | 同上 | 同上 |
| 3 | **`src/content/panel/sidebar.ts` 的 CSS** | 注释里用**反引号**包类名（`` `.acct-row` ``） | **模板字符串的结束反引号** | `TS1005` / `TS1351`（`Identifier cannot immediately follow a numeric literal`） |

##### 共同点

> **往"会被解析的容器"里写"容器的结束标记"。**

容器与它的结束标记：

| 容器 | 结束标记 | 不能在里面裸写 |
| --- | --- | --- |
| `/* … */` 块注释 | `*/` | `*/` |
| 模板字符串 `` `…` `` | `` ` `` | 反引号（**以及 `${`**，会开启插值） |
| 单/双引号字符串 | 同种引号 | 未转义的同种引号 |
| `//` 行注释 | 换行 | ——（但 `\` 续行会延长它） |
| JSX 文本 | `{` / `}` | 未转义的 `{` `}` |

##### 判据

> **往注释 / 模板字符串 / 字符串里插入内容前，先对插入内容做一次"结束标记"检查。**

```bash
# 查你准备插入的文本里有没有容器的结束标记
# 块注释：grep -n '\*/'   → 有就不能直接插
# 模板字符串：grep -n '`'  → 有就必须换成单引号或用 \` 转义
```

**最实用的做法：不要在 CSS 模板字符串里写带反引号的注释。**
`sidebar.ts` 的 `PANEL_CSS` 就是这种情况 —— 注释里写类名时**用单引号或直接写名字**，
不要用反引号包（那在 Markdown 里是习惯，在模板字符串里是地雷）。

##### 为什么这类错误特别耗时间

它**不在你编辑的那一行报错**，而是在**容器结束之后的某一行**报一串莫名其妙的话：

```
TS1351: An identifier or keyword cannot immediately follow a numeric literal
```

看到这种错，**先往上看有没有被提前闭合的容器**，不要从报错行开始找。

#### ⚠️ 反向验证可能"根本没改成"—— 先证明改动落盘，再看测试（2026-11-11）

上面 §5⑤ 讲的是"改错了地方"。还有更隐蔽的一种：**你以为改了，其实文件没变**。

真实案例：用 PowerShell `-replace` + `Set-Content` 把一条判据改坏，跑测试 **全绿**。
差一点得出"我的测试抓不住这个判据"——**那会让一条真实的测试保护被误判为无效，然后被删掉或放宽。**

真相是替换**根本没落盘**，测试跑的是原文件。

| 失败的样子 | 性质 | 危险度 |
| --- | --- | --- |
| 替换命中注释示例 → 测试变红 | 假阳性 | 低：你会去查 |
| **替换没落盘 → 测试全绿** | **假阴性** | **高：你会得出"测试无效"的结论** |

**做法**：改完立刻**回读文件确认**，再跑测试。

```bash
# 落盘后复验：确认那一行真的变了
Select-String -Path 文件 -Pattern "旧判据"   # 必须 0 命中
Select-String -Path 文件 -Pattern "新判据"   # 必须 1 命中
```

**优先用 Node / 编辑工具改，不用 PowerShell 的 `-replace` + `Set-Content`** ——
它在编码、管道、原地写入上都有静默失败的面。

#### 🔴 恢复只能用"自己做的备份" —— `git checkout -- <file>` 会清掉别人的改动（2026-11-11 事故）

上面讲的是"改动没落盘"。这一条讲**改动落了盘，但恢复时把别人的改动一起清掉了**。

##### 真实经过

做反向验证时用 `git checkout -- src/shared/types/errors.ts` 恢复文件。
测试确实恢复正常了 —— **但那个文件里还有 `engineer-a` 尚未提交的术语改动（`播放账号` → `取流账号`）**，
也一起回到了 HEAD 的旧文案。

发现后手工逐字改回并 `git diff` 核对一致。**这次影响可控（只一个文件），但机制是危险的。**

##### 为什么 `git checkout` 不能当"撤销"

```
git checkout -- <file>   =  把文件恢复到 HEAD（上次提交）
你自己动手前的状态        =  工作区当时的内容（含别人的未提交改动）
```

**这两者不是一回事。** 共享工作区里，别人可能正在同一个文件里改东西。

> **判据：「回到上次保存的状态」≠「回到你动手前的状态」。**

##### 三条规则

1. **反向验证的恢复只能用自己做的备份。**
   ```bash
   # 动手前：把当前工作区状态存下来（不是 git 的，是你自己的）
   git diff -- <file> > /tmp/my-backup.patch    # 或直接复制文件
   # 或者更简单：只改副本，不改原文件
   ```
2. **`git checkout -- <file>` / `git stash` / `git reset --hard` 在共享工作区一律禁止。**
   前两个的破坏性早就写在 `docs/guides/team-workflow.md` §5.1，
   `checkout -- <file>` 是同一类东西的**更隐蔽变体**（看起来只动一个文件，其实动的是"所有未提交改动"）。
3. **首选"根本不碰真实文件"的做法**：把被测代码复制到独立副本 / 建临时探针文件，在副本上做反向验证。
   **不碰真实文件就永远不需要恢复** —— 这是本事故后采用的做法，也应该是默认做法。

##### 同类事故清单（都是"用 git 操作替代备份"）

| # | 事故 | 后果 |
| --- | --- | --- |
| 1 | `git stash`（带不带 pathspec 都一样） | 20 个文件凭空消失，两个成员同时看到"工作没了" |
| 2 | `checkout -- <file>` | 连别人的未提交改动一起回到 HEAD |

**共同点**：它们都在**替你做决定**"哪些改动该留"。而共享工作区里，那个决定权不属于你。

#### ⚠️ "删除"同样需要测试保护 —— 否则删除是静默的（2026-11-11）

上面讲的都是"行为改错了要变红"。但有一类改动**测试完全看不见**：**把一个分支删掉**。

真实案例：过渡期一个旧的 reason 值 `'same-account'` 改名成 `'self'`，
为了让两边都不阻塞，中间层同时接住了两个值。清理时把旧值删掉 ——
**所有测试都是绿的**，因为没有任何断言关心"这个值是否还在"。

于是**删除变成了静默的**：明天有人照着旧记忆写了 `reason: 'same-account'`，
类型层如果恰好也没覆盖到，它会安然通过，然后在运行时走进一个不存在的分支。

**做法**：给"已删除"这件事本身写一条断言，用 `@ts-expect-error` 钉住。

```ts
it('旧名已不在类型域里（加回来会红）', () => {
  const s = makeState();
  // @ts-expect-error —— 'same-account' 已从联合里移除，不再是合法输入
  s.setProxyIdentity('same-account');
  // 运行时若被强塞进来，也不许产出对应的结论
  expect(s.view()?.primary.reason).not.toBe('same-identity');
});
```

**为什么 `@ts-expect-error` 比"只要不报错就行"强**：TS 对**未被使用**的
`@ts-expect-error` 本身报错。所以
- 旧值还在 → 这行不再有类型错误 → `@ts-expect-error` 变成"未使用" → **编译失败**
- 旧值删了 → 类型错误出现 → 被 expect-error 消费 → 通过

一条断言把"删干净了"和"没删干净"都钉住了。

**推广**：任何**移除**公开取值 / 分支 / 导出的改动，都配一条 `@ts-expect-error`
或等价的"此物不存在"断言。**只删不测 = 静默删除。**

#### ⚠️ 数"有几处"必须机械扫描，人给的清单只能当起点（2026-11-11，同一轮三次踩）

一个"把术语 A 改成 B"的替换任务，**三个人三种漏法**，全部出在"候选集没列全"上：

| 角色 | 漏法 | 具体 |
| --- | --- | --- |
| Lead 出清单 | **凭印象** | 任务卡写"涉及 4 个文件"，实际 6 个（漏 `badge-content`×3、`summary-view`、`collect`×2） |
| 验证者 | **输出被截断** | `Select-Object -First 20` 把结果切在第 20 行，第 21 处就看不见——与 handoff 记的"21 处实为 26 处"**完全同一个坑** |
| 实现者补扫 | **机械扫描**（正确） | 非注释行逐行扫出**另外 7 处**，含 `proxy.handler.ts:125` 错误消息、`content-panel.content.ts:188` 面板提示条 |

**规则**：

```bash
# ① 先取总数，再决定怎么展示 —— 不要用 head / First 限制输出后再数
grep -rn "播放账号" src/ entrypoints/ | wc -l        # 总数
grep -rn "播放账号" src/ entrypoints/ | grep -v "^\S*:\s*\*"   # 排除注释后再数

# ② 排除注释后再确认一遍：注释里的旧名是历史表述，不该改但也不该被当成漏改
```

**判据**：一个"枚举 + 替换"任务，**必须先用命令取总数**，
不能凭记忆列清单，也不能看截断过的输出下结论。**人能想起来的都是他注意到过的。**

#### ⚠️ 变异测试的恢复校验，在并行改动环境下必须"定向"（2026-11-11）

做反向验证（把判据改坏 → 测试变红 → 恢复）时，"恢复成功"的校验手段有三个坑：

| 手段 | 陷阱 |
| --- | --- |
| `git diff` 为空 | **对未跟踪的新文件永远为空**——"diff 空"证明不了恢复对了 |
| 全仓 `git diff` 的 SHA256 | 并行协作时**别人一改就变**，你会误以为自己恢复失败 |
| `git stash` 备份 | **共享工作区绝对禁止**（本项目出过两次事故） |

**正确做法**：
1. 恢复校验只针对**自己碰过的文件**：`git hash-object <file>` 与备份比对
2. **在报告里显式列出"我碰过哪些文件"**，让别人能核对
3. 对未跟踪的新文件，用**行为证据**代替哈希：相关测试数、`tsc` 结果、关键判据 `grep`
4. **脚本写回文件后必须跑 `prettier --write`** —— 用脚本恢复会破坏格式，
   `format` 项会红，而那看起来像是"格式化出了问题"，实际是恢复脚本的锅

#### 🔴 用正反样本约束一个判据，**三个维度缺一不可**（2026-11-11，逻辑证明 + 实测）

上面所有"反向验证"都是同一个结构：**给判据喂正样本（该命中）和负样本（不该命中），两边都必须对。**

2026-11-11 给 `check-messages.mjs` 的内联联合正则写形态穷举测试时，发现**这个二元框架自身有一个后门**。

##### 后门在哪

设 `X` = 所有可能输入，`P` = 被约束的谓词（这里是那个正则）。

| 约束 | 含义 |
| --- | --- |
| ① 该报的要报 | `P(a)` 对所有 `a ∈ A` 成立（`A` = 正样本集） |
| ② 不该报的不报 | `¬P(b)` 对所有 `b ∈ B` 成立（`B` = 负样本集） |

**只要 `A` 和 `B` 都非空，①②就可以同时被满足 —— 无论"约束的适用范围"有多大。**

也就是说：**如果你很宽松地定义"什么情况下该报"，那么正负样本可以全部通过，而实际保护范围已经缩到零。**

##### 实测：四种退化方向，其中一种穿透了二元约束

把正则换成各种退化形态，跑同一组断言（7 正 / 6 负）：

| 变异体 | 正样本通过 | 负样本通过 | 被拦住？ |
| --- | --- | --- | --- |
| 【原始】正常正则 | 7/7 | 6/6 | （预期全过） |
| 【变异1】`/(.*)/` 什么都报 | 7/7 | **0/6** | ✅ 被 ② 拦住 |
| 【变异2】`/zzz-never-match/` 什么都不报 | **0/7** | 6/6 | ✅ 被 ① 拦住 |
| 【变异3】去掉前置竖线 `\|?` | **6/7** | 6/6 | ✅ 被 ① 拦住 |
| **【变异4】去掉字段白名单（任何字段都查）** | 7/7 | 6/6 | ❌ **漏网** |

**变异4 就是那个后门**：把"哪些字段算封闭枚举"从 4 个字面量放宽成 `\w+`（任何字段）之后，
**15 个形态样本恰好全部仍然正确** —— 但误报范围从 4 个字段炸到全部字段。

##### 第三维：**约束的定义域不许被放宽**

必须额外断言"**约束的适用范围本身没变**"，而这条：

> **通常是"结构检查"而非"行为检查"** ——
> 你没法用又一个正反样本证明"我的样本集没被缩小"，
> 只能直接检查**样本集的来源**（例如：白名单必须是字面量数组、不许出现通配符）。

实测的那条断言：

```ts
it('★ 字段白名单必须是封闭枚举，不许放宽成"任何字段"', () => {
  const decl = /const SEALED_ENUM_FIELDS = \[([^\]]*)\]/.exec(src);
  // ① 白名单必须是带引号的字面量
  for (const f of FIELDS) expect(decl?.[1]).toContain(`'${f}'`);
  // ② 不许出现通配写法
  for (const bad of ['\\w+', '[a-zA-Z]+', '(\\w*)']) expect(decl?.[1]).not.toContain(bad);
});
```

变异4 加回去 → **精确报出"白名单被放宽成通配"**。

##### 判据

> **任何"黑名单 / 白名单"式的判据，都要多问一句：这张名单本身能不能被悄悄放宽？**
>
> 能放宽的，就必须再加一条**结构断言**把名单钉住。

适用范围（不只是检查脚本）：

| 场景 | ① / ②（正负样本） | ③（定义域） |
| --- | --- | --- |
| `check-messages` 内联联合 | 形态穷举 | 字段白名单不许通配 |
| `check-patch-scope` 授权常量 | 四类改写各自的正反样本 | 授权常量清单不许加新项 |
| `check-page-gate` 入口登记 | 每个入口的 matches 正反样本 | 登记的入口清单不许扩 |
| **反向验证本身** | 改前红 / 改后绿 | **"改的到底是哪一行"不许漂到别处** |

**注意最后一行**：反向验证自己也需要第 ③ 维（"变异落点"），这正是上面那三节
（"先断言命中次数" / "改动没落盘" / "恢复清掉别人的改动"）在讲的事。

##### 推广到"报告"层面

> **"本文件有保护"和"本文件对所有退化方向都有保护"是两件事。**
> 不写清楚，下一个人会以为改什么都安全。

本轮的几乎所有严重问题，根子都是"**看起来有保护**"：

| 看起来有保护 | 实际 |
| --- | --- |
| `same-account` 有 `reason` 值 | 零 UI 消费方，用户一个字都看不到 |
| `rewriteGate` 有门控 | 放错层面（消费端而非生产端），否掉 ADR 0020 |
| `check-messages` 有内联联合检查 | 漏掉 Prettier 多行形态（最常出现的形态） |
| 双向约束有正负样本 | 仍有一个维度（定义域）漏网 |

**写"我加了保护"时，同时写清"它不覆盖什么"。** 后者才是可核查的部分。

#### 🔴 行为测试若**自己构造参数**，就测不到"调用方有没有传参数"（2026-11-11）

反例验证（改坏 → 变红 → 恢复）有一个**沉默的失效**：**你改坏的地方，测试根本没在看。**

##### 真实经过

`page` 模式下面板画质区显示「已接管」，而 `page` 模式下**什么都没换 Cookie** ——
那是"界面陈述错误事实"。查下来，**判据本身是对的**：

```ts
// popup-state.ts，一直是对的
if (snap.streamingIdentity === 'page') return pageIdentity();   // 「无需代理」
```

它**永远不触发**，因为链路断在两处调用点：

```
describePopup()            ← 判据正确
  ↑ snapshot.streamingIdentity  恒为 undefined
buildPopupSnapshot()       ← ✅ 接受这个字段
  ↑
loadPanelModel()           ← ❌ 调用时**没传**
  ↑
content-panel.content.ts   ← ❌ 调用 loadPanelModel 时**没传**
```

**"函数接受参数但调用方没传"** —— 比判据写错难发现得多，
因为**读被调用的函数时会以为已经修好了**。

##### 为什么行为测试抓不到它

我写了 10 条行为断言，跑得挺好。然后做反向验证：**删掉 `loadPanelModel` 里那一行透传。**

```
10 条里只有 1 条红。
```

原因：

```ts
// 测试自己构造参数 —— 复刻了调用方的传参
buildPopupSnapshot({ proxy, account, buckets, pageKind, streamingIdentity });
//                                                            ↑ 测试自己传的
```

**行为测试只要自己传对了参数，就永远测不到"调用方忘了传"。**
它测的是"这个函数收到参数后行为对不对"，而 bug 在"参数根本没送到"。

##### 判据

> **行为测试若自己构造参数，就测不到"调用方有没有传参数"。**
> 对"函数接受参数但调用方没传"这类**断链**，必须有**源码级断言**。

具体做法：**断言链路的每一个节点同时存在**，缺任一环就红。

```ts
const chain = {
  签名接受:      /loadPanelModel\(input: \{[\s\S]*?streamingIdentity/.test(panelData),
  透传给下游:    /buildPopupSnapshot\(\{[\s\S]*?streamingIdentity/.test(panelData),
  入口传进来:    /loadPanelModel\(\{[\s\S]*?streamingIdentity/.test(contentEntry),
};
expect(chain).toEqual({ 签名接受: true, 透传给下游: true, 入口传进来: true });
```

**为什么写成一个合并断言而不是三条**：
分开写会让人以为"我只改了这一处，另外两处没动所以没问题" ——
而 bug 的形态正是"**每一处单独看都没改坏**"。

##### 实测数据（补了源码级断言之后）

| 改坏哪里 | 变红的条数 |
| --- | --- |
| 删 `panel-data` 的透传 | **2 red**（含「三处节点必须同时存在」） |
| 删 `content` 入口的传参 | **1 red** |
| 只有行为测试（补之前） | **1 red / 10 条** ← 等于没测 |

##### 什么时候必须用它

| 场景 | 需要源码级断言吗 |
| --- | --- |
| 参数经**多层转手**（A → B → C），任意一层可能没传 | ✅ 必须 |
| 同一个参数在**多个入口**各传一次 | ✅ 必须（漏一个入口 = 一条路径坏） |
| 函数**只有一个调用点**且就在附近 | ❌ 行为测试够用 |
| 被调函数**不可单测**（依赖真实消息 / `chrome.*`） | ✅ 只能靠它 |

##### ⚠️ 它测不到什么（别把它当万灵药）

源码级断言只看**文本形态**，不理解语义。下列都会漏：

| 形态 | 例子 |
| --- | --- |
| 变量中转 | `const id = cache ?? null; loadPanelModel({ streamingIdentity: id })` ← 正则看不到 `id` 的来源 |
| 解构重命名 | `const { streamingIdentity: si } = input;` |
| 条件展开 | `...(cond ? { streamingIdentity } : {})` ← 正则能看到字段名，但看不到 `cond` 是什么 |
| 顺序无关的误传 | 传了**另一个**变量给同一个字段名 |

所以：**源码级断言是"补行为测试的洞"，不是"替代行为测试"。** 两者都要。

#### 🔴 `verify` 绿 ≠ 工作完成（2026-11-11 连续两次踩）

**`verify` 全绿只证明"没有坏代码"，不证明"活干完了"。**

##### 真实经过

一个成员中途崩溃，接手的人查工作区：
- `verify` **21/21 全绿**
- `git status` 干净

于是判断"**没留下半成品**"。**错。**

查 `git diff` 才发现：那个成员**把实现（+110 行）和文档（一整节分支表）都写完了**，只是**测试还没写**。

**`verify` 看起来全绿，是因为"没有测试"本身不报错** —— 少写测试不会让任何检查项变红。

##### 为什么这是系统性盲区

| 你想知道 | `verify` 能回答吗 |
| --- | --- |
| 有没有坏代码（编译、lint、既有测试） | ✅ 能 |
| **新增功能有没有测试** | ❌ **不能**（没有测试 = 没有失败） |
| **任务卡里的验收判据是否全部满足** | ❌ 不能（那是人写的，不是机器检查的） |
| 代码写完没写完 | ❌ **不能** |

**"没有失败"和"没有遗漏"是两件事。** 前者是 `verify` 的职责，后者不是。

##### 判据

> **判断一个任务"完成度"，不能只看 `verify`。**
> 必须**逐条对照任务卡的验收判据**打勾 —— 那一项是"新增单测"，`verify` 永远不会告诉你它缺。

**接手别人未完成的工作时，先做的不是"跑 verify"，而是三件事**：

1. `git diff --stat` —— 看**改了多少**（110 行说明干过大活，不是没动）
2. 读一遍改动 —— 看**它做到哪一步**（实现？文档？测试？）
3. 对任务卡的验收判据逐条核对 —— 找**缺哪几条**

**"干净的工作区"也可能是一个「实现完了、测试没写」的半成品。**

#### 🔴 错误代价不对称时，默认值选"错得轻"的那一侧（2026-11-11）

**当信息缺失、必须给一个默认值时，先问：两个方向都错，哪个**错得更轻**？**

##### 实例：`proxyIdentity` 缺失时说什么

界面要显示"为什么没有对比基线"。`primary.reason === 'same-identity'` 有两种成因，
靠 `PageTracksView.proxyIdentity` 区分。**但这个字段可能缺失**（老快照 / 回包还没到）。

两个候选默认值：

| 默认值 | 猜对时 | **猜错时** |
| --- | --- | --- |
| 「取流身份与页面身份相同」（事实陈述） | 正确 | 在 `page-identity` 下**不够精确**（没说清是用户选的） |
| 「当前用浏览器登录账号取流」（选择陈述） | 正确 | 在 `self` 下是**假话**（用户可能根本没选过） |

**两个方向都错，但错的性质不同**：

- 第一个错 = **不精确**（说了正确的事，只是没说全）
- 第二个错 = **假话**（把"碰巧相同"这个事实说成了"你的选择"）

> **判据：选那个「错得轻」的 —— 第一个。**
> 「身份相同」在 `self` 情形下**永远正确**，只是没说清成因；
> 而把 `self` 说成"你选的浏览器账号"是**事实错误**，会让用户困惑（他没选过）。

##### 判据的通用形式

给默认值时，画一张两行表：

| | 猜对 | 猜错 |
| --- | --- | --- |
| 候选 A | ? | ? |
| 候选 B | ? | ? |

**如果两侧"猜对"的收益相当，就看"猜错"的代价 —— 选代价小的那个。**

##### 同类应用（本项目已有）

| 场景 | 选了什么 | 为什么是"错得轻"的方向 |
| --- | --- | --- |
| `router.ts` 非法 URL | `routeFor()` 返回 `'primary'` | 少代理 = 画质没提升；错代理 = **点赞点到别人的号** |
| `ProxyActivateReason` 未知值 | fail-closed →「未知」 | 说"未知" = 用户多看一眼；说"已接管" = **谎报扩展在工作** |
| `normalizeStreamingIdentity` 非法值 | 收敛成 `'extension'`（默认值） | 回落默认 = 配置回到升级前的状态；抛错 = 功能起不来 |
| `lastActivateReason` 缺省 | 保持既有判据 | 改口 = 拿未知冒充结论 |

**共同点：都是"宁可少说/少做，也不要说错/做错"。**

##### ⚠️ 反向陷阱：不是所有场合都该保守

**"选错得轻的方向"只适用于「信息缺失」**。信息**已经拿到**时，该说清就说清 ——
否则会变成另一种错：**该说的没说**（用户以为没这功能）。

见本文件 `🔴 行为测试若自己构造参数` 那条里"未知态也渲染"的反例：
**控件消失不是安全默认值，而是隐形 bug。** 不猜**内容** ≠ 删掉**入口**。

### ⑥ 规范一致性：逐条对照文档，别凭印象打勾

**"这个页面存在" ≠ "这个页面做完了"。**

判断阶段完成度必须**逐条对照规范章节**，不能看文件在不在。

本项目真实翻车两次，都出在这一步：

1. **漏看了核心区**：popup 的 5 种规范状态都做了，就被标成"界面完成"，
   而 `docs/02-ui-spec.md` §2.3「当前页解锁画质」——规范原文写着"整个 popup 唯一不能省的部分"——根本没做。
2. **规范本身是错的**：后来才发现代码里实际有 7 种状态，规范漏了 2 种（已停用 / 异常），
   而规范里那 1 种（非视频页）根本没实现。

**所以顺序是：先确认规范没落后于代码，再照规范打勾。** 两边都要核。

### ⑦ 改动安全性：大段代码怎么不误删

**不要用 `s.index(起点)` / `s.index(终点)` 做区间替换**，除非你能保证
两个 marker 之间只有你想删的东西。

真实事故：改 `main-world.js` 时用区间切片，起点和终点之间夹着
`sbDetail`、`trackSourceBuffer`、`noteCodec`、`reportHdrNow` 等**整段代码**，
一次性吞掉约 700 行。

安全做法（按优先级）：

1. 用精确字符串匹配（Edit 工具的 `old_string`），匹配不上就报错，不会误删
2. 必须用切片时，先断言 `end > start`，再打印中间内容的长度和首尾各 3 行，人工确认
3. 改完立刻做**函数清单比对**：

```bash
grep -o "function [A-Za-z_]*" 文件 | sort -u > /tmp/after.txt
# 和改动前的清单比，少了的必须能解释
comm -13 /tmp/after.txt /tmp/before.txt
```

**恢复源**：`public/` 下的静态资源在 `.output/chrome-mv3/` 有原样副本
（WXT 只拷贝不编译）。`git show HEAD:` 可能落后工作区很多，不一定是安全网。

## 6. 速查

**开始排查前**

- [ ] 有可观测的判据吗？没有就先加日志
- [ ] 候选集列全了吗？写下来，不是心里过
- [ ] 每个候选有能触发它的真实场景吗？
- [ ] 验证成本低吗？不低就换"读能工作的实现"

**宣布"修好了"之前**

- [ ] 是在修判据，还是在调参数？答不出"为什么是这个值"就是调参
- [ ] 修在数据层还是展示层？展示层补丁有没有掩盖真问题？
- [ ] 改的函数还有谁用？诊断日志的口径跟上了吗？
- [ ] 依赖的"下一次"什么时候来？永远不来会怎样？
- [ ] 把修复回滚，测试会变红吗？（没验证就是没写）
- [ ] 对照规范逐条核验了吗？不是"文件在就算完成"
- [ ] 大段替换有没有误删？函数清单比过了吗？
