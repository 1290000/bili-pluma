# Release 说明模板

> Release 页是**唯一会被陌生人在 GitHub 上直接读到**的地方，也最容易被截图传播，
> 因此措辞比 README 更需要克制。
>
> 由 `scripts/package.mjs` 生成后落在 `dist/release-notes.md`，
> 发布时用 `gh release create --notes-file dist/release-notes.md`。
>
> 分发边界见 [ADR 0018](../decisions/0018-ship-built-artifacts.md)。

---

## 内容来源：两半拼起来

| 部分 | 来源 | 随版本变？ |
| --- | --- | --- |
| **本版内容** | **`CHANGELOG.md` 对应版本节** | ✅ 会变 |
| 下载 / 怎么用 / 边界 / 已知限制 / 许可证 | `package.mjs` 的 `releaseNotes()` | ❌ 基本不变 |

**判据：会不会随版本变？** 会变的写 `CHANGELOG.md`，不变的写在模板里。

### 为什么这么分（2026-10-27）

原来整段都是硬编码模板，只有版本号会变 —— 于是 1.0.0 的 Release
正文和 0.9.0 除了版本号一模一样，**看不到"这一版改了什么"**。

现在 `extractChangelogSection()` 从 CHANGELOG 提取 `## <版本号>` 这一节，
填进「本版内容」。**找不到该小节时打包直接失败**，不会发出空正文的 Release。

所以新增版本时：**先写 CHANGELOG，再打包**。

---

## 写作原则

| 要 | 不要 |
| --- | --- |
| 中性动词：下载 / 加载 / 构建 | 「一键安装」「开箱即用」「发布上线」 |
| 主动写「也可以自己从源码构建」 | 只给 zip，让编译变成隐藏选项 |
| 主动列「已知限制」 | 隐去不支持的东西 |
| 「修复过的 bug」用中性描述 | 「破解」「解锁会员」「绕过限制」 |
| 短 | 长（读的人不关心细节，关心的不读细节） |

**最忌讳的两个词**：`破解` / `解锁会员`。它们会直接影响对方如何定性这件事。

---

## 怎么写 `CHANGELOG.md` 里的「本版内容」

Release 正文的第一节由 `CHANGELOG.md` 提取，所以**怎么写 CHANGELOG 就是怎么写 Release**。

### 版本节标题（硬性）

```markdown
## 1.0.0
```

| 规则 | 原因 |
| --- | --- |
| **`## ` + 纯版本号**，与 `package.json` 的 version 逐字一致 | `extractChangelogSection()` 按字符串精确匹配 |
| **不带 `v` 前缀** | `v1.0.0` 是 git tag 的写法；文件名、CHANGELOG 都不用（见 `releasing.md`） |
| **不带日期** | 日期在 tag 里已有，两处写必然漂移 |
| **版本节用 `##`，子节用 `###`** | 提取时子节会自动降为 `####` |

**不匹配的后果是打包硬失败**（退出码 2）—— 这是故意的，宁可发不出去也不要发出空正文的 Release。

### 子节：按版本性质选一套

| 场景 | 用哪套子节 | 理由 |
| --- | --- | --- |
| **首个公开版本** | `### 双账号分离` / `### 界面` 这类**能力分类** | 没有上一版可比，写「新增」无从谈起 |
| **之后的版本** | `### 新增` / `### 修复` | 读者想看"这版变了什么" |

后续版本按需可再加两个（**不要凑数**）：

| 子节 | 什么时候用 |
| --- | --- |
| `### 变更` | 行为改了但既不算新增也不算修复（如"角标默认位置从左上改右上"） |
| `### 移除` | 删掉了原本支持的东西 —— **必须写**，否则用户会当成 bug 来报 |

### 条目写法

```markdown
- 支持番剧取流（原计划 v1.5，提前完成）
- 修复 4K 视频在某些分区不出现在画质菜单
```

| 要 | 不要 |
| --- | --- |
| **动词开头**（支持 / 修复 / 调整 / 移除） | 「番剧支持」—— 看不出是新功能还是修复 |
| **一行一条** | 一条里塞多个改动 |
| **不写内部实现** | ❌「重构了 DNR 规则管理」→ ✅「修复关闭总开关后个别标签页画质不回落」 |
| **不写"优化了体验"** | 无法验证等于没说，要具体到"画质菜单出现更快" |

### 需要用户操作时，单列

变化影响用户操作时**必须说清**，用引用块放在子节之后（视觉上更醒目）：

```markdown
> ⚠️ 首次使用需重新扫码 —— 凭据格式有变，旧版无法迁移。
```

三类常见情形：**需要用户操作** / **只影响特定场景** / **不兼容**。
如果什么都不用做，可以省略。

### 什么时候写

**功能完成时就写，不要等发布时回忆。** 发布时间想起"这版改了什么"必然遗漏。

做法：`CHANGELOG.md` 顶部常备一节

```markdown
## 未发布

### 新增

- （边做边记）

## 0.9.0
...
```

发布时把「未发布」改成版本号。`extractChangelogSection` 只认精确版本号，
所以「未发布」不会被误提取。

## 结构

```markdown
## Pluma <版本>

B站双账号画质助手。用主账号浏览、点赞、收藏，让一个大会员账号专门负责取流。

### 本版内容

<!-- 由 package.mjs 从 CHANGELOG.md 的 `## <版本>` 一节自动填入。
     不要在这里手写 —— 手写会和 CHANGELOG 漂移。 -->

### 下载

| 文件 | 内容 |
| --- | --- |
| `pluma-<版本>.zip` | 构建产物，解压后在 `edge://extensions`（Chrome 用 `chrome://extensions`）加载 |
| `pluma-<版本>-with-source.zip` | 同上 + 完整源码 |

也可以自己从源码构建：`pnpm install && pnpm build`，加载 `.output/chrome-mv3`。

这份产物由本项目开发者构建，未经过浏览器扩展商店签名，仅供学习交流使用。

### 怎么用

1. 加载扩展后点工具栏图标
2. 点「扫码登录播放账号」，用大会员账号扫码（独立窗口，不影响当前登录）
3. 打开任意 B站视频，画质菜单里会出现 4K / 1080P60

**加载后还要开一个权限**，否则扫码窗口打不开：
`edge://extensions`（Chrome 用 `chrome://extensions`）→ Pluma →「详细信息」
→ 打开「在 InPrivate 中允许」
（Chrome 叫「在无痕模式下启用」）→ 重新加载扩展。

需要 Chrome 120+ 或 Edge，两个浏览器共用同一份产物。

### 边界

- **不绕过付费墙**：会员专享番剧、电影仍需购买
- **不解锁你没有的权益**：4K / 1080P60 来自你登录的大会员账号
- **不伪装会员标识**：界面显示你的真实状态
- **不解锁地区限制**
- **与哔哩哔哩官方无任何关联**，未获授权或认可

### 已知限制

- 番剧 / 直播不支持（番剧页取流走 SSR，扩展代理不到）

### 许可证

GPL-3.0-only + [附加条款](<仓库根目录 ADDITIONAL-TERMS.md 的链接>)
```

> ⚠️ **「怎么用」这一段不能省。** 2026-10-27 实测发现：用户装完扩展、
> 打开视频发现画质没变，**因为还没登录播放账号**，而原模板没写这一步。
> InPrivate 权限同理 —— 不开的话扫码窗口根本打不开。

## 关于「已知限制」写什么

**只写「不支持且有价值让人提前知道」的东西。** 判据：

| 该写 | 不该写 |
| --- | --- |
| 功能**没做**（番剧 / 直播） | 功能**做了但未实测**（>116 分钟流地址刷新 —— 那是我们的待办，不是用户的问题） |
| 用户会直接撞上的 | 实现细节（杜比视界为什么没有徽章 —— 能播就行，说了反而引出疑问） |

**"未实测"和"不支持"性质完全不同**：前者是我们的欠账，写进 Release 会让读者以为
这版有已知缺陷；后者是范围决定，写清楚能省掉重复提问。

未实测项只在 [03-open-questions.md](../03-open-questions.md) 里跟踪。

## 检查清单（发布前逐条过）

- [ ] 标题是 `Pluma <版本>`，没有「发布！」之类的词
- [ ] 两个 zip 都在下载表里，文件名是 `pluma-<版本>.zip` 格式（不带 `v`、不带浏览器名）
- [ ] **有「也可以自己从源码构建」那句**
- [ ] **有「未经商店签名，仅供学习交流使用」那句**
- [ ] 「边界」四条齐全
- [ ] 「已知限制」只写功能不支持的项
- [ ] 全文没有 `破解` / `解锁会员` / `一键安装` / `开箱即用`
- [ ] 没有「感谢支持，欢迎 Star」之类经营项目的话
