# Release 说明模板

> Release 页是**唯一会被陌生人在 GitHub 上直接读到**的地方，也最容易被截图传播，
> 因此措辞比 README 更需要克制。
>
> 由 `scripts/package.mjs` 生成后落在 `dist/release-notes.md`，
> 发布时用 `gh release create --notes-file dist/release-notes.md`。
>
> 分发边界见 [ADR 0018](../decisions/0018-ship-built-artifacts.md)。

> ⚠️ **Release 正文的「结构」由 `scripts/package.mjs` 的 `releaseNotes()` 生成**，
> 本文只规定**怎么写内容**。不要在这里另存一份结构说明。
>
> 2026-11-10 删掉了原来那节「结构」—— 它和实现直接冲突：模板里还写着
> 「校验和」「边界」「许可证」三节（2026-10-30 已从实现删除）、「怎么用」写 3 步
> （实际 4 步）、「已知限制」写"番剧不支持"（番剧早已支持）。
> **两份结构必然漂移，权威只有一处**（`AGENTS.md` §6.1）。

## 内容来源：两半拼起来

| 部分 | 来源 | 随版本变？ |
| --- | --- | --- |
| **本版内容** | **`CHANGELOG.md` 对应版本节** | ✅ 会变 |
| 下载 / **校验和** / 怎么用 / 边界 / 已知限制 / 许可证 | `package.mjs` 的 `releaseNotes()` | 基本不变（**校验和每次打包都会变**） |

**判据：会不会随版本变？** 会变的写 `CHANGELOG.md`，不变的写在模板里。

### 为什么这么分（2026-10-27）

原来整段都是硬编码模板，只有版本号会变 —— 于是 1.0.0 的 Release
正文和 0.9.0 除了版本号一模一样，**看不到"这一版改了什么"**。

现在 `extractChangelogSection()` 从 CHANGELOG 提取 `## <版本号>` 这一节，
填进「本版内容」。**找不到该小节时打包直接失败**，不会发出空正文的 Release。

所以新增版本时：**先写 CHANGELOG，再打包**。

---

## 写作原则

| 要 | 不要 |
| --- | --- |
| 中性动词：下载 / 加载 / 构建 | 「一键安装」「开箱即用」「发布上线」 |
| 主动写「也可以自己从源码构建」 | 只给 zip，让编译变成隐藏选项 |
| 主动列「已知限制」 | 隐去不支持的东西 |
| 「修复过的 bug」用中性描述 | 「破解」「解锁会员」「绕过限制」 |
| 短 | 长（读的人不关心细节，关心的不读细节） |

**最忌讳的两个词**：`破解` / `解锁会员`。它们会直接影响对方如何定性这件事。

---

## 怎么写 `CHANGELOG.md` 里的「本版内容」

Release 正文的第一节由 `CHANGELOG.md` 提取，所以**怎么写 CHANGELOG 就是怎么写 Release**。

### 版本节标题（硬性）

```markdown
## 1.0.0
```

| 规则 | 原因 |
| --- | --- |
| **`## ` + 纯版本号**，与 `package.json` 的 version 逐字一致 | `extractChangelogSection()` 按字符串精确匹配 |
| **不带 `v` 前缀** | `v1.0.0` 是 git tag 的写法；文件名、CHANGELOG 都不用（见 `releasing.md`） |
| **不带日期** | 日期在 tag 里已有，两处写必然漂移 |
| **版本节用 `##`，子节用 `###`** | 提取时子节会自动降为 `####` |

**不匹配的后果是打包硬失败**（退出码 2）—— 这是故意的，宁可发不出去也不要发出空正文的 Release。

### 子节：按版本性质选一套

| 场景 | 用哪套子节 | 理由 |
| --- | --- | --- |
| **首个公开版本** | `### 双账号分离` / `### 界面` 这类**能力分类** | 没有上一版可比，写「新增」无从谈起 |
| **之后的版本** | `### 新增` / `### 修复` | 读者想看"这版变了什么" |

后续版本按需可再加两个（**不要凑数**）：

| 子节 | 什么时候用 |
| --- | --- |
| `### 变更` | 行为改了但既不算新增也不算修复（如"角标默认位置从左上改右上"） |
| `### 移除` | 删掉了原本支持的东西 —— **必须写**，否则用户会当成 bug 来报 |

### 版本基线：只和上一个**正式发布版**比

CHANGELOG 的比较对象永远是**上一个发布到 Release 的版本**，
**不是开发过程中的内部测试包**。

| 情形 | 归入 |
| --- | --- |
| 该功能上个正式版没有 | **新增**。开发过程中为它修的 bug **一律不写** —— 用户没有过旧版本，谈不上修 |
| 症状只在开发过程中存在过 | 不写。它没有用户 |
| 上个正式版有这功能，行为被改了 | **修复** / **变更**，可写 |

判据一句话：**上一个正式版的用户升级后，能观察到什么不同？** 答不上来就不写。

> 反面案例（1.4.0 初稿）：写了 11 条「修复」，其中 10 条修的是本版新做的东西 ——
> 时间轴、PCDN 开关、活动页支持。1.3.0 里 `src/core/loading/timeline.ts` 这个文件
> 都不存在，「换集后时间轴不归零」对它的用户是空话。
> 这些不是修复，是把开发过程汇报给用户。

### 条目写法

```markdown
- 支持活动专区页（`/festival/*`）的视频
- 面板「显示」Tab 新增「屏蔽 PCDN 线路」开关
- 切换清晰度或播放出错重连后，播放位置回退到先前位置
```

| 要 | 不要 |
| --- | --- |
| **动词开头**（支持 / 新增 / 改为 / 修复） | 「番剧支持」—— 看不出是新功能还是修复 |
| **一行一条** | 一条里塞多个改动 |
| **只陈述事实**：多了什么、改了什么、修了什么 | **解释它能带来什么**（「弱网起播更稳」「你第一时间就知道」） |
| **只写现在的样子** | **写从前是什么**（❌「（原为先播试看画面再整页刷新）」） |
| **不写内部实现** | ❌「重构了 DNR 规则管理」→ ✅「修复关闭总开关后个别标签页画质不回落」 |
| **不写"优化了体验"** | 无法验证等于没说，要具体到"画质菜单出现更快" |
| **不写排期与来源** | ❌「原计划 v1.5，提前完成」—— 用户不关心我们的节奏 |

#### 为什么不能解释收益、也不能写从前

CHANGELOG 回答「**这版有什么变化**」，不回答「**为什么值得升级**」，
也不回答「**以前是怎么坏的**」。

前两者由 Release 页正文和 README 承担；第三者由 ADR 与 commit message 承担。
条目里再写一遍，就是同一件事在多处重复，而且每处措辞不同，必然漂移
（`AGENTS.md` §6.1：每件事只有一个权威位置）。

功能说明书归 UI —— 开关的名字、面板里的提示文字已经说明它做什么，
条目只登记**名称**。同理，「改成了什么」写清楚，读者自然知道它与自己的旧版本不同，
**不需要我们替他做这个对比**。

#### 一条 = 一个事实（可机械检查）

出现下列任一即视为违规：

| 违规形态 | 例 |
| --- | --- |
| 括号补旧行为：`（原为…）` `（此前…）` `（原来…）` | ❌「取流改为进页即启动完整流（原为先播试看画面再整页刷新）」 |
| 冒号后超过 12 字 | ❌「新增「屏蔽 PCDN 线路」：不看 P2P 线路，全部走 B站 官方镜像」 |
| 出现破折号 `——` | ❌「支持活动页的视频——这类页面的播放器也会被接管」 |
| 收益词：`即可` `就能` `不再用` `省得` `第一时间` `更稳` `更快` | ❌「改为进页即启动完整流——**进页即可拖进度**」 |

改写方式就一句：**把括号/冒号/破折号之后整段删掉**，剩下的通常就是合格条目。

#### 两种句式（够用，不要自创）

| 句式 | 用于 |
| --- | --- |
| `支持 <对象>` | 能力扩张（支持番剧 / 支持活动页） |
| `面板「X」Tab 新增「Y」开关` | 界面新增开关 / 条目 |

#### ⚠️ 所有子节都只写一行，不只「修复」

原规则只约束「修复」和「变更」，于是 1.4.0 的「新增」也写出了长解释 —— 说明规则漏了。
现在适用于**全部子节**（首个公开版的「能力分类」节除外，那里允许讲用法步骤）。

#### ⚠️ 修复只写一行，不写任何补充说明（2026-10-30 定，用户明确要求两次）

**`### 修复` 下每条就是一个标题行，没有子级解释。**

```markdown
### 修复

- 番剧页偶发「画质菜单能选 4K，实际只有 1080P」
- 个别集数停在 6 分钟试看
- 重开总开关后最长 10 分钟仍卡在试看
- 关掉总开关后个别标签页画质不回落
```

| ❌ 不要 | ✅ 要 |
| --- | --- |
| 条目后加 `- 部分番剧集的完整流是另一种编码形态…` 这类子级说明 | 只留标题行 |
| 「此前"已刷新过一次"的记录会拦住后续刷新」 | 不写修复前的行为 |
| 「原来没被识别出来，于是被当成试看流处理」 | 不写修复前的行为 |
| 「播放位置回退（原会被拽回几分钟前）」 | 只写现象本身 |

#### 为什么（2026-10-30 定，用户要求过两次；2026-11-19 扩到全部子节）

1. Release 页是给**用户**的，他只需判断"这版值不值得升级"——原理对他没有信息量
2. 写了原因，就不可避免要写"此前是什么"，于是把内部机制拖进来，
   与「不写内部实现」直接冲突
3. 原理与修复前行为**已经记录在 ADR 和 commit message 里**，CHANGELOG 只留结论
   （`AGENTS.md` §6.1「每件事只有一个权威位置」）

**`### 新增` 的例外**：允许有序号步骤 —— 那是在告诉用户**怎么用**（首次使用要做什么），
不是内部讲解。但仍不得写收益与原因。

### 需要用户操作时，单列

变化影响用户操作时**必须说清**，用引用块放在子节之后（视觉上更醒目）：

```markdown
> ⚠️ 首次使用需重新扫码 —— 凭据格式有变，旧版无法迁移。
```

三类常见情形：**需要用户操作** / **只影响特定场景** / **不兼容**。
如果什么都不用做，可以省略。

> ⚠️ **引用块只承载"用户需要做什么"，不写本版概括**（2026-11-17 用户明确要求）。
>
> | 允许 | 禁止 |
> | --- | --- |
> | 「⚠️ 首次使用需重新扫码 —— 凭据格式有变」 | 「界面整体重做，功能位置与用法没有变」 |
> | 「⚠️ 设置页已废除，功能搬到了页面左侧的贴边面板」 | 「本次更新带来更清爽的视觉体验」 |
> | 「⚠️ 旧版配置不兼容，需重新选择一次」 | 「本版优化了若干细节，提升了稳定性」 |
>
> **判据：删掉这句话，用户会不会多做错一件事？**
> 会 → 它该留；不会 → 它就是噪音。
>
> 这条规矩的由来：1.3.0 的 Release 正文开头写了两行灰体概括
> （"界面整体重做…功能位置与用法没有变"），用户的原话是
> 「这些字全部删掉，以后我也不想看到这种灰体的概括介绍」。
> 概括在 Release 正文里是**重复**：下面「变更」列表已经逐条说了改了什么。

### 什么时候写

**功能完成时就写，不要等发布时回忆。** 发布时间想起"这版改了什么"必然遗漏。

做法：`CHANGELOG.md` 顶部常备一节

```markdown
## 未发布

### 新增

- （边做边记）

## 0.9.0
...
```

发布时把「未发布」改成版本号。`extractChangelogSection` 只认精确版本号，
所以「未发布」不会被误提取。

## 关于「已知限制」写什么

**只写「不支持且有价值让人提前知道」的东西。** 判据：

| 该写 | 不该写 |
| --- | --- |
| 功能**没做**（番剧 / 直播） | 功能**做了但未实测**（>116 分钟流地址刷新 —— 那是我们的待办，不是用户的问题） |
| 用户会直接撞上的 | 实现细节（杜比视界为什么没有徽章 —— 能播就行，说了反而引出疑问） |

**"未实测"和"不支持"性质完全不同**：前者是我们的欠账，写进 Release 会让读者以为
这版有已知缺陷；后者是范围决定，写清楚能省掉重复提问。

未实测项只在 [03-open-questions.md](../03-open-questions.md) 里跟踪。

## 检查清单（发布前逐条过）

- [ ] 标题是 `Pluma <版本>`，没有「发布！」之类的词
- [ ] 两个 zip 都在下载表里，文件名是 `pluma-<版本>.zip` 格式（不带 `v`、不带浏览器名）
- [ ] **有「也可以自己从源码构建」那句**
- [ ] **有「未经商店签名，仅供学习交流使用」那句**

- [ ] 「已知限制」只写功能不支持的项
- [ ] 全文没有 `破解` / `解锁会员` / `一键安装` / `开箱即用`
