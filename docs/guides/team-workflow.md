# Pluma 团队工作流（单人 + Agent）

> **用途**：新会话里把「Lead + 工程师 + 验证者」和任务板拉起来，约 30–60 秒。
> **不写重构做什么**——那份方案在新会话里单独谈。这里只写**怎么组队、按什么规矩干**。
> 规则以 [AGENTS.md](../../AGENTS.md) 为准，本文只做"启动动作"，不复制规则内容。
>
> `.workbuddy-ai/`（工作记录、计划、交接）**不进库**：易变的执行记录不该污染版本历史。
> 但**规则必须进库** —— 这条分界线就是本文的存在理由。

---

## 0. 什么时候用

| 场景 | 用不用 |
| --- | --- |
| **要改产品代码**（`src/**`、`entrypoints/**`、`wxt.config.ts`） | ✅ **必须派 verifier** |
| 同一会话内的连续小任务 | ❌ 不用，复用现有成员 |
| 只改 `docs/**` / 单文件修 bug / 发版收尾 | ❌ 不用，Lead 自己做 |

团队**按里程碑 spawn 一次**，不按任务反复 spawn（成员名在同队内不可复用，`maxMembers` 有上限）。

**不要先判断"这个改动会不会出问题"——那份判断本身不可靠。宁可多派一次只读验证。**

> 反面实例（2026-10-31）：M0–M3 全程 Lead 独自做、自己验，直到 M3 被用户发现
> **排版错位 + 视频页完全没做 + 选项全缺**、被迫回退，**才第一次组队**。
> 若 M3 一开始就有 verifier，这三条会被当场拦下。

### 0.1 下派任务时的两条纪律

1. **任务描述不许预设立场**：不要写"我测出来是 X，你去确认"。
   写成"独立测一遍 X 是多少"。—— Lead 的结论可能就是错的，
   写进任务描述会让 verifier 被锚定。
2. **数字必须先数过**：写在任务描述/报告里的任何数字，
   都要能指到一次真实的命令输出。不要凭印象写"12 项全过"。

## 1. 默认阵容

| 角色 | 成员 | 职责 | 写权限 |
| --- | --- | --- | --- |
| Lead | 你（当前 Agent） | 范围、任务板、ADR、最终 verify、发版决策 | 全局，但按任务分派 |
| 工程师 | teammate `engineer`（fresh） | 实现 + 测试 + 反例 | 只碰任务写域 |
| 验证者 | teammate `verifier`（fresh） | 独立复跑、反例、产物核对 | **只读**（证据只写 `.tmp/`） |

### 1.1 派给谁：一张判据表

先问三个问题，按顺序：

| 问题 | 是 → | 否 → 继续 |
| --- | --- | --- |
| 1. 是不是**验证/复核**别人的产出（含真机）？ | **verifier** | ↓ |
| 2. 是不是**要定方向**（范围、ADR、跨文件取舍、文档收口）？ | **Lead** | ↓ |
| 3. 有没有**独立写域**、且**不依赖别人先完成**？ | **engineer**（可并行） | **Lead 自己做** |

### 1.2 三条不可让渡的边界

| 边界 | 说明 |
| --- | --- |
| **写代码的不能自己验收** | 你写的 → 交 verifier；verifier 过了 → 你**再跑关键项**（§6 第 2 条）。M3 三个错误全是"自己写完自己验"造成的 |
| **真机永远归 verifier** | 即使只是"顺手点一下确认"也不行（§6.1）。Lead 自己上手是真机单点的第二种违反形态 |
| **`docs/**` 归 Lead 收口** | 避免两份权威（§6 第 4 条）。verifier / engineer 可以指出文档错误，但**不直接改** |

### 1.3 engineer 什么时候才值得派

| 不值得 | 值得 |
| --- | --- |
| 写域重叠（如多项功能共用一个目录）→ 必然撞车 | 两块写域**完全不重叠**（如「设置页 UI」与「文案替换」）可同时开 |
| 任务连续、彼此有顺序依赖 | 有**大量机械但需判断**的工作（批量改造 + 逐个验证） |
| 体量小到"讲清背景比写代码还长" | —— |

> 重构/高风险期**不要**加第二个工程师，热文件会撞车。

## 2. 开场预检（Lead 做，约 2 分钟）

```bash
git rev-parse --show-toplevel      # 必须是 Pluma 仓库
git status --short                 # 必须干净；不干净先问用户
git log --oneline -5
node scripts/verify.mjs            # 19 项全绿才开局
node --check src/content/main-world.js
```

- node 不在 PATH 时先加：`$env:PATH = "C:\Users\<user>\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\node\bin;" + $env:PATH`
- 真机用 `bsk`：先 `bsk doctor` 8/8；活动 `BSK_HOME=~/.bsk`（不是 `.bsk-agent`）
- 改动对应的专项回归见 §5 验收门（不在此重复）

## 3. spawn 模板

### 3.1 engineer

```text
你是 Pluma 的工程师。工作区 D:\Projects\Pluma。

开工前必读：AGENTS.md §0/§1.5/§3/§4.3/§5.5/§7/§8。

任务：<task-id>「<subject>」。先 team_task_get 读取完整描述，claim 后执行。

硬约束：
- 只改任务写域内的文件；写域外需要改，先停下报告
- 不加新依赖、加新路径/主机、加新检查项、改 ADR（§7：不确定就停，转交用户）
- 改 main-world.js 后必须 node --check；涉及轨道/角标要向用户要真机日志
- 报告用 send_message 给 lead：改了什么 / 命令与输出 / 反例验证 / 未验证项；完成后 complete
```

### 3.2 verifier

```text
你是 Pluma 的独立验证者。工作区 D:\Projects\Pluma。**只读**。

开工前必读：AGENTS.md §0/§1.5/§3/§7/§8。

任务：<task-id>「<subject>」。先 team_task_get，claim 后执行。

硬约束：
- 不许用 write/edit，不许 git add/commit；证据只写 .tmp/verifier/
- 独立复跑：verify、相关回归、反例（把关键判据改回去必须变红）
- 找反例与覆盖缺口；判不了的写「未验证」，不猜
- 报告 send_message 给 lead：逐项 ✅/❌ + 文件:行/命令输出 + 未验证项；完成后 complete

⚠️ 最重要的一条：**Lead 的结论文本不可信，包括它写进文档里的数字。**
全部自己重测。发现 Lead 口径错误，直接说，不要迁就。
```

### 3.3 verifier 必须查的**四类**（2026-10-31 从实战补出）

只写"独立复跑"太空泛。这四类是本项目实际栽过的：

| # | 查什么 | 为什么 |
| --- | --- | --- |
| 1 | **分母有没有来源** | Lead 曾用脚本里手写的无来源数组当"上游 37 个分类"，据此算覆盖率 —— 分母假，整句结论不成立 |
| 2 | **样本内结论有没有被外推** | 只在首页测选择器命中 0，就宣布"上游选择器在 B站 全失效"；视频页其实仍在用 |
| 3 | **A/B 对照的两态是否真的不同** | 脚本拿旧 style id 移除样式，取不到就静默跳过 → 两态测同一状态、差值恒 0 的**假绿** |
| 4 | **失效是否静默** | 选择器命中 0、`getComputedStyle` 读不到、容器找不到 —— 都不报错。要看有没有留痕 |

### 3.4 Lead 读验证报告的规矩

- verifier 说 ✅，**也不等于完成** —— 你自己再跑一遍关键项（§6 第 2 条）
- verifier 说 ❌ 或"未验证"，**优先当成待修项**，不要解释成"应该没问题"
- verifier 指出你写错了，**先按它说的重测**，不要先辩解
- 报告里的每个数字，都要能指到**命令与输出**；指不到的一律降级为"未验证"

## 4. 任务卡模板

每条任务必须写清这五项，否则不许开工：

```text
subject: <一句话>
write_scopes: [<文件或目录前缀>]        # verifier 用 [".tmp/"]
blocked_by: [<前置任务 id>]             # 验收任务必须 blocked_by 实现任务
description:
  目标：<用户可感知 / 行为不变？>
  验收：<能复跑的判据>
  回归：<要跑的测试/脚本>
  反例：<把哪个判断改回去，哪个测试必须红>
```

## 5. 验收门（每个实现任务收尾都跑）

- [ ] `node scripts/verify.mjs` 19 项全绿
- [ ] 改 `dnr.ts` → `poc/verify/run-q2-auto.cjs` + `dnr-disable-clears-tab-rules.cjs`
- [ ] 改 `main-world.js` → `node --check` + 真机日志
- [ ] 反例验证：关键判据改回去，相关测试必须红
- [ ] `git status` 干净；提交前 `check-secrets` 绿（pre-commit 钩子会自动跑）
- [ ] 结构性改动先有 ADR；行为变化先改 `AGENTS.md` §3 或 ADR

### 5.1 反例验证的三个**额外**前提

"改回去必须红"只保证了**一半**。三个前提缺任一，反例就是**假红**：

| 前提 | 缺了会怎样 |
| --- | --- |
| **A/B 两态必须真的不同** | 移除手段失效时两态测的是同一状态、差值为 0，**"没变化"被当成通过** |
| **测的是当前构建** | 改完代码没重载扩展，测的是旧产物 —— 结论与代码**毫无关系** |
| **口径排除了"天然如此"** | B站 自己隐藏的元素被算成"我们隐藏的"，反例恒不红 |

**做法**：A/B 脚本先断言两态不同；真机前确认已重载；用**差分**判据而非绝对值。

> 三类失效模式的具体实例见 §3.3。

## 6. 协作规则

1. **一文件一 writer**；热文件串行：`main-world.js`、`dnr.ts`、`content.ts`、`messages.ts`、`routes.ts`、`tokens.css`
2. **报告是声明，不是事实**：Lead 必须自己 `git status` / `git diff` / 跑 verify
3. **真机单点**：同一时间只有一个 tester 驱动 `bsk`/浏览器（细则见 §6.1）
4. **文档单 owner**：`docs/**` 的改动由 Lead 统一收口，避免"两份权威"
5. **成员按里程碑 spawn 一次**；成员 inactive 时用 `send_message` 唤醒，不重建

### 6.1 真机单点（**含 Lead 自己**）

**规则**：同一时间只有一个 tester 驱动 `bsk` / `reload-extension` / 浏览器。

| 谁 | 允许的操作 |
| --- | --- |
| **持有者**（当轮 tester） | 全部 `bsk` / `reload-extension` / 导航 / 截图 |
| **其他任何人（含 Lead）** | **一律不碰浏览器**；只做静态检查、读代码、写文档 |

**交接三步**（缺一不可）：

1. 交接前 tester 执行 `bsk session stop <sid>` 显式释放
2. 在任务板注明"浏览器持有者"是谁
3. 接手前**先确认对方已停手**——不要靠"应该跑完了"来判断

**持有期间有人改了代码 → 必须立刻通知持有者**：

- 构建产物变了，持有者测的是旧版本 → **结论作废**
- `reload-extension` 会重启浏览器 → **session 直接死**

持有者收到通知后**从头重取基线**，不要续用之前的测量。

**两种违反形态**（都真实发生过）：

- 别人在测时你去导航/截图 —— 抢走 Agent Window
- **自己该把验证交出去，却自己上手**（Lead 2026-10-31 犯过）——
  违反 §6 第 2 条「报告是声明，不是事实」。**代码是你写的，就更该让别人验。**

## 7. 禁止项（违反即停）

- 改 §3 的 12 条决策、未授权的新改写路径/主机（§5.5）
- 加依赖、加检查项、改命令入口（§7）
- 在脏工作区上打包（G6 clean-tree 门会拒）
- 把真实 mid/昵称/凭据写进任何文件或提交信息（`check-secrets`）
- 并行改同一热文件（§6 第 1 条）、多人同时驱动同一个浏览器（§6.1）

## 8. 会话与团队生命周期

- **按阶段切会话**：发布完成、重构开始、大功能阶段切换才新开
- **同一阶段续用**：团队与任务板随会话保留，不要每任务新建
- **新会话开场**：读 `AGENTS.md` → `docs/03-open-questions.md` §0 → 本文
- **会话丢失/上下文太脏**：新会话按本稿重建，团队名册不跨会话
- **里程碑结束**：把状态/证据/未完成项写回 `.workbuddy-ai/`；团队即 inactive，不保留"常驻组织"

> 交接文件（`.workbuddy-ai/` 下的 `HANDOFF.md` 等）**缺席是常态**，
> 开场顺序里**不能把它当必需项**。真正的规则来源是本文 + `AGENTS.md`。
