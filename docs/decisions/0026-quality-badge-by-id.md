# ADR 0026：画质徽章改用 `quality id`，并修订 ADR 0014 的"HDR 不出徽章"

- 状态：**已采纳**（2026-10-29，用户真机指出）
- **修订**：[ADR 0014](./0014-quality-compare-from-page-data.md) 中「HDR 永不产出徽章」这一条
- 影响文件：`src/shared/types/playinfo.ts`（`Capability.topQualityIds`）、
  `src/shared/utils/quality.ts`（`QUALITY_NAMES` / `qualityLabels`）、
  `src/core/playinfo/rank.ts`、`src/core/playinfo/summary-view.ts`

---

## 触发这次修订的原话

> 「我测试的这个番剧有 1080p 高码率还有 HDR 真彩」

而 popup 只显示了一个 `1080P`。

---

## 根因：`heightLabel()` 把同高度的多个档折叠成一个

改动前 `unlockedBadges()` 的第一行是 `heightLabel(cap.maxHeight)`。
而 B 站**在同一个像素高度下分多个档**，真机实测（ss34412）：

| qid | `support_formats` 名称 | `height` | 码率 |
| --- | --- | --- | --- |
| 125 | HDR 真彩 | **1080** | 1437687（AV1） |
| 112 | 1080P 高码率 | **1080** | 3461623（AVC）/ 1669370（HEVC）/ 1072363（AV1） |
| 80 | 1080P 高清 | **1080** | 987711 |
| 64 | 720P 准高清 | 720 | 658795 |

`heightLabel(1080)` 对前三个都返回 `1080P` —— 用户能看到的三档，界面上只剩一个。

**这不是"少标了一个"，而是信息被抹平**：1080P 高清和 1080P 高码率的码率差 3.5 倍，
HDR 更完全是另一回事，用户无法从 popup 判断这次到底拿到了什么。

---

## 决定

**徽章的主判据从「像素高度」改为「`dash.video[].id`」。**

### 为什么用 `id` 而不是 `accept_quality`

| 来源 | 能不能用来判断"拿到了什么" |
| --- | --- |
| `dash.video[].id` | **能**。服务端在**每一条真实轨道**上返回的 id |
| `accept_quality` | **不能**。未登录时返回含 8K 的假数组（Q9，`poc/verify/RESULT.md` §四） |
| `support_formats` | **不能单独用**。它是"视频支持的档位"，不是"这次给到了哪些轨" |

所以：**id 从 `dash` 里取，从 `accept_quality` 里一个字都不取。**
这与 [ADR 0014](./0014-quality-compare-from-page-data.md) 的核心纪律完全一致 ——
变的只是"从 dash 的哪个字段读"，从 `height` 变成 `id`。

### `Capability` 新增 `topQualityIds: number[]`

**最高那一档**在 `dash.video` 里出现过的所有 id（去重、降序）。

- 空数组 = 取不到 id（老数据 / 解析失败）→ UI 退回 `heightLabel(maxHeight)`，**不许猜档位**
- 只有**最高高度那一档**的 id，不是全部 —— 徽章讲的是"拿到了哪些高分档"，
  把 360P/480P 也列出来是噪音

### 名称表只收实测过的 id

`QUALITY_NAMES` 里每个键都标了观测来源。表里没有的 id → 返回空串 →
调用方退回高度标签。**不许凭记忆补全整张表**：写错一个 id 的后果是
用户看到「8K」而实际只有 1080P，属于这个项目最不能犯的错。

---

## 修订 ADR 0014 的哪一条

ADR 0014 写的是：

> | ~~`HDR`~~ | **永不产出**，见 ADR 0014 |

理由是「四个可用信号全被实测证伪」。

**那句话针对的是运行时信号**：`(video-dynamic-range: high)`、
`(dynamic-range: high)`、编码家族（AV1/HEVC 都能承载 SDR 和 HDR）、
`<video>` 元素的属性 —— 它们**确实判断不了**"当前这条轨是不是 HDR"。

而 `dash.video[].id === 125` 是**另一类事实**：它是服务端在真实轨道上
标注的档位 id。它说明「这次下发的轨里有 HDR 档」，
**不声称**「你正在看 HDR」。所以：

- ✅ 可以说：徽章 `HDR`（语义 = 本视频本次提供了 HDR 档）
- ❌ 不可以说：角标写「你在看 HDR」（那是运行时事实，仍然判不了，ADR 0014 原文保留）

**页内角标不受本次修订影响**，它仍然只用 `videoHeight` + SourceBuffer 的实际 mime。

## 一条自查：为什么这个 bug 之前没被发现

`tests/fixtures/playinfo/playback-4k.json` 里 4K 档只有 `120` 一个 id、
1080 档只有 `80`（见 fixture 的 `dash.video`），**没有 112 / 125**。
所以"同高度多档"这个真实情况**在 fixture 里根本不存在**，测试自然抓不到。

**教训**：fixture 覆盖了"有 4K"，却没覆盖"同一高度有多个档"。
以后补 fixture 要按 `support_formats` 的真实清单来，而不是挑几条代表轨。

## 补记：`topQualityIds` 的收集范围（2026-10-29 三次修正）

这个字段的收集逻辑被真机推翻了两次，过程值得留下 —— 因为**每一次都是"合理的设计"**，
每一次都被实际数据否掉。

| 版本 | 做法 | 真机暴露的问题 |
| --- | --- | --- |
| v1 | 只收 `height === maxHeight` 的轨 | 4K 视频里 `112`(1080P+) 明明能选，却没标 |
| v2 | 每个高度档取最高 id | `125`(HDR) 与 `120`(4K) **同在 2160 档**，取最大把 `120` 丢了 → **4K 徽章消失** |
| v3（现行） | **收全部真实 id，按 id 降序** | —— |

### v3 的关键认识

**`height` 不能用来做"档位优先级"的判断。**

同一高度下有多个**互不包含**的档：`125`(HDR) / `120`(4K) / `112`(1080P+) 都是用户
能分别选的东西。任何"每个高度只留一个"的收敛都会丢掉真实存在的选项。

### 那低档（720/480/360）怎么办

**在展示层处理，不在数据层裁剪。**

- `capabilityOf()` 如实收全部 —— `Capability` 是**数据**，该描述"拿到了什么"
- `BADGE_QUALITY_NAMES` 只保留能体现"额外价值"的档（8K/杜比视界/HDR/4K/1080P60/1080P+/1080P），
  720 及以下不做徽章 —— 那是**展示决策**
- PGC 页再由 `PGC_HIDDEN_BADGES` 过滤掉 `1080P/720P/480P/360P`

**把展示偏好塞进数据层，就会出现 v1/v2 那种"数据为了 UI 好看而被裁剪"的错误。**

### 用户是怎么发现 v1 的

> 「番剧的集数里面是能正常显示 1080p+ 的，只有国创等的集数里面才不会显示，就不能统一一下吗？」

真机数据（国创 ep733317）：
```
125@2160  120@2160×3  112@1080×3  80@1080×3  64@720×3  32@480×3  16@360×3
```
`112` 明明在 dash 里。番剧那几集"能显示"是因为**它们最高只有 1080**，
`112` 正好落在最高档里；国创这集最高 2160，`112` 就被 v1 的 `height !== maxHeight` 挡掉了。

**同一份代码，因为最高高度不同而表现不同** —— 这就是"不统一"的根因。

### 验证

`tests/unit/core/playinfo/rank.test.ts` 新增 3 条，其中「4K 视频里 1080P+ 依然要收进来」
直接对应这次反馈。**反向验证**：改回 v1（加 `height !== maxHeight` 的 continue）→ 3 条红。
