# ADR 0031：页内视觉改造是**第三类**能力 —— 不碰请求、不碰响应、不碰账号

- 日期：2026-10-31
- 状态：**已采纳**（2026-10-31 用户拍板）

## 背景：功能从"一条链路"变成"两类链路"

1.0.x 只有**一条**改造链路：在网络层换身份、在响应层改字段（ADR 0004 / 0013 / 0017 / 0021）。
它全部作用在**请求与响应**上，**从不碰页面 DOM**（唯一例外是 ADR 0022 的 toast 隐藏，见下）。

1.1.0 引入的三项（删除广告 / 首页净化 / 删除直播水印）性质完全不同：**它们只改用户眼前的页面**，
不发一个请求、不改一个字节的响应、不读账号。

**把两类混进同一份授权清单，会让"越权"这件事失去判据**：`check-patch-scope.mjs` 现在守的是
「哪些接口的响应能被改」，而新功能根本没接口。硬塞进去，等于把这把尺子废掉。

---

## 决定一：新能力**不进** `PATCH_PATHS` 那套授权表

`AGENTS.md` §5.5 的四类改写（`PATCH_PATHS` / `PROGRESS_PATCH_PATHS` / `PGC_PREVIEW_FLAGS` /
`PGC_TOAST_ITEM`）**一条都不动**，也**不新增第五类**。

**为什么不算"第五类改写"**：

| 维度 | 四类改写（ADR 0013 等） | 页内视觉改造（本文） |
| --- | --- | --- |
| 作用面 | 网络请求头 / 响应体 | 页面 DOM 与 CSS |
| 影响对象 | 服务端返回的数据、播放器判断 | 用户看到的元素 |
| 失效后果 | 画质上不去、灰屏、播放中断 | 广告还在、水印还在（**功能不可用，但不损伤任何数据**） |
| 越权风险 | 高（改的是"权益外观"与"账号可见性"） | 无（连账号都不读） |
| 谁在守 | `check-patch-scope.mjs` 对账 ADR | 无自动化，靠真机冒烟 |

> **判据一句话**：改响应体 = 让**网站**相信一件不真的事；改 DOM 样式 = 让**用户**少看一个元素。
> 前者需要逐字段授权，后者只需要一份"能碰哪些页面"的边界（下面 §决定二）。

**与 ADR 0022 的区别**：ADR 0022 也动 DOM（隐藏 `PromptBar` toast），但它是**为取流服务**的
（不藏它，播放器会在 361 秒处主动停），因此仍挂在 PGC 那条链路的授权里。
本文这三项**与取流无关**，是纯偏好功能，所以单独成篇。

---

## 决定二：边界由「**能力**」划定 —— 视觉清理与取流互不越界

既然不碰请求与响应，越权的风险就从"改了不该改的数据"变成"**在用户没预期的页面上动手**"。

### 2026-10-31 修订：从「按站点」改为「按能力」

初版把边界写成**站点白名单**（首页归视觉清理、播放页归取流）。实施 M3 时发现这个划法不成立：

**视频详情页同样有广告**（实测 3 个可见单元：`.ad-report.strip-ad.left-banner` 668×56、
`.ad-report` 350×104、`.ad-report.ad-floor-exp` 350×175），
若播放页整站划给取流链路，这些广告就永远没人处理。

所以边界改为**按能力划分**，两种能力可以在同一 URL 上共存：

| 能力 | 归属 | 可作用的页面 | 绝不做的事 |
| --- | --- | --- | --- |
| **视觉清理**（插样式 / 打标记） | `content-home` | `www.bilibili.com` 全站（内部按 URL 分支决定做哪几项） | 读 cookie、发请求、改响应、遮播放器、碰播放器内部节点 |
| **取流接管**（报到 / 观察画质 / 下发配置） | `content.ts` | 仅 `/video/*` 与 `/bangumi/play/*` | 改页面样式 |
| 直播水印清理 | `content-live` | `live.bilibili.com/*` | **任何取流行为** |

**两条能力互不调用、互不读对方状态**，各自独立失效。这是本次修订的核心保证。

### 具体到 content script（实测依据）

| 入口 | `matches` | 内部按 URL 分支 |
| --- | --- | --- |
| `content-home.content.ts` | `*://www.bilibili.com/*` | 首页 → 广告 + 净化；视频页 → **仅广告**；其它 → 什么都不做 |
| `content.ts` | `/video/*`、`/bangumi/play/*` | 不变（取流编排） |
| `content-live.content.ts` | `*://live.bilibili.com/*` | 不变（水印） |

⚠️ **`content-home` 扩到全站是能力范围扩大，不是权限扩大**：`host_permissions` 本来就有
`*://*.bilibili.com/*`，这里只是让"视觉清理"这一能力在已授权域内**按需生效**。
但**注入面确实变大了**，所以它必须遵守下面三条硬约束：

1. **按 URL 白名单分支**：不认识的页面直接 `return`，**不许"顺手也清一下"**
2. **绝不碰播放器内部节点**（`.bpx-player-*`、`video` 元素）：那是取流链路和用户的领域
3. 新增任何作用面（新页面 / 新选择器族）**必须先改本文**

### 站点层面仍然如此

| 站点 | 允许 | 不允许 |
| --- | --- | --- |
| `www.bilibili.com` | 视觉清理（按 §上表的能力约束） + 取流（仅播放页） | 读 cookie、发请求、改响应、遮播放器 |
| `live.bilibili.com` | 仅插样式隐藏水印 | **任何取流行为**（见决定三） |
| 其他任何站点 | —— | **一律不注入** |

### `host_permissions` 的扩面：并列加 `live.bilibili.com`

现状只有 `*://*.bilibili.com/*`。而直播间的 URL 是 **`live.bilibili.com/<房间号>`**，
**不匹配**该条（`*.bilibili.com` 的 `*.` 只覆盖子域，不覆盖把主域当子域用的情形以外的写法——
实测结论：现有条目覆盖不到 `live.bilibili.com`，因此需要独立条目）。

**代价必须写清**：装包时用户看到的权限提示会从"bilibili.com"变为**"bilibili.com 和 live.bilibili.com"**。
这是本 ADR **唯一会改变用户可见行为**的地方，也是 §决定一 说"新能力本身无越权风险"时
唯一的例外。

## 决定三：**不翻案 ADR 0007，只澄清口径**

ADR 0007 的结论是「v1 只做视频 + 番剧，直播不做」。本 ADR **不改它**：

| 仍然不做 | 依据 |
| --- | --- |
| 直播**取流代理**（换 Cookie 拿更高画质） | `routes.ts` 两条直播路径**保持 `enabled: false`**，不许改 |
| 直播的会员权益相关能力 | 与 ADR 0004 的前提不符（直播取流链路未验证） |

**唯一新增的能力**是直播间的**样式层清理**（隐藏水印 logo）。

**因此 README 的措辞必须改**：原文「**不支持直播**——这是决定，不是遗漏」会被读成
"扩展在直播间完全不工作"，而现在它**会**注入（只是不碰取流）。
改为「**不做直播取流**」（理由与取舍由本文承载，README 只留结论）。

> ⚠️ 这两件事同时成立很容易被误读，所以 `routes.ts` 里那两条 `enabled: false` 的 `note`
> **要补一句**：`不改 true；直播间只做样式清理，不取流`。否则下一个人看到"支持直播页了"
> 会顺手把白名单打开 —— 那才是真正的翻案。

## 决定四：Shadow DOM 例外 —— 且**只**适用于页面级样式

`AGENTS.md` §5.3 规定「页内注入必须用 Shadow DOM（`mode: 'closed'`）」。本文**不改这条规则**，
而是**限定它的适用范围**：

| 注入的是 | 是否 Shadow DOM | 为什么 |
| --- | --- | --- |
| **我们自己的 UI**（页内角标、未来的悬浮控件） | ✅ **必须** `mode:'closed'` | 与页面样式互相污染；页面脚本不得篡改我们的 UI |
| **作用于页面元素的样式**（隐藏广告 / 水印 / 卡片） | ❌ **必须不进** | CSS 作用域规则决定：shadow root 里的选择器**无法命中**外部文档的元素 |

**这不是"放宽纪律"，是"这条纪律本来就只针对 UI"。** §5.3 的理由是"与页面样式互相污染"，
而隐藏页面元素的样式**天然就该是页面级**的 —— 它要命中的就是页面元素。

> 曾考虑过的替代方案：用 `chrome.scripting.insertCSS` 注入而不是自己插 `<style>`。
> 两者都作用于文档树，本条结论相同；具体取哪种属于实现细节，不在本 ADR 决定范围内。

## 与"不做远程配置"（决策 6）的关系

选择器表是**内置在包里的常量**，不从任何服务器拉取。@不新增远程配置机制。

**代价要在 ADR 里说清**：B 站改版会让选择器失效，而**我们没有任何远程手段修复它**，
用户必须等下一个版本。这正是把"失效可见化"（诊断页显示匹配状态）列为必需项的原因 ——
否则用户只会看到"这插件突然没用了"。

## 后果

**正面**：

- 三项功能与取流链路**完全解耦**，任何一个失效都不会影响画质
- 授权形式从"逐字段"变成"逐站点"，`check-patch-scope.mjs` 的原有尺子**不受污染**
- 为后续同类功能（隐藏推荐、精简首页等）预留了不需要再写 ADR 的空间（只要**不扩站点**）

**负面 / 已知弱点（不许当成已验证）**：

1. **B 站改版即失效**，无远程修复手段（见上）
2. **"删除直播水印"的 CSS 方案只在"水印是 DOM 元素"时有效**。若 B 站把水印烧进视频画面，
   CSS 必然无效 —— **未实测**，写入 `docs/03-open-questions.md` Q18
3. **无自动化测试**：DOM 样式功能跑不了完整单测，只能真机冒烟 + 离线 jsdom 验证 CSS 规则。
   这是本 ADR 主动接受的测试债务
4. 权限提示变化可能让部分用户顾虑（已在上文列为明示代价）
5. **选择器失效是静默的**：命中 0 不报错。这是本条最需要警惕的失败模式。

## 附录：2026-10-31 独立验证的纠正

首轮实施时有三条结论被独立验证者推翻，**记录在此以防重犯**：

| 当时的说法 | 实测 | 教训 |
| --- | --- | --- |
| 「上游 37 个首页分类只有 4 个有落点」 | 滚动 80 步后出现 **9 类**；且那"37 项"是脚本里**手写的无来源数组**，含"广告"这种非分类项 | **分母不可信时，覆盖率无从谈起**。先确认名单来源，再谈覆盖率 |
| 「上游选择器在当前 B站 全部失效」 | 仅对**首页**成立；视频页的 `.gg-pic` 等**仍然存在**，实测有 8 类可见广告位 | **样本内结论不得外推**。首页 ≠ 全站 |
| 「`.bili-video-card` 是视频页卡片类名」 | 视频页该类名命中 **0**；真实是 `.video-page-card-small` + `.rec-list` | 每类页面必须**单独实测**选择器 |

另两条方法论修正（已写入 `ads.ts` / `ads-css.ts` 注释）：

- **布局测量必须排除 `.load-more-anchor`**：它被补偿规则顶到 `top:-9999px`，
  按几何算行会得出上万像素的**假空洞**（曾据此误判"排版错位"）
- **A/B 脚本的 style id 变化会导致假绿**：脚本用已不存在的 id 移除样式，取不到就静默跳过，
  两态测的是同一状态、差值恒 0 —— **A/B 验证必须自检"两态确实不同"**

## 一句话

**改响应体要逐字段授权，改页面样式只要划清站点边界。** 这两把尺子必须分开，否则越权就没判据了。
