## 背景

### 一、"删除"路线的代价是我们自己量出来的

ADR 0038 选的是"把 PCDN 候选从 `backup_url` 里删掉"。代价在 `poc/probe/pcdn-diag/REPORT-remaining.md`
里有数：

| 指标 | 实测值 |
| --- | --- |
| 2160p 轨剔除 PCDN 后 `official=0` 的 | **0 / 24**（所以边界 5 没触发，开关在 4K 上"有效"） |
| 剔除后**只剩 1 条**官方候选的 | **15 / 24（62.5%）** —— 没有备份可切 |
| backup 是否真在救场 | 毒化对照：两条 PCDN 全 `ERR_TIMED_OUT`，靠 `backupUrl` 回落仍流畅播完（计划 F1） |

也就是说：删路线**用一个确定的代价（备份从 3 条掉到 1 条）换一个未证实的收益**——
严格 A/B 至今零有效样本（见 ADR 0038「价值判断」节），"起播快 X 秒"没有数据支撑。

### 二、换 host 的技术前提已经验证过（不是拍脑袋）

| 事实 | 证据 |
| --- | --- |
| B站 CDN 的 `upsig` / `uparams` **不绑 host** | 计划 F6：把 upos host 套原 base 的签名参数，换 host 仍 206 |
| 换 host 实测命中率 | 匿名 720p、1 个视频，**27/27**：25 条直接换官方镜像返回 206；2 条 `*.mcdn.bilivideo.cn`（path `/v1/resource/upgcxcode/`）换 host 403，改 `proxy-tf-all-ws.bilivideo.com?url=<编码后的原地址>` 包装后 206 |
| 两个生产项目都在用 | bdFun 给 19 个写死镜像、`rewrite()` 只换 host（path/query 不动）；BiliPai 对 `/upgcxcode/` 的 mcdn 也换 host、TF 类走 proxy 包装 |
| 规则清单同源 | BiliPai 的 `risky` 后缀（mcdn/pcdn/gotcha + szbdyd/mountaintoys/qrstuvwxyzab/zhenidc）与我们 `classify.ts` 的 `PCDN_LABELS` + `PCDN_DOMAINS` **完全一致** —— 名单不用补 |

**两个独立 Kotlin 项目 + 我们自己的 27/27 → 同一结论**：这批官方镜像同路径可互换。

### 三、换 host 同时拿到"零 PCDN"与"满额备份"

| 指标 | 现在（删） | 换 authority |
| --- | --- | --- |
| 4K 轨候选数 | 15/24 条从 3 掉到 1 | **不变（仍 3 条）** |
| 实际 PCDN 流量 | 0 | 0（URL 已不指向 PCDN） |
| 弱网退路 | 没了 | **保留** |
| 会否造新地址 | 不会 | 会 —— **本 ADR 显式授权**（仅 authority，及 mcdn 的 proxy 包装） |

关键：这两件事在"删"的方案里互斥，在"换"的方案里同时成立。
而且失败是**响亮**的：换错 host → 403 + 320 字节错误页，不会静默降级成"能播但还在走 PCDN"，
排查时能直接看见。

### 四、这是"主动放弃过的选项"，现在收回

换 host 在方案 §2 曾被否决（"技术上可以，本方案主动不做"），写进 ADR 0038 边界 2。
当时是为了守住"不造地址"的洁癖。现在用户明确推翻该约束 —— **本 ADR 就是那次推翻的授权载体**。

## 决定

**授权第五类响应体改写的第二种形态：把 PCDN 候选的 authority 换成官方镜像，取代"删除"。**

对每一条轨的候选 `[base, ...backups]`：

1. 逐条分类（**必须传 `search`**，理由同 ADR 0038 / `classify.ts`）；
2. **PCDN 候选** → 换 authority 到官方镜像：
   `new URL(url)` 后只改 `protocol` / `host` / `port`，**`pathname` / `search` / `hash` 一字不动**；
   若该 URL 命中 mcdn 的 `/v1/resource/upgcxcode/` 变体（换 host 实测 403 那一类），
   改为 `proxy-tf-all-ws.bilivideo.com?url=<encodeURIComponent(原 URL)>` 包装（**唯一允许改变 URL 结构的例外**）；
3. **官方 / third-party / unknown 候选** → 原样保留，不换、不排、不删；
4. **候选条数严格不变**：换失败（解析异常、清单缺项、无映射）的那条**原样保留**；
5. 其余字段（`quality` / `support_formats` / 轨数 / `height` / `codecid` / 带宽 …）**一字不动**。

### 八条硬边界（缺一条就超出本授权）

| # | 边界 | 为什么 |
| --- | --- | --- |
| 1 | **只改 authority**（`protocol`/`host`/`port`）；`pathname`/`search`/`hash` 一字不动 | 换 host 成立的全部前提就是同路径可互换；动路径等于编数据 |
| 2 | **不新增、不删候选**：输出条数 **严格等于** 输入条数 | 这是本方案相对"删"的核心收益（备份全留）；破了这个就等于退回删路线 |
| 3 | `quality` / `support_formats` / `accept_quality` / 轨数量 / `height` / `codecid` / 带宽字段**一字不动** | 继承 ADR 0038 边界 3：用户能选什么画质由服务端决定 |
| 4 | **不得伪造任何权益**（会员/画质/`is_preview`/`play_check`/`user_status`） | 继承 ADR 0038 边界 4；本 ADR 只动线路，不碰身份 |
| 5 | **换不了的候选原样保留**，`new URL()` 抛错的一律保留 | 判不了就别动 —— 静默失败可以接受，制造坏 URL 不行 |
| 6 | **镜像清单与 proxy 模板经 `cfg` 下发**，不在主世界写死 host | 与 ADR 0038 的 `pcdnRules` 同机制：镜像域名漂移时不必发版 |
| 7 | **mcdn proxy 包装仅限 `/v1/resource/upgcxcode/` 变体**，且只对 PCDN 候选 | 这是唯一改变 URL 结构的例外，扩大会变成"任意 URL 重写" |
| 8 | **不并发批量试探镜像**，控制请求规模 | 批量构造官方地址对 B站 基础设施有真实成本（见风险节） |

#### 边界澄清：候选容器不止 `dash.video` / `dash.audio`（2026-11-18 补记）

这不是新授权，是把上文既有授权**说全**。上表 1/2 条说的"候选"指的是 `dash` 里**所有**
带候选地址的容器，共四处，规则完全相同：

| 容器 | 形状 | 依据 |
| --- | --- | --- |
| `dash.video[]` | track 数组 | playurl 常规视频轨 |
| `dash.audio[]` | track 数组 | playurl 常规音频轨 |
| `dash.flac.audio` | **单个** track 对象（外层 `dash.flac.display` 是布尔） | `src/core/playinfo/parse.ts` 的 `parseDash()`：`isRecord(flacObj?.audio)` |
| `dash.dolby.audio[]` | track 数组（外层 `dash.dolby.vision` 是布尔） | 同一处：`arr(dolbyObj?.audio)` |

- 四者**同规则**：条数严格不变、只换 authority、`pathname`/`search`/`hash` 一字不动。
- `dash.flac.display` / `dash.dolby.vision` / `dash.duration` 属于**非候选字段**，
  一字不动（与本 ADR 边界 3 同源）。
- 形状不对（缺失 / `null` / 非对象 / `flac.audio` 不是对象 / `dolby.audio` 不是数组）
  → 该容器整块跳过，**不抛错**（边界 5 的同一口径）。

**为什么必须写明这一条**：实现（`src/content/main-world.js` 的 `filterDashOf()`）在
2026-11-18 之前只遍历 `dash.video` / `dash.audio`，而 Hi-Res（flac）与杜比全景声（dolby）
这两类音轨的 PCDN 候选**完全没被过滤** —— 那几轨照旧走 PCDN，开关却是开着的、
界面一切正常。这正是本 ADR 与 `src/core/cdn/classify.ts` 共同点名的
**最坏失败方向（静默失败）**。当时没测到，是因为探针样本
（`poc/probe/pcdn-diag/remaining-candidates.json` 的 8 个 UGC 视频）里
`flac` / `dolby` 全是 `null`，样本没覆盖到这一块 —— 属"样本太窄"这条风险的
第二个实例（第一个实例见上文风险表首行）。

### 与 ADR 0038 的关系（升级，不是推翻全部）

| ADR 0038 条款 | 本 ADR 的处理 |
| --- | --- |
| 边界 1（删除或重排候选） | **替换**：改为"替换 authority"，不再删除 |

## 风险（必须写清，上线前逐条处理）

| 风险 | 现状 | 处置 |
| --- | --- | --- |
| **样本太窄** | 27/27 是 **1 个视频、匿名 720p** | ⚠️ **上线前必须补 8 个视频 × 24 条 4K 轨的命中率验证**（见"验证门"）。只验"2160p 路径在镜像上同样通"，不验收益 |
| **proxy 多一跳的代价** | ✅ **已量化，四轮实测，2026-11-19 结案**：TTFB 波动极大（同一批候选先后测出 949 / 220 / 297 ms），**不是稳定属性**。可靠口径是吞吐 + 长窗口观察：36 对 2 MiB 配对 proxy 中位 **7.78** vs 直连 5.27 MB/s；16 MiB 长窗口 8 对 —— proxy **8/8 全程不掉速**（稳态中位 55.55、末/首 1.68–6.25），直连 **4/8 掉速**（`mirrorbd` 掉到 0.94/1.37 MB/s，末/首 0.08–0.09） | **维持现状（不改为"直连失败才用 proxy"）**。理由见下方「proxy 代价的结案」：①先直连必吃一次确定性 403（18/18），再多付 proxy 一跳；②proxy 两档窗口下都不劣化，而**直连会中途限速** |
| **官方镜像可能中途限速** | ⚠️ **新发现（16 MiB 长窗口）**：`mirrorbd` 直连给完首段突发后掉到 **0.94 MB/s 并持续**，撑不起任何 4K 轨。`mirrorcoso1` 则是**慢启动**（首桶 1.6 s，随后 5–9 MB/s）而非持续限速 | **本轮不做镜像筛选**（边界 8 禁止逐 host 试探，做筛选需另立 ADR）。当前默认镜像是 `mirrorhw`，**尚未观测到限速**。此项只作为**将来改默认镜像时的强制前置检查**记录在案。n=8 单轮单机，未复现验证 |
| **镜像缺该 segment → 403** | 未观测到，但理论上可能 | 本方案**不删候选**，其他候选天然兜底 —— 比"删到只剩 1 条"安全得多。先用真实数据看 403 出现率，不预防性加复杂逻辑 |
| **批量构造官方地址有基础设施成本** | 换 host 会把 PCDN 候选的流量打到官方镜像 | 不无节制并发试探；不为选镜像做逐 host 探测（明确不抄 bdFun 的 1 MiB 测速） |
| **"屏蔽 PCDN"文案的真实性** | 删路线下"删了候选但播放器可能从别处拿到 PCDN"，文案有水分 | 换 authority 后流量确实不走 PCDN，文案**变成字面真实**；但收益类话术仍受 ADR 0038「价值判断」约束，不承诺秒数 |

## proxy 代价的结案（2026-11-19，三轮实测后回填）

本节**只记录已测到的事实与由此得出的边界**，不新增授权。原始数据：
`poc/probe/pcdn-diag/proxy-throughput.json`（gitignored，含签名 URL）、
`poc/probe/pcdn-diag/REPORT-v1-path-on-official.md`。

### 一、路径问题已彻底排除，规则 B 必须保留

`/v1/resource/upgcxcode/…` 这个 path 形态**在所有官方 host 上都不被接受**：

| 组 | 做法 | 结果 |
| --- | --- | --- |
| Q1 | 原 `/v1` path × 4 种官方 host（`mirrorhw` / `mirrorcoso1` / `estgoss` / **同轨 peerHost 原值**） | **0/24 = 206** |
| W1 | **同 host、同一份已验证 206 的签名**，只把 path 加上 `/v1/resource` | **0/6 = 403** |
| W2 | 同 host、同签名、原 `/upgcxcode/` path（自检） | **6/6 = 206** |

W1/W2 是决定性对照：同 host、同签名、同对象，**只差路径前缀**。⇒ 403 由**路径**造成，
与签名有效期、host 选择、对象是否存在都无关。**边界 7 的 proxy 例外是唯一通路，不许删。**

### 二、TTFB 不是可靠口径 —— 这是本轮最重要的方法论结论

同一批候选，三轮测出三种中位数：

| 轮次 | 时间 | n | proxy TTFB 中位 | 分布特征 |
| --- | --- | ---: | ---: | --- |
| 第一轮 | 11-17 深夜 | 18 | **949 ms** | 8 条 ≤478 ms、10 条 ≥915 ms，**478–915 之间零样本** |
| 第二轮 | 11-18 傍晚 | 45 | **220 ms** | 全部 ≤474 ms，≥800 ms **0 条** |
| 第三轮（本轮） | 11-19 凌晨 | 36 | **297 ms** | p90 447 ms |

第一轮那条空档证明它**不是连续分布而是两档**（疑似边缘节点缓存命中与否）。
所以：**「proxy 固定慢 X 倍」不成立**，任何引用单一中位数的倍数结论都必须撤回。
第三轮 C 组（2 个全新对象、同一 URL 连打 5 次）呈同样两档：首次 384/278 ms → 后续稳定 88/58 ms。

> ⚠️ **禁止在任何文档、文案、commit message 里写"proxy 慢 N 倍"或"proxy 快 N 倍"。**
> 要引用就引吞吐，并注明 n 与轮次。

### 三、吞吐才是可靠口径，且 proxy 不劣于直连

36 对配对（同一对象：proxy 包装 vs 同轨官方候选直连，各下 2 MiB，交替顺序 × 3 轮）：

| 指标 | proxy | 直连官方 |
| --- | ---: | ---: |
| 吞吐中位 | **7.78 MB/s** | 5.27 MB/s |
| 吞吐 p10 | 3.57 | 0.60 |
| **stall（>2s 无数据）** | **0 / 36** | **0 / 36** |
| 满足轨码率 1.5 倍余量 | **36 / 36** | 32 / 36 |

逐对比值（proxy/direct）中位 **2.05**，proxy 更快 26/36。

**但整体数字被一个慢镜像带偏，按 host 拆开才看得清：**

| 直连用的镜像 | n | proxy | 直连 | 谁快 |
| --- | ---: | ---: | ---: | --- |
| `mirrorcoso1` | 12 | 6.87 | **1.21** | proxy **快 5.7 倍** |
| `estgoss` | 12 | 5.84 | 7.95 | 直连快（proxy 0.73×） |
| `mirrorbd` | 6 | 15.38 | **27.59** | 直连快（proxy 0.56×） |
| `mirrorhw` / `mirrorhwo1` | 6 | 36.7 / 47.0 | 27.3 / 28.1 | proxy 略快 |

⇒ **2 MiB 窗口下，慢的是 `mirrorcoso1` 这个官方镜像自己**（直连 0.5–1.2 MB/s）。
`mirrorbd` 上 proxy 确实只有直连的 0.56 倍，但 15.4 MB/s 仍远超 4K 所需。

> ⚠️ **但 2 MiB 窗口不够长 —— 下面 §三之二 的 16 MiB 复测把上表的重心改了。**
> 读本节结论前必须先读 §三之二：`mirrorcoso1` 的"慢"其实是**慢启动**（首桶 1.24 MB/s，
> 1.6 s 后恢复到 8–15 MB/s），而真正会卡的是**直连在给完首段突发后限速**（4/8 掉到约 1 MB/s）。

### 三之二、16 MiB 长窗口复测：2 MiB 只测到了突发段（关键限定）

**为什么要补这一测**：23.21 Mbps 的轨，2 MiB 只够播 **0.7 秒**。CDN 的典型行为是
「先给一段高速突发把你喂饱，之后降到目标速率」—— 若拐点落在 2 MiB 之后，
上一测**恰好把突发段全部测到、把限速段全部漏掉**。
探针：`poc/probe/pcdn-diag/measure-long-window.mjs`（16 MiB，按 2 MiB 分 8 桶），
输出 `long-window.json` / `long-window-coso1.json` / `long-window-fast.json`（均 gitignored）。

**8 对（4 个慢镜像组 + 4 个正常镜像组）的结果，按"稳态"（去首桶后的中位）看：**

| 对象 | 路径 | 首桶 | **稳态** | 轨需要 | 末/首 |
| --- | --- | ---: | ---: | ---: | ---: |
| BV1NDsS6UE8D#t0 | proxy | 5.61 | **10.50** | 2.11 | 1.97 |

**三条由此改写/加强的结论：**

1. **「慢镜像」的性质改了**：`mirrorcoso1` 直连在 16 MiB 下稳态 **5.0–9.1 MB/s**（不是 2 MiB 测出的 1.2）。
   它的真实形态是**慢启动**：首桶 1.24 MB/s、耗时 1.6 s，之后恢复。**2 MiB 把慢启动误读成了持续限速。**
2. **真正会卡的是「直连限速」，而且它出现在 4/8 样本里**：`mirrorbd` 直连给完首段
   （11.8 / 18.2 MB/s）后**掉到 0.94 / 1.37 MB/s 并一直保持**（末/首 0.09 / 0.08）。
   proxy 在同一对象上是 15.97 / 56.62 MB/s。**这一条对「规则 A 只换 host 到官方镜像」是坏消息**：
   换到会限速的官方镜像上，比留在 proxy 更糟。
3. **proxy 全程没有掉速**：8 次里 `末/首` 全部 > 1（1.68–6.25），稳态中位 **55.55 MB/s**；
   直连稳态中位 **7.06 MB/s**，且有 4 次 `末/首` < 0.3。**proxy 不限速这件事，在两档窗口下都成立。**

**必须写明的局限（不然又会犯"2 MiB"那一轮的错）**：
- n=8 对，**单机、单时段**（2026-11-19 01:36–01:39 +0800），不能当普遍规律；
- 每轮只测 1 次，没有重复验证 `mirrorbd` 的限速是否稳定复现（这是下一步该做的，不是已证实的）；
- 16 MiB 仍未覆盖整集（一集 4K 通常 1–3 GB），**超长时段的行为仍未知**；
- 直连与 proxy 是**同一对象的两条不同路径**，符合对照要求；但两者的连接数/协议可能不同，
  这不是纯"代理 vs 直连"的物理实验。

### 四、由此得出的四条边界（本轮不新增授权，只是把话说死）

1. **不改 proxy 策略。** ADR 0039 风险表里预留的"直连失败才用 proxy"**经实测否决**：
   该类候选直连是**确定性 403**（18/18，中位 9 ms），先直连只会多付一次失败请求，
   再照样付 proxy 一跳，**比现状更慢**。
2. **不把 proxy 候选挪到 backup 位。** 曾被考虑为"消掉首块慢"的方案，本次否决：
   ①`/v1` 候选与同轨官方候选是**两份独立签名**（`uparams` 字段集 27–30 vs 25，
   前者含 `mcdnid`/`cdnid`），挪位会让首选位变成与用户实际候选不同源的地址；
   ②它改动候选顺序，超出边界 2「不新增、不删候选」的字面授权，需另立 ADR；
   ③而 16 MiB 数据显示**proxy 全程不掉速、直连反而会掉**，代价方向与当初假设相反。
3. **文案不许写"慢"。** 见 §二 的警告框：TTFB 波动是两档、幅度不定，
   写"变慢"既可能夸大也可能低估。开关描述改为只讲事实（换成官方线路），
   开发视角的代理细节留给诊断面板。
4. **镜像选择不能只看"通不通"，要看"会不会中途限速"。** （新增，来自 §三之二）
   `mirrorbd` 直连稳态 0.94 MB/s 是已经观测到的实例。**但本轮不做任何镜像筛选**：
   ①ADR 0039 边界 8 明确不许逐 host 试探，做筛选要另立 ADR 并评估流量成本；
   ②现状（规则 A 换到 `mirrorhw`）尚未观测到限速，样本里最差的是 `mirrorbd`，
   而它当前不是默认镜像（`DEFAULT_REWRITE_RULES.mirrorHost = 'upos-sz-mirrorhw.bilivideo.com'`）。
   这条只作为**将来改默认镜像时的前置检查项**记录在案。
