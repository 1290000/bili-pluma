# 0013. 允许改写播放器信息接口的响应体（Q12 的例外）

日期：2026-10-25
状态：已采纳（**对 [Q12](../03-open-questions.md)「不做伪装会员标识」的例外授权**）

## 背景

[Q12](../03-open-questions.md) 定的是：**不做伪装会员标识，连开关都不放**。
理由是收益小（只是界面顺眼）、有风控风险、有伦理问题（用户误以为自己有会员）。

但 P1 实装后，`src/content/main-world.js` 实际做的事比 Q12 的字面范围大：

| 做法 | 状态 |
| --- | --- |
| 改 `window.__INITIAL_STATE__.user.vipStatus` / `vipType` | ADR 0010 已授权（"只改本地显示状态"） |
| 改 `window.__INITIAL_STATE__.svip` 相关字段 | 同上 |
| **改写 `/x/player/wbi/v2` 与 `/x/player/v2` 响应体里的 `vip.status` / `vip.type` / `vip.due_date`** | ⚠️ **本 ADR 授权** |

实测记录（`docs/01-architecture.md` §9 P1 表格）：不改响应体时，**用户在播放器里切画质会被弹「开通大会员」，请求根本不发出去**。

## 决策

**允许改写 `/x/player/wbi/v2`、`/x/player/v2`、`/x/web-interface/nav` 这三个接口响应体里的会员字段。
除此之外的一切伪造都在禁止范围内。**

授权范围精确到字段与方法，不做含糊表述：

```
允许改写的接口：  /x/player/wbi/v2、/x/player/v2、/x/web-interface/nav
                （仅 https、仅 api.bilibili.com）
允许改写的字段：  vip.status、vip.type、vip.due_date
                vipStatus、vipType（同源字段）
禁止改写的字段：  mid、rights（权限位）、以及任何身份归属相关字段
```

> `/x/web-interface/nav` 于 2026-10-26 追加授权，理由与边界见文末「补充授权」一节。

`mid` 与 `rights` 被显式排除，因为它们决定**身份归属**与**实际权益判定**——改了会让诊断失真，
且违反「宁可少代理，不可错代理」这条原则（见 `src/core/identity/router.ts`）。

## 为什么这是例外而不是翻案

**Q12 仍然成立**，一个字没改。它约束的是「界面上的会员标识」（头像旁的大会员图标、等级标签等），
本 ADR 授权的是「播放器判断"能不能去请求高清"这一层的内部状态」。

两者动机完全不同：

| | Q12 禁止的事 | 本 ADR 授权的事 |
| --- | --- | --- |
| 目的 | 让界面看起来是会员 | 让播放器**愿意发出**取流请求 |
| 效果 | 用户误以为自己有会员 | 用户拿到真实的高清流 |
| 不改会怎样 | 界面难看一点 | **功能完全不工作** |

**关键区别：改写后能否拿到 4K 仍取决于服务端。** 播放账号不是真会员的话，
DNR 换完 Cookie 服务端照样返回低画质——这条链路不会因为本地状态被改就成了"假会员"。

## 被放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 不改响应体，只在画质菜单弹出时提示 | 用户每切一次画质弹一次框，等于功能不可用 |
| 改 `rights` 权限位 | 越界。这是实际权益判定字段，改了可能引出未定义行为 |
| 让 DNR 改响应体 | DNR 只能改请求头，改不了响应体（Web 平台能力边界） |
| 由 background 代理这两个接口 | 播放器读的是页面自己发的 XHR，转给 background 要桥接 Promise，复杂度高且更脆 |

## 后果

- **必须在根 `README.md` 诚实描述**：本扩展会修改播放器用于判断会员状态的本地响应，
  以便让画质切换不被拦截；**不改变账号在服务端的真实权益**。
- Q12 的表格补一句「例外见 ADR 0013」，但 Q12 的结论本身不变。
- `src/content/main-world.js` 的 `PATCH_PATHS` 常量是这条授权的**唯一落地点**，
  加任何新路径都必须回来更新本 ADR。
- 若将来 B 站改成在别的接口里给会员状态，本 ADR 需要重新评估，**不要顺手扩 `PATCH_PATHS`**。

## 补充授权：`/x/web-interface/nav`（2026-10-26）

### 为什么追加

`src/content/main-world.js` 的 `PATCH_PATHS` 实际是三个路径，比本文原授权多一个 `nav`。
按本文「加任何新路径都必须回来更新本 ADR」的要求，这里补授权，**不是**默许既有代码。

追加的事实依据（来自实装后的用户反馈，不是推测）：

- `nav` 是**账号信息接口**，返回 `vipStatus` / `vipType`，播放器与 B站前端其它模块都读它判断当前身份有没有会员权限
- 只改 `/x/player/wbi/v2` 时，用户在播放器里**切高清 / 开 Hi-Res 会弹充值页**——因为 `nav` 那一路仍然回答"你不是会员"
- 补上 `nav` 之后该现象消失

### 边界没有放宽

| 项 | 状态 |
| --- | --- |
| 允许改写的字段 | 仍是 `vip.status` / `vip.type` / `vip.due_date` / `vipStatus` / `vipType` |
| `mid` | **仍禁止**。`nav` 的 `data.mid` 是身份归属的核心字段，改它会污染诊断、也会让"点赞归主账号"这条验收失去意义 |
| `rights` / 权限位 | **仍禁止** |
| 改写范围 | 仍是 `patchVipScoped()` 的递归白名单，不是整份响应替换 |
| 开关 | 仍随总开关关闭即停（`patchResponseText` 第一行 `if (!enabled ...) return text`） |

### 仍然是"例外"而不是"翻案"

Q12 一个字没改：**界面上的会员标识不做伪装**。`nav` 属于"播放器判断能不能去请求高清"这一层，
和"让头像旁边显示大会员"是两件事。改写后能否真的拿到 4K，仍取决于服务端对播放账号的真实响应。
