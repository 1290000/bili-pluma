# 0010. 登录播放账号会覆盖主账号登录态（阻塞性问题）

日期：2026-10-25
状态：**已被 [ADR 0012](./0012-isolated-window-login.md) 解决**

> 本文记录问题本身与排查过程。**最终方案见 [ADR 0012](./0012-isolated-window-login.md)：隔离窗口登录。**

## 现象

实测（`poc/verify/verify-cookie-overwrite.cjs`，全新 profile）：

```
① 登录主账号（普通用户）
   dedeUserId = {{primary_mid}}      navMid = {{primary_mid}}      vip = 0

② 用扩展扫码登录播放账号（大会员）
   dedeUserId = {{playback_mid}}   navMid = {{playback_mid}}   vip = 1

cookieOverwritten: true
```

**浏览器的登录态被完全替换。** 不是"共存"，是覆盖。

## 为什么

扫码登录流程的最后一步是跳转 `passport.biligame.com/x/passport-login/web/crossDomain`，
服务端通过 `Set-Cookie` 下发 `SESSDATA` / `DedeUserID` / `bili_jct`。
**Cookie 是按域名唯一的**——同一个 `www.bilibili.com` 上只能有一套。

所以"把播放账号的凭据存进 vault"这件事，在实现上等于"把浏览器的登录态换成播放账号"。

## 与既有决策的冲突

| 决策 | 原文 | 现状 |
| --- | --- | --- |
| [ADR 0004](./0004-request-level-identity-proxy.md) | 浏览器全程 A，只对取流接口换 B 的凭据 | **前提不成立**：登录 B 的那一刻浏览器就变成 B |
| `AGENTS.md` §2 第 2 条 | "请求级代理，不切 cookie" | 同上 |
| `README.md` 首屏 | "浏览器全程保持主账号登录" | **当前实现下不成立** |

## 影响面

**这不是实现 bug，是方案设计的缺口。** 之前所有"验证通过"的结论都失效：

| 结论 | 实际 |
| --- | --- |
| 页面播放 4K | 浏览器本来就是大会员，不装扩展也能播 |
| DNR 换 Cookie 生效 | 注入的和浏览器自带的是同一套凭据 |
| 双账号代理有效 | 从未在双账号场景验证过 |

`poc/verify/result-page-e2e.json`、`result-dual-account.json` 的结论均需作废重做。

## 候选方案

### 方案 A：无痕窗口登录，取完凭据即关

用 `chrome.windows.create({ incognito: true })` 开无痕窗口，在其中登录播放账号，
登录成功后读 cookie 存入 vault，**然后关闭无痕窗口**（cookie 随窗口销毁）。

| 优点 | 缺点 |
| --- | --- |
| 主账号登录态完全不受影响 | 需要 `incognito` 权限（用户可能拒绝） |
| 符合"请求级代理"原意 | 部分浏览器/企业策略禁用无痕 |
| | 需要额外处理：无痕窗口里能否装扩展 |

**这是最贴合 ADR 0004 原意的方案，需要优先验证可行性。**

### 方案 B：让用户从别的浏览器手动导入凭据

用户在另一个浏览器（或手机）登录播放账号，导出 `SESSDATA`，
粘贴到扩展的设置页。

| 优点 | 缺点 |
| --- | --- |
| 技术最简单，无需权限 | **用户体验差**：要手动复制 cookie，容易出错 |
| 主账号零影响 | 普通用户不会用 |

### 方案 C：接受"浏览器是播放账号"，改做账号切换器

放弃"全程主账号"，改成**一键切换当前浏览器身份**：
主账号用来浏览/点赞，切到播放账号看视频。

| 优点 | 缺点 |
| --- | --- |
| 技术上最简单，无需任何取流代理 | **不是原方案**：点赞/评论/历史会归播放账号 |
| 体验直观 | 需要重写 README 定位与大面积文档 |

### 方案 D：分浏览器（主账号 Edge / 播放账号 Chrome）

明确要求用户**在两个浏览器分别登录**，扩展只装在主账号那个，凭据通过文件或剪贴板传递。

| 优点 | 缺点 |
| --- | --- |
| 技术上最干净，零覆盖风险 | 强依赖用户遵守约定；跨浏览器传凭据仍要手动 |

## 决策所需的信息

1. **扩展能否在无痕窗口里运行**（`incognito: "split"` 或 `"spanning"`）——决定方案 A 是否成立
2. 无痕窗口里的 `Set-Cookie` 是否只影响该窗口——预期是，但需实测
3. 用户是否接受方案 B/C 的操作成本

**下一步：先验证方案 A 的可行性（无痕窗口 + 扩展）。** 若不成立，则在 B/C/D 中选。
