# ADR 0001. 采用纯 MV3 扩展，不做桌面端

日期：2026-10-24
状态：已采纳
取代：v0.1 的三进程方案

## 背景

最初（v0.1）设计了「浏览器扩展 + Rust Core 常驻进程 + Flutter GUI」三进程架构，理由是"扩展拿不到高画质，必须由本地服务持副账号身份独立取流"。

## 决策

**v1 只做纯 MV3 浏览器扩展**（Chrome + Edge）。桌面端降级为 v2 可选增强项。

## 理由

1. **核心能力在 JS 层就能完成**。Dual Account Helper 已证明：Hook `fetch`/XHR + 请求级换 Cookie 头，就能让播放器拿到高画质流。整个过程不需要独立进程。
2. **三进程带来的成本是真实且持续的**：两套语言、FFI 绑定、安装包签名、自动更新、跨进程协议。而它换来的能力（跨设备同步、批量下载）在 v1 阶段并不需要。
3. **凭据安全可以通过其他手段补**（扩展存储 + AES-GCM），不必为了 DPAPI 引入整个桌面端。
4. **维护成本与项目预期寿命不匹配**（见 ADR 0003 的后果说明：本类项目可能因律师函短期关停）。

## 被放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 三进程（扩展 + Rust Core + Flutter） | 过度设计，v1 成本翻倍 |
| 油猴脚本 | 受脚本管理器限制，无法做凭据加密存储，且用户需装 Tampermonkey |
| 纯扩展 + `chrome.debugger` 改响应体 | 会弹"正在调试"提示条，商店政策受限 |

## 后果

**收益**：
- v1 开发周期从 8–10 周压缩到 4–5 周
- 用户安装只需"装扩展"一步，无需安装软件
- 没有端口、配对、进程保活等一系列可失效点

**代价**：
- 凭据只能存在 `chrome.storage.local`，安全强度低于 Windows DPAPI（缓解：可选"启动时解锁"）
- 无法做跨设备凭据同步（缓解：扫码一次 + 长期保活，让同步变得不必要）
- 无法做长时间后台任务（SW 30 秒休眠；v1 不需要）
