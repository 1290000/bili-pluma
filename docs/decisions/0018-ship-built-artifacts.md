# 0018. 分发构建产物（放宽「只发源码」红线）

日期：2026-10-27
状态：已采纳（对决策 8 的修订）；**2026-11-17 再次修订：不再发 `-with-source.zip`**

## 背景

v1 六条验收通过后，用户提出：希望用户能**直接下载扩展包并加载**，而不是每个人都得装 Node、跑 `pnpm build`。

这条诉求与决策 8 直接冲突。决策 8 原文：

> **只发源码**，不上架商店、不发预编译包

理由是（见 [Q16](../03-open-questions.md) 与 [Q13](../03-open-questions.md) 背景）降低「提供可用侵权工具」的观感，减小暴露面。

**用户决定要做。** 本 ADR 记录「怎么做才把代价压到最低」，不再讨论「要不要做」。

## 决策

改为：**不上架商店；不发 crx；可以发 zip（单个附件），源码由 Release 页自带的
`Source code` 归档提供。**（2026-11-17 修订，理由见文末）

精确边界：

```
允许发布：  pluma-<版本>.zip              构建产物，解压后可在开发者模式加载
                                        （源码不在包里，见 Release 页的 Source code 归档）
禁止发布：  crx（任何来源自签的一律装不上，且观感是"已签名安装包"）
            任何形式的网盘 / 第三方镜像主动分发
            上架 Chrome / Edge 商店
必须保持：  README 以**源码构建**为主路径，zip 是退路而非主推
```

权威位置分工：

| 内容 | 权威位置 |
| --- | --- |
| 为什么这样分发、边界在哪 | 本 ADR |
| 文件名格式、zip 内结构、发布步骤 | [guides/releasing.md](../guides/releasing.md) |
| Release 说明的语气与结构 | [guides/release-notes-template.md](../guides/release-notes-template.md) |

## 为什么当初要求同时发带源码版（已于 2026-11-17 取消）

> 以下为**当时的理由**，结论见文末「2026-11-17 修订」。保留它们是因为
> 「为什么这条约束曾经重要」比「它现在没了」更值得记 —— 否则下一个人会以为
> 当初只是随手加的。

这一条是那次修订的**核心约束**，不是补充说明。

只有「构建产物」时，它在用户眼里就是一堆 js —— 和任何一个来路不明的扩展没有区别。加上源码，能让第三方**独立重建并比对**。区别不在体积（约 216 KB → 约 1.5 MB），在于**可验证性**。

⚠️ **诚实说明它的局限**：带源码**不能**让产物变合规或更安全。它只是让「这是在做什么」对任何人可见。**不要把它当免责手段用** —— 它是自我约束，也是证据。

## 为什么明确禁止 crx

技术上就装不上：浏览器只认商店签名的 crx，自己生成的会被拒绝安装。既然装不上，发出去只会制造「下载了不能用」的投诉，还平白留下「我发了安装包」的痕迹。

## 被放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 只发源码（维持原决策） | 用户明确要求降低使用门槛；且参考实现里也有直接给产物的做法 |
| 发 crx | 浏览器拒绝非商店签名，用户装不上 |
| 发 exe 安装包 | 要写注册表 + 改浏览器策略，会被杀软报毒。**观感比发 zip 恶劣得多** |
| 让用户把 zip 直接拖进浏览器 | 浏览器没有这个入口。「加载解压缩的扩展」只接受**目录** |

## 后果

- `AGENTS.md` 决策 8 改为「不上架商店；分发方式见本 ADR」—— 决策表只留指针，细节归这里
- `docs/03-open-questions.md` Q16 的「分发决策」表同步改写
- `README.md` 安装章节提供两条路径：**下载现成产物在前，源码构建在后**
  （2026-10-27 调整 —— 最初按「源码构建在前」写，后确认绝大多数用户不会构建，
  让 95% 的人去读 5% 的人才需要的说明是错配。ADR 这条决定本身没变，变的是呈现顺序）
- 新增 `scripts/package.mjs`，命名与结构由 `releasing.md` 定义
- Release 说明必须包含「未经商店签名，仅供学习交流」这句

| 项 | 状态 |

| 不上架商店 | **不变** |
| 不做中文 SEO / 不主动推广 | **不变** |

## 2026-11-17 修订：取消 `-with-source.zip`

**改了什么**：Release 只带一个附件 `pluma-<版本>.zip`。

**为什么「可验证性」没有因此消失**（这是本节的关键，别省）：
GitHub 每个 Release 页**自带 `Source code (zip / tar.gz)` 归档** —— 那是仓库在
该 tag 的完整快照，任何人都能 `pnpm install && pnpm build` 重建并逐字节比对。
`-with-source.zip` 的额外价值只是「产物与源码在同一个包里」，不是「源码的唯一来源」。
它体积是轻量版的 7 倍（约 360 KB → 4.5 MB），换来的便利与代价不相称。

**代价，写在明处**：
`BUILD.md`（构建凭证：commit / 工作区状态 / wxt 版本 / 产物逐文件 sha256）
**不再随包分发**。它仍由 `package.mjs` 生成在 `dist/BUILD.md`，供维护者核对，
但不作为附件上传 —— 也就是说**第三方失去了「一眼看到这个包由哪个 commit 构建」的入口**，
只能靠 tag 反查（tag 与 Release 同名，通常能对上）。

**没有改变的事**：不上架商店、不发 crx、不主动镜像分发的边界全部不变。
