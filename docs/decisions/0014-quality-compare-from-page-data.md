# ADR 0014. 画质对比只用"页面已经收到的数据"，且不承诺 HDR

日期：2026-10-26
状态：已采纳（P3 开工前置决策）
影响：[02-ui-spec.md](../02-ui-spec.md) §2.3 / §4.2、`core/playinfo/*`（P3 待建）、`public/main-world.js`

## 背景

P3 要做两处"画质对比"：

1. **popup §2.3**：`已解锁 [4K][1080P60][Hi-Res]` + 锚点小字 `主账号仅可用 1080P`
2. **options §4.2 体检表**：六行对比（清晰度 / 帧率 / HDR / 杜比视界 / Hi-Res / 杜比全景声）

02-ui-spec.md §4.2 原文要求「对当前 BV **分别**用两套身份调一次 playurl，对比 `dash` 各轨存在性」。

**这句话在当前架构下做不到。** 四条约束逐条成立：

| # | 约束 | 依据 |
| --- | --- | --- |
| 1 | 总开关打开后，**任何上下文**（含 background）向 `/x/player/wbi/playurl` 发请求，都会命中全局路径规则（ID 10000 段，priority 1，无 `tabIds`），Cookie 被换成播放账号 | `src/platform/http/dnr.ts` 的 `enableProxy()` / `buildPathRule()` |
| 2 | 用"主账号身份"发请求 = 必须读主账号 `SESSDATA`，而 `SESSDATA` 是 httpOnly，只能走 `chrome.cookies` | 决策 4 / Q7：扩展不管理、不读取主账号 |
| 3 | `accept_quality` 不能当判据 —— 未登录时它就返回含 8K 的完整数组 | Q9 实测、`poc/verify/RESULT.md` §四 |
| 4 | HDR 的四个可用信号**全部**被实测证伪 | `src/content/isolated/badge-content.ts` 的"HDR 徽章已移除"注释 |

第 1 条意味着"分别调两次"必然两次都是播放账号；第 2 条意味着唯一能绕开第 1 条的路被项目最核心的承诺堵死。

## 决策

### 1. 主账号的能力数据，只能来自"页面已经收到的数据"

B站服务端在渲染视频页 HTML 时，会**用主账号身份**生成 `window.__playinfo__` 并内嵌进 HTML。
主世界脚本本来就要在播放器读它之前把它藏起来（ADR 0010），所以这份数据**已经在手上**。

做法：藏之前先把它的 `dash` 解析成轨道摘要，随主世界的 `hello` 上报，按 `tabId` 存 `storage.session`。

**这样做的三个好处**：

- 不读任何主账号凭据 —— 数据是页面自己收到的，扩展只是"看了一眼"
- 不临时关规则 —— 没有竞态窗口，其他标签页不会掉回主账号画质
- 数据是**服务端真实响应**，不是推断，也不受 `accept_quality` 那类假数组影响

### 2. 对比表绑定"当前打开的页面"，不支持输入任意 BV 做双列对比

因为主账号那一列的唯一来源是"这一页的 SSR"。脱离页面就没有基线。
options 的体检页因此定位为**当前页体检**，不是"任意 BV 查询器"。

### 3. 体检表只保留能由 `dash` 轨道确定的行

| 行 | 判据 | 做不做 |
| --- | --- | --- |
| 最高清晰度 | `dash.video[].height` 最大值 | ✅ |
| 最高帧率 | `dash.video[].frame_rate` 最大值 | ✅ |
| Hi-Res | `dash.flac.audio` 存在 | ✅ |
| 杜比全景声 | `dash.dolby.audio[]` 非空 | ✅ |
| 杜比视界 | `dash.dolby.vision` 布尔，措辞必须是「本视频**提供**」 | ✅（措辞受限） |
| **HDR** | 无可靠判据 | ❌ **砍掉** |

砍 HDR 的理由不是省事：角标那边已经为它付过一次代价（先误报 8K SDR 为 HDR，再全部漏报），
最终结论是"漏报可接受，误报会让用户不再信任整个角标"。体检表如果保留一行猜出来的 HDR，
等于把刚拆掉的雷重新埋回去，而且埋在一个**更权威的位置**（"体检报告"）。

## 实现约束与验证门（2026-10-26 补，**✅ 已于当日验证通过**）

本决策的前提是"`__playinfo__` 是服务端用主账号身份 SSR 进 HTML 的"。
**这个前提在两份文档里说法不一致**：

| 出处 | 说法 |
| --- | --- |
| [ADR 0010](./0010-page-proxy-via-tab-ids.md) | B站把播放数据 SSR 进 HTML，播放器**直接读**这个变量、根本不发 playurl 请求，所以必须藏 |
| [`poc/verify/RESULT.md`](../../poc/verify/RESULT.md) §一.2 | 普通视频页的 `__playinfo__` 是**客户端请求后写入**的（不是 SSR）；加载完成后含 4320P，而 playurl 响应最高只有 2160P |

两者不能同时为真，也可能各自描述了一个阶段（SSR 给初值 → 播放器后续覆写）。

### ✅ 实测结论（2026-10-26 16:57，Edge，BV1jt421t7XH P1，真实双账号）

诊断页「当前页取流数据」四行：

```
主账号基线 · BV1jt421t7XH P1   SSR，可用 · 最高 1080p
播放账号（页面 playurl 响应）   最高 2160p · 19 条视频轨 · Hi-Res
对比结论                       提升 1080p · +30fps · +Hi-Res
主账号昵称（页面读取）          {{primary_name}}
```

**两条都成立，A 方案有效。** 同时这条实测裁决了上面的矛盾：

- **ADR 0010 是对的**：`document_start` 那一刻的 `__playinfo__` 确实是 SSR 的，且是**主账号身份**（1080p）
- **RESULT.md §一.2 也是对的，但它测的是另一份**：加载完成后 `__playinfo__` 被页面覆写成含 8K 的版本
- 所以两份文档不矛盾，是**同一个变量在两个时刻的两个值**。这也正是本决策坚持"只认第一份"的原因

### 风险：会静默谎报（保留作背景，已通过闸门）

如果页面上的 `__playinfo__` 是**客户端**写的那份，它来自页面自己发的 playurl ——
而那个请求已经被 DNR 换成了播放账号身份。拿它当"主账号基线"，
对比结果会**永远显示"主账号也有 4K"**，也就是"扩展没起作用"。

这种失败不会报错、不会崩溃，只会让功能看起来完全无效。**它比崩溃更糟。**

### 三条硬约束（已实现）

1. **只用 `document_start` 那一刻已经存在的值。** 主世界记 `firstSeen`（`initial` / `set` / `none`）
   与 `playurlBefore`（那次赋值前有没有发过 playurl），两者一起判可用性。
2. **必须验证它是主账号的。** 判据：SSR 基线的最高高度 **低于** playurl 响应的最高高度。
   ✅ 实测 1080p < 2160p，成立。
3. **拿不到就是未知。** UI 显示"主账号：未知"，不许用单边数据假装对比（同 `diffCapability` 的 `null` 语义）。

### 验证门的观测点（留给以后回归用）

`options.html#/diagnostics`（原独立自检页，2026-10-26 已并入）的「当前页取流数据」四行。
判据：`主账号基线` 行必须是 `SSR，可用` 且最高高度**低于**播放账号那行。
若出现 `⚠️ 客户端写入（播放账号身份）→ 不可用`，说明本决策的 A 方案失效，必须回到决策阶段重选。

## 被放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 在 options 里临时 `disableProxy()` → 发主账号请求 → 恢复 | 有竞态窗口；期间所有标签页掉回主账号画质；且违反「宁可少代理，不可错代理」 |
| 读主账号 `SESSDATA` 自己拼请求 | 直接违反决策 4 与 README 首屏的承诺（"扩展不碰主账号"） |
| 用 `accept_quality` 差值当对比 | 未登录时它就返回含 8K 的假数组，会得出"主账号也有 4K"的荒谬结论 |
| 用 `<video>.videoHeight` 当"播放账号能力" | 那是**实际在播**的画质，受用户手动选择影响，不是能力上限 |

## 后果

- `02-ui-spec.md` §4.2 的"分别用两套身份调一次 playurl"必须改写（已改）
- popup §2.3 的"主账号仅可用 X"在 **SSR 缺失时显示"未知"**，不许用别的数据顶替
- 新增一条页面数据通道（主世界 → content → SW 的 per-tab 缓存），消息类型需登记进 `messages.ts`
- `shared/types/playinfo.ts` 需补 `dolbyVision` 字段（现在只有 `flacAudio` / `dolbyAudio`）
- 体检页的"主账号"列只对当前打开的页面有效，UI 必须写清楚这一点
