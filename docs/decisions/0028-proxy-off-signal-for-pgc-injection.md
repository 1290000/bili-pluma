# ADR 0028：总开关的「关」必须在注入处可判

- 日期：2026-10-29
- 状态：**已采纳**（设计评审通过，待落地验证）
- 弥补：[ADR 0020](./0020-pgc-sync-injection-and-reload.md) 的能力边界 —— 它只定义了「有缓存就同步注入」，**没有定义总开关关闭时这条链路该怎么断开**
- 相关：[ADR 0023](./0023-intercept-playview-durl-swap.md)（SPA 切集走响应层，不走本文这条）、
  [ADR 0024](./0024-pgc-no-primary-baseline.md)（PGC 页不做主账号基线对比）、
  [ADR 0027](./0027-proxy-backup-api-host.md)（同为"用户报一个具体现象 → 挖出结构性缺陷"）

---

## 事故：关掉总开关，番剧页画质不回落

用户原话：「总开关 + 刷新导致的画质回落，只在视频页生效，番剧/国创页不生效」。

| 页面 | 关开关后刷新 | 为什么 |
| --- | --- | --- |
| 普通视频页 | 画质回落 ✅ | playurl 每次加载都重新请求，规则删了就换不回播放账号 Cookie |
| 番剧 / 国创页 | **不回落** ❌ | 取流由主世界主动调一次，结果存进页面 `sessionStorage`，**刷新不清它** |

番剧页的链路（[ADR 0020](./0020-pgc-sync-injection-and-reload.md)）是：

```
第一趟  主世界主动调 /pgc/player/web/playurl（DNR 换成播放账号）
        → 写 sessionStorage['pluma:pgc-vi:<cid>'] → reload()
第二趟  __playinfo__ 的 setter 里同步读 sessionStorage → 就地替换 video_info
```

**关掉总开关只是删 DNR 规则，`sessionStorage` 里的那份缓存一点没动。**
于是第二趟照样注入 4K 流 —— 画质当然不回落。

---

## 为什么「在注入处等 cfg」这条路从根上不通

三版都试过，全部被真机或既有测试否掉。记在这里，因为**下一个人还会想再试一次**。

| 版本 | 写法 | 死因 |
| --- | --- | --- |
| v1 | `if (pgcActive === false) return;` | `pgcActive` 初值 `null`，`null !== false` → 放行，等于没门控 |
| v2 | `if (pgcActive !== true) return;` | 真机：开关**正常开着**也 `skipUnknownCount: 1`，注入从 ~600ms 拖到 1879ms。`pgcActive` 只由 `page/activate` 的回包驱动，而 `hello` 那条 cfg 不带它 |
| v3 | `if (cfgEnabled !== true) return;`（`null` 也拦） | 打破 3 条既有测试，其中一条是 ADR 0020 的最终修法：「cfg 完全不到场时，只要有 `sessionStorage` 就在 setter 里注入」 |

**v3 的失败最有信息量。** 它断言的是：

> **不允许把注入绑在任何异步通道上。**

理由很硬：`cfg` 可能**永远不到**（扩展上下文失效、SW 没唤醒、content script 崩了）。
那时不注入就等于"这个功能不存在"。而 PGC 支持的全部价值就在于那一次同步注入。

### 真机时序（`ep3854818`，开关关闭）

```
ssAt           : 357ms   ← SSR 赋值，__playinfo__ 的 setter 触发
patchedAt      : 358ms   ← 注入发生（此刻 cfg 还没到）
cfgCount       : 4       ← cfg 全部在 358ms 之后才到
lastCfgEnabled : false   ← 等 cfg 到时，注入早就做完了
```

**这不是时序运气差，是结构性必然。** 门控信号的产生路径是
`content → background（解密凭据 → 装 DNR 规则）→ 回包 → postMessage`，
比页面自己内联脚本赋值长一到两个数量级。它**永远**会晚。

→ **结论：注入处不能等任何异步信号。** 这是本文最重要的约束。

## 第一版修法（被否）：开关关闭时清 `sessionStorage`

想法是"不在注入处门控，改在源头断掉"：清掉缓存，主世界就没东西可注入，与时序无关。

**方向对，但有三个洞。** 记下来，因为每一个都很容易被当成"已经想过了"。

### 洞 1：清缓存本身仍在跟 SSR 赋值赛跑

清缓存的唯一可靠触发点是 `content` 收到 `page/activate` 回包（`reason === 'disabled'`）。
而那个回包必然晚于 358ms 的注入：

```
357ms  setter → 读缓存（命中 4K）
358ms  注入完成                ← 早于清缓存
~400ms page/activate 回包 → 清缓存   ← 太晚了，video_info 已经是 4K
```

**用户看到的仍然是"关了开关、刷新一次、画质没回落"** —— 正是他报的 bug。
清缓存只是把竞争从「读缓存」挪到「删缓存」，**赛跑结构一点没变**。

### 洞 2：清完缓存后重开开关，会永久卡在试看

`pgc-reload:<cid>` 那个护栏记的是「本会话已为这一集刷过一次」（10 分钟 TTL）。
清缓存时若保留它（应该保留，它是防刷新循环的护栏），就会出现：

```
关开关 → 清 vi，留 guard
重开开关 → 刷新 → 无缓存 → 该取流了
        → isAlreadyTried(guard) === true → 直接 return
        → 不取流、不刷新、没有任何提示 → 停在试看，最长 10 分钟
```

**这是同一类 bug 的反面**：开关的动作在另一个方向不生效。不可接受。

### 洞 3：`sessionStorage` 按标签页隔离

`sessionStorage` 是 tab 级存储。用户开着 5 个番剧标签页时，"清缓存"只能清到当前那个。
虽然"其他 tab 不刷新就不会重新注入"能挡掉大部分场景，但这条路线**天然缺一个跨标签页的判据**。

## 决定：三层

### 第一层：门控 —— 主世界在 setter 里同步读一个 `localStorage` 标记

**这是本 ADR 的核心。** 判据必须满足一个条件：**读的那一刻就能判定**，不依赖任何先后假设。

`localStorage` 满足：

| 性质 | 为什么关键 |
| --- | --- |
| **同步 API** | 与 `sessionStorage` 同级，微秒级。不会错过 `createPlayer` 那 0~2ms 窗口 |
| **跨标签页共享**（同 origin） | 一处写，5 个番剧标签页全部生效 —— 补掉洞 3 |
| **不依赖扩展消息** | `cfg` 永远不到也照样能判 —— 不违背「不许绑异步通道」 |

标记只在**关闭**时写，打开时删。**三态语义**：

| 读到的值 | 含义 | 动作 |
| --- | --- | --- |
| 存在且新鲜 | 用户关了总开关 | **不注入** |
| 不存在 | 开关开着，或从未写过 | 注入 |
| 读不出来（抛错 / 隐私模式） | 判不了 | **注入**（宁可多注入一次，不可让功能静默消失） |

⚠️ **"新鲜"是必须的。** 标记是"写入时刻的状态"，不是"读的时刻的状态"。
某次写失败（配额满 / 隐私模式 / SW 没醒）就会永远读不到 → 永远放行 → 退回原 bug。
给一个时间上界，把"最多错多久"变成可陈述的数字。

### 第二层：清理 —— 开关关闭时清掉 `sessionStorage` 里的注入缓存

不再承担门控职责（那是第一层的事），只做两件小事：

1. **数据卫生**：开关关着时，页面里躺着一份 4K 流地址没有意义
2. **双保险**：如果 `localStorage` 被外部工具清掉，缓存也没了

**必须遵守**：只清 `pluma:pgc-vi:` 前缀。**不清** `pluma:pgc-ep:`（见下方"边界"）。

### 第三层：恢复 —— 开关重开时清掉 `pluma:pgc-reload:` 护栏

补掉洞 2。只有"用户明确做了一次开关动作"这个一次性事件才清，
**不能**在每次页面加载时清 —— 那会废掉 `alreadyTried` 的防循环本意。

## 三层门控的先后顺序与语义

现在注入处有三道判断。顺序与语义必须写死，否则下一个人改一处就会让另一处失效。

```
① localStorage 标记  →  明确"关"  →  skip，lastStage = 'skip-proxy-off'
② cfgEnabled        →  明确"关"  →  skip，lastStage = 'skip-disabled'
③ pgcActive         →  明确"关"  →  skip，lastStage = 'skip-inactive'
   （以上三道的"未知/null"一律放行）
```

**语义：任一道明确为「关」就拦；没有任何一道明确为「关」就注入。**

### 为什么不是"三道都满足才拦"

那等于回到 v1/v3 的老问题：只要有一道永远到不了（`cfg` 不到、`page/activate` 不回），
门控就永久失效。**"与"关系在异步信号上等于没有门控。**

### 为什么"任一道为关就拦"不会互相遮盖

三道判据的**触发条件互不重叠**，所以不存在"① 拦住了 ② 就永远看不到自己该拦的情况"：

| 道 | 什么时候为「关」 | 是否依赖扩展消息 |
| --- | --- | --- |
| ① `localStorage` 标记 | 用户关了总开关 | **否**（页面自己的能力） |
| ② `cfgEnabled` | 用户关了总开关 | 是（`hello` 那条 cfg 就带） |
| ③ `pgcActive` | 未配置凭据 / 两账号相同 / 处理出错 | 是（`page/activate` 回包） |

① 和 ② 是**同一件事的两个独立观测**（冗余，不是互补）。冗余在这里正是要的：
`localStorage` 不依赖消息，`cfgEnabled` 不依赖页面存储能力，**任一条能到就够**。

② 和 ③ 是**互补的**：② 管"用户不想用"，③ 管"想用但用不了"。

⚠️ **副作用：必须先判 ①。** 否则开关关闭时 `cfgEnabled` 也是 `false`，
日志里只会出现 `skip-disabled`，看不出"到底是哪条路先拦住、另一条是否还活着"。
先判 ① 让**两条冗余观测各自都有机会被观测到**（关着开关多刷几次，
应当同时看到过 `skip-proxy-off` 和 `skip-disabled`；只看到一条说明另一条坏了）。

### 计数必须分开

| 计数器 | 含义 | 关着开关刷新后应看到 |
| --- | --- | --- |
| `skipProxyOffCount` | 被 ① 拦了几次 | ≥1 |
| `skipDisabledCount` | 被 ② 拦了几次 | 可能为 0（① 先拦了） |
| `skipInactiveCount` | 被 ③ 拦了几次 | 可能为 0 |

**合成一个计数会让这套门控变成不可观测的。** 上一轮排查之所以走了三版弯路，
一半原因就是"看不出是哪条路在拦"。

## 边界：哪些 key 清、哪些不清

| key | 清？ | 理由 |
| --- | --- | --- |
| `pluma:pgc-vi:<cid>` | **清** | 唯一影响注入的数据源，本 ADR 的主体 |
| `pluma:pgc-ep:<epId>` | **不清** | 它是 `ep_id → cid` 的映射，与"能不能注入"无关；清了只会让页面状态对不上 |
| `pluma:pgc-reload:<cid>` | 关闭时**不清**，重开时**清** | 它是防刷新循环的护栏，不是缓存。关闭时清掉会削弱护栏，重开时不清会卡在试看 |
| `pluma:pgc-resume:<cid>` | **不清** | 播放位置记忆，与画质无关 |

### 被明确否掉的一条推理

> 「清掉 `pgc-ep` 映射 → 下次进页面找不到缓存 → 多一次取流 → 这次取流正好是主账号身份，可能反而是想要的」

**不成立，三个理由：**

1. `pluma:pgc-ep:` **不参与**取流决策。要不要取流看的是 `storage.local` 的缓存与同步缓存是否存在。
2. 开关关闭时那次"多出来的取流"拿到的是主账号身份 → 服务端返回试看流 → 被 `hasPlayableStream` 判否 → `kind: 'denied'` → **不写缓存、不刷新**。是一次无害但无用的请求。
3. **"用主账号再取一次基线"这条路
   [ADR 0024](./0024-pgc-no-primary-baseline.md) 已经明确否决**。它需要在请求期间摘掉 DNR 规则，
   与 [ADR 0006](./0006-no-per-request-nonce.md)「常驻规则、不每请求增删」直接冲突。

## 代价（如实记下）

| 代价 | 上界 | 是否可接受 |
| --- | --- | --- |
| 标记写失败 → 门控退化 | 最多陈旧一个窗口期，之后标记失效、自动放行 | 可接受。**不放行比多注入危险得多** |
| 重开开关后用户看到一次刷新 | 1~2 秒闪屏 | 可接受。与"首访新集"是同一种代价（ADR 0020 已接受） |
| 无痕窗口与普通窗口共享 `localStorage` | 两边开关不同步时，标记可能反映另一边 | 已知弱点，见下 |

### 已知弱点：无痕分区的标记一致性

`incognito: "split"` 下扩展存储是**分实例**的，但 `localStorage` 是**按 origin**、两实例共享。
于是可能出现：

- 普通窗口关了开关 → 标记写上 → 无痕窗口（开关还开着）也被拦住
- 反向同理

**缓解**：标记只影响"要不要注入缓存流"，不影响取流本身（取流由 DNR 规则决定，分实例独立）。
所以最坏结果是"无痕窗口这次没注入"，而不是"无痕窗口出错了"。
**不做额外处理** —— 为它引入实例 id 之类的机制，成本远大于收益，且会让方案复杂到没人敢改。

## 验证

新增测试（全部在 `tests/unit/content/main-world-pgc.test.ts`，纯 jsdom，不需要真机）：

| # | 断言 | 守什么 |
| --- | --- | --- |
| 1 | 标记新鲜 + 有 `sessionStorage` 缓存 → **不注入**，`skipProxyOffCount === 1` | 本 ADR 的主效果 |
| 2 | 标记不存在 → 正常注入 | 不误伤正常路径 |
| 3 | 标记过期 → 正常注入 | 防"永久静默失效" |
| 4 | 读标记抛错 → 正常注入 | 隐私模式降级 |
| 5 | 标记 + `cfgEnabled=false` 并存 → 仍不注入，且计数分得清 | 两道冗余观测不互相遮盖 |

必须保持绿的既有测试：

- `main-world-pgc.test.ts` 的「cfg 完全不到场时，只要有 `sessionStorage` 就在 setter 里注入」——
  **这是本 ADR 的准入条件**，改任何东西之前先跑它
- `main-world-pgc.test.ts` 的「总开关关闭时不注入」两条（`cfgEnabled` 路径）
- `tests/unit/content/pgc-reload-plan.test.ts` 全绿 —— **`shouldReload` 的签名不许动**

**真机验收**（不可用单测替代）：

1. 关总开关 → 刷新番剧页 → `video.duration` 回到试看长度，`skipProxyOffCount ≥ 1`
2. 重开开关 → 刷新同一集 → 取流发生、缓存写回、`duration` 回到整集
3. 开 3 个番剧标签页，只关开关不刷新，逐个刷新 → 三个都回落（验证跨标签页）
