# ADR 0035：把首页推荐接口加入代理白名单 —— 且只代理「滚动加载」那一段

- 日期：2026-11-11
- 状态：**已采纳**（2026-11-11 用户逐条裁决）
- 影响文件：`src/shared/constants/routes.ts`（新增一条 `PROXY_ROUTES`）、新增 content 入口（来源分界线）
- 相关：[ADR 0004](./0004-request-level-identity-proxy.md)（请求级身份代理，**不改其路线**）、
  [ADR 0006](./0006-no-per-request-nonce.md)（常驻规则，**不改其结论**）、
  [ADR 0031](./0031-page-level-visual-cleanup-boundary.md)（页内视觉改造边界）
- 方案：[docs/plans/1.2.0-account-roles-plan.md](../plans/1.2.0-account-roles-plan.md) 步骤 5
- 证据：`poc/probe/api-inventory/RESULT.md` §10、`poc/probe/feed-boundary/RESULT.md`

---

## 决定

把 `/x/web-interface/wbi/index/top/feed/rcmd` 加入取流白名单（`PROXY_ROUTES`），
使首页**滚动加载**的推荐流可以以取流账号身份取回。

**这是本项目第一次给"非取流"接口开代理。** 白名单此前只放行 playurl 族，
唯一的判据是"这条路径能不能拿到更高画质"。本条路径不提升任何画质，
它改变的是**用户看到哪一批推荐**，因此必须单独成篇说明边界。

路径修订号按 `routes.ts` 的规则 +1（新增路径字符串）→ **3 → 4**。

### ⚠️ 「可配置」的粒度：二选一，不是任意多账号

本文与方案里的「可配置」**只指在两个合法来源之间二选一**：

| 可选的两项 | 说明 |
| --- | --- |
| 浏览器当前登录的账号 | 即「主账号」，不需要扩展托管任何凭据 |
| 扩展托管的那个账号 | vault 里那**一个** blob |

**不是"推荐流可以选任意账号"** —— 多账号（vault 存 N 个）**不做**。
原因是 `vault.ts` 是**单 blob** 模型、`credential-store.ts` 全是单数签名，
多账号是 v1 的既有边界（推迟到 v1.5，见 `docs/04-project-structure.md` §6「v1 只支持单个播放账号」），
且每加一个号要开一次无痕扫码，撞 [ADR 0012](./0012-isolated-window-login.md)。

> 写死这段是为了防止下一个人读成"推荐流可以按账号随便切"，然后基于错误前提做设计。

## 为什么不扩大越权

| 疑问 | 回答 |
| --- | --- |
| 会不会读到别人的数据 | 不会。它和 playurl 一样是**读取请求者自己的推荐流**，不涉及任何他人数据 |
| 换了 Cookie 签名会不会失效 | **不会**。实测 `w_rid` 传 32 个 `0` 仍返回 `code 0`；`playurl` 同样（对照组） |
| `wbi` 密钥是否与身份绑定 | **不绑定**。登录态与游客态取到的 `nav` wbi keys **完全相同** |
| 怎么证明它确实按身份给推荐 | 响应回显 `data.mid` = 请求者身份，Cookie 换成谁 `mid` 就是谁 |

> ⚠️ 适用面限定：以上"不校验签名"的结论**只到实测过的 `rcmd` 与 `playurl`**。
> 不得外推成"B 站所有 wbi 接口都不校验"（`poc/probe/api-inventory/RESULT.md` §A2 原文限定）。

## 能力边界：**默认只换滚动加载；打开独立开关后连首屏一起换**

> ⚠️ **本节在 2026-11-11 之后被扩展过** —— 原文写的是「首屏换不了」，
> 那是**当时**的结论。现在有了另一条路（隐藏首屏批），见本文末尾
> 「后续实现：隐藏首屏批」。**下面这段仍然成立的前提是"用户没打开那个开关"。**

这是本 ADR 最需要说清的一段。**默认情况下**，用户打开首页时看到的 10 张卡，
**在代理生效后仍然是页面身份的**。

### 为什么首屏换不了

首页主文档的 HTML **由 Cookie 决定**（实测：同一 URL 带 Cookie `178839` 字节并回显
`mid:{{当前登录mid}}`；不带 Cookie `153423` 字节、无 `mid`，差 25 KB）。

> 这里要证明的是「**存在 `mid` 字段，且它随 Cookie 变化**」，不是「它等于某个具体数字」，
> 所以按 `AGENTS.md` §6.3 用占位符。字节数是脱敏无关的实测规模，可以留。

要连首屏一起换，只能代理 `www.bilibili.com` 的 `main_frame` —— 那会让**整页变成另一个身份**
（顶栏头像、未读数、私信全变），直接违背 [ADR 0004](./0004-request-level-identity-proxy.md)，
且竞态不可枚举。**不采用。**

### 实际行为

| 时刻 | 推荐来源 |
| --- | --- |
| 打开首页（SSR 初渲） | **页面身份** |
| rcmd 接口返回后 | 接口数据；实测 SSR 那 10 张**混入**其中，分不出哪条来自 SSR |
| 继续滚动 | 每次净增 **8 条**，纯尾部追加 |
| **刷新页面** | **退回页面身份**（分界线也退回原位） |

> ⚠️ 最后一个行为**必须告知用户**，不能让用户以为"设一次就永久生效"。

### 为什么能按条数插「来源分界线」

实测 `poc/probe/feed-boundary/RESULT.md`：

| 判据 | 结果 |
| --- | --- |
| 首屏 SSR 批大小 | `[10,10,10,10,10]`，**标准差 0**（原始 HTML 统计 + `DOMParser` 两路交叉） |
| 后续滚动 | 每次净增 8 条，`droppedCount: 0`、`relativeOrderKept: true`、`newCardsBeforeOldHead: 0` |

所以分界线插在**第 10 个 `.bili-video-card.is-rcmd`** 之后。

**三条错误判据（实测会错位，写在这里防止下一个人"顺手优化"）**：

- ❌ 按"有 BV 的第 N 张" —— 实测 **8–10 浮动**（广告卡有标题、无 BV）
- ❌ 按 `.bili-video-card` 总数 —— 实测是 **12**（含 2 张非 rcmd 骨架），不是 10
- ❌ 按滚动像素 —— 随视口宽度变

## 被放弃的备选

| 方案 | 放弃原因 |
| --- | --- |
| 代理首页 `main_frame` | 整页换身份，违背 ADR 0004；竞态不可枚举 |
| 只插切换按钮、不改数据源 | 点下去**没有数据可换** —— 列表是页面自己请求的 |
| 历史记录的切换按钮 | DOM 无障碍（浮层是普通 DOM，可插按钮），但 `history/cursor` 的数据由**页面请求**带来，Cookie 只能靠 DNR 网络层改；而"点按钮才切"需要动态 add/remove 规则，**违反 ADR 0006** |
| 让 background 用 vault 凭据直发请求 | **不存在这条路**。`Cookie` 是 forbidden request header，脚本设置会被浏览器静默丢弃；vault 凭据只能经由 DNR 网络层使用 |

## 后果

**正面**：用户可用取流账号的推荐流，且滚动加载部分立即生效，不需要刷新。

**负面 / 已知弱点（不许当成已验证）**：

1. ~~**首屏永远是页面身份** —— 这是架构决定，不是缺陷~~ →
   **2026-11-11 已不成立**：打开「首页推荐流使用取流账号」开关后，首屏批被隐藏，
   用户看到的第一屏就是取流账号的推荐。见下面「后续实现」
2. **刷新即退回** —— 用户需重新滚动才再次生效
3. **分界线依赖"尾部追加"行为** —— B 站改版会失效，且 SSR 批大小也需复测
   （⚠️ 分界线功能已于 2026-11-11 整体删除，此条仅存档）
4. **游客态 SSR 批大小未测** —— 清 cookie 是硬红线，主动跳过
5. **换账号后分界线是否仍第 10 条未测** —— 需跨账号真机
6. **移动端/窄视口未测**

## 后续实现：隐藏首屏批（2026-11-11）

**本文档上面"首屏换不了"的论证仍然成立** —— 它证明的是"不能代理 `main_frame`"。
但后来发现**还有一条不需要代理主文档的路**：首屏那 10 张 `.feed-card`
和滚动加载的 `.bili-feed-card` 在 DOM 里是**两批不同的元素**，
所以可以**只把前者藏掉**，让后者顶上来。

### 与本文档的关系

| 项 | 状态 |
| --- | --- |
| 本文档授权（把 `feed/rcmd` 放进 DNR 白名单） | **不变**，仍是必经之路 |
| 「首屏换不了」这个**架构结论** | **被绕过，不是被推翻** —— 仍然不能代理 `main_frame` |
| 首屏的处理方式 | 从"不动它"改为**"藏掉它"**（纯页内视觉，不发请求、不改响应） |

### 实现的三个要点

1. **独立开关** —— 「首页推荐流使用取流账号」，与取流身份**完全独立**
   （用户原话：「这是两个不同的功能」）
2. **独立 DNR 规则 ID 段**（`11000`）—— 推荐流规则的启停不与白名单顺序耦合
3. **状态推导**（`rule-plan.ts`）—— 任何状态变化都由 `buildRulePlan()`
   一次性推导完整计划，而不是"在某个动作里补一句"

### 真机实测（2026-11-11，三次采样 + 滚动 3 轮）

| | 隐藏前 | 隐藏后 |
| --- | --- | --- |
| 首屏可见卡 | 22 张（页面账号 12 / 取流账号 10） | 22 张（**页面账号 0 / 取流账号 22**） |
| 首张可见卡 `top` | 255 | **255**（零空洞） |

滚动 3 轮回顶后 `top` 精确恢复 255，取流账号批每轮稳定 +14 补位。

### ⚠️ 新增的两条已知限制（不许当成已验证）

1. **B 站曝光上报可能按 DOM 顺序** —— 藏掉首屏批后，曝光上报可能仍记在它们身上。
   **未测。** 若属实，"已看过"的记录与用户实际看到的不一致。
2. **依赖 `.feed-card` 类名** —— B 站改版会失效。
   失效时**不静默**：`evaluateHidePlan()` 会在匹配 0 张时 `console.warn`。

---

## 一句话

**这条路径换的是「用户看到哪一批推荐」，不是「能看多高的画质」；
所以它的授权必须写成"默认只换滚动加载；打开独立开关后连首屏一起换
（藏掉首屏批）、刷新即回"，而不是笼统的"推荐流已切换"。**

> ⚠️ 本句 2026-11-11 订正：原文只有"首屏不动"这一种情形，
> 而隐藏首屏批落地后已有第二种（见上方「后续实现」）。**两种情形要分开说**——
> 只说"首屏不动"会让文案与实现矛盾，只说"全部切换"则会掩盖"这条接口本身管不到首屏"。
