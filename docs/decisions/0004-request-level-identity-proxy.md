# ADR 0004. 请求级身份代理，而非 Cookie 切换

日期：2026-10-24
状态：已采纳
这是整个项目的**架构基石**，其余设计都建立在它之上

## 背景

需求是"主账号负责收藏/点赞/评论/历史，播放账号（大会员）负责取流解锁高画质"。有两条路：

**路线 A（切换式）**：保存两套 Cookie，播放前切到 B，播完切回 A。

**路线 B（代理式）**：浏览器始终是 A，只对特定取流接口，用 B 的凭据重发该请求。

## 决策

采用**路线 B：请求级身份代理**。浏览器全程保持主账号 A 的登录态，扩展在 JS 层为**白名单内的路径**换一套凭据重发。

```
主账号 A：浏览器 cookie jar 里唯一的身份，全程不变
播放账号 B：只存在于扩展的加密存储里，从不写入 cookie jar

打开视频页
  ├─ /x/web-interface/nav        → 正常 A → 返回 A 的头像/未读数        ✅
  ├─ /x/player/wbi/playurl       → 命中白名单 → B 的凭据重发 → 4K/HDR ✅
  ├─ 点赞 /archive/like          → 不在白名单 → A 的凭据               ✅（记到 A）
  ├─ 进度 /click-interface/...   → 不在白名单 → A 的凭据               ✅（历史记到 A）
  └─ 评论 /x/v2/reply/add        → 不在白名单 → A 的凭据               ✅（评论在 A）
```

## 理由

### 1. 路线 A 有无法消除的竞态

切换 Cookie 的那一刻，页面上**所有**在飞的请求都可能串号：

- 切换窗口期内，A 的消息轮询请求带着 B 的 Cookie 发出去 → A 的未读数错误
- 切回 A 之后，B 的请求还没回来 → 响应写到 A 的会话里
- 播放页的 SPA 路由、预加载、实时弹幕连接都会持续发请求

这类 bug **不可复现、不可测试**，因为取决于网络时序。加锁能让概率变低，但无法归零。

### 2. 路线 B 的失败模式是"可枚举的"

| 路线 | 失败原因 | 可控性 |
| --- | --- | --- |
| A 切换式 | 时间窗口内所有请求都可能错 | ❌ 不可枚举 |
| B 代理式 | 白名单里漏写了某个路径 | ✅ 可以逐条核对 |

**这是本质区别**：A 的失败是概率问题，B 的失败是清单问题。

### 3. 副产品：D/E 需求免费解决

原方案里，"点赞归主账号""历史归主账号"被列为难点，需要"劫持 heartbeat → 用主账号重放 → 返回伪造 200"。

**采用路线 B 之后，这段逻辑整段删除**——因为浏览器从头到尾就是 A，所有写操作和历史天然归 A，不需要任何干预。

这是路线 B 最漂亮的地方：**它不是"更优雅地解决了问题"，而是"让问题不存在"。**

### 4. 有可运行的先例

Dual Account Helper 用这个模式跑了不短时间，其 7 个代理路径的白名单是实测结果。虽然它的实现（油猴 `GM_xmlhttpRequest`）不能直接搬到扩展，但**机制已验证**。

## 被放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 切换 Cookie（路线 A） | 竞态不可消除；频繁切换还容易触发风控 |
| 双浏览器 profile | 需要用户开两个浏览器窗口，体验割裂；且"历史归主、播放归副"无法跨 profile 实现 |
| 自建播放器完全接管 | 弹幕、快捷键、画质菜单、互动视频全要重写，工作量巨大 |

## 后果

**收益**：
- 主账号的社交行为与历史无需任何特殊处理
- 不需要劫持/重放/伪造响应这套高风险操作
- 不需要"暂停主账号轮询"之类的 hack

**代价**：
- 白名单的完整性成为关键（→ Q8：必须系统性抓包，漏一个路径就有一个场景失效）
- B 站新增取流接口时需要跟进（→ Q15 已定：只做本地版本号 + 升级提示，不做远程配置）
- 依赖 DNR 在并发下的正确性（→ **Q2，最大风险**）

## 对 UI 的影响

因为"天然不串号"，UI 上可以做一件很有说服力的事：把两个账号的职责明确写在卡片上（A："收藏·点赞·评论·历史"，B："仅取流"），用来消除用户"我的号会不会被切走"的恐惧。

详见 `docs/02-ui-spec.md` §2.4。
