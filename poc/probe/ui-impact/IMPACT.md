## 0. 方法说明（为什么这份清单是唯一防线）

1. **每一条都给了 `文件:行号`**，没有"大概在 xxx"。文案类改动 `verify` 查不出（2026-11-11 交接文档 §2.5 实测：把副标题改回旧的、把 `releaseNotes()` 换成禁用词，`verify` 仍全绿），所以**一行没登记就是一行会漏改**。
2. **`仍成立` 的行也列了**：不列的话，改版时会有人顺手把不冲突的东西一起改掉 —— 本轮已经有过"把已定稿的东西当 bug 修"的先例。
3. 判断口径只有一条：**这句话/这个判据在新模型下会不会陈述一个假事实**。只是"长得丑/读着别扭"的归 `需改文案`，`CONFLICT` 只留给会说谎的。
4. **头部的条数是被脚本数出来的**（`grep '^| [0-9]+\.[0-9]+ |'` 再按 `CONFLICT` / `需改文案` / `仍成立` 分桶），不是我手数的 —— 交接文档 §2.1 的教训是"Lead 自己报的数被成员实测推翻"（说 21 处，实数 26）。**谁改这份表，谁重跑一次那个计数。**

### 新模型下的三种"会出事的配置"

盘点里反复引用这三个场景，后文用编号指代：

| 代号 | 配置 | 与今天的差别 |
| --- | --- | --- |
| **S1** | 取流号 = 记录号 = 浏览器登录态（**单账号退化**，不代理） | 今天不可能：`page/activate` 直接拒绝，且 `describePopup` 的判据要求"有播放账号凭据" |
| **S2** | 取流用 A、记录用 B，**A 比 B 弱**（例如 A 是普通号、B 是大会员号） | 今天不可能：播放账号恒强于主账号是隐含假设 |
| **S3** | 记录号 ≠ 浏览器登录态（浏览器里登录的是第三个号 / 游客） | 今天不可能：记录号**恒等于**浏览器登录态（决策 4） |

**关于题面问的「若取流账号 = 浏览器登录身份，对比是否还成立」（ADR 0014）**：

**不成立，而且是双向的。** ADR 0014（`docs/decisions/0014-quality-compare-from-page-data.md`）的**整个前提**是"`__playinfo__` 是服务端用**主账号** SSR 的，播放账号通过 DNR 拿到了另一份" —— 见该文件 §背景 第 1 条与 §决策 1。单账号模式下：

- 页面只发**一次** playurl，用**同一个**身份，服务端返回的是同一份流的两种表述 → SSR 与 playurl 的差异只剩"覆写前后"，**不是"谁更强"**。
- ADR 0014 §实现约束里那条验证门「SSR 基线的最高高度**低于** playurl 响应」在 S1 下**恒假**（两者相同），于是 `applySsr()` 会把 `usable` 判成 `client-written` → 锚点常驻「主账号基线不可用（数据来源是播放账号）」。
- 结论：**单账号模式必须整块关闭画质对比**，只显示徽章（"取到了什么"），不显示"比谁强"。

```
取流身份     ◉ <昵称 A>        [换]
记录身份     ◉ <昵称 B>        [换]
推荐流身份   ○ 未指定          [换]
```

理由：用户要回答的问题从"谁是谁"变成了"**这件事现在归谁**"，而前者在新模型下不再有唯一答案。三个职责恰好对应题面的三条需求（取流 / 首页推荐 / 历史进度评论）。缺点是**每种职责都得有一个"未指定"态**，这是新增的界面负担 —— 不要为了保留 A/B 两卡而硬凑。

### 题面要求的两条纪律原文（`primary-card.ts`）

> 1. **`loggedIn === 'no'` 时绝不读缓存。** 那是"确认未登录"（DOM 就绪后读不到 `DedeUserID`）。此时显示缓存昵称 = 把游客说成"某个账号"，而那可能是上一个账号。
> 2. **`unknown` 绝不渲染成"未登录"。** `unknown` 的语义是"还没读到"，把它说成"没登录"是在编结论 —— 而"刚进视频页就点 popup"正是最常见的路径。
> —— `src/shared/utils/primary-card.ts:15-18`

**新模型下是否还成立：都成立，但适用范围要缩窄。**

两条纪律保护的是"**A 卡显示的那个昵称到底是不是当前这个浏览器会话的号**"。在新模型下：

- 纪律 1、2 **照旧成立**，而且**更重要**：因为基线账号（S3 下）可能不是用户配的记录号，"把游客说成某个账号"的代价更大了。
- **但**它们**只覆盖了"浏览器登录身份"这一个候选**。新模型下还需要**第三条纪律**：**"卡片上显示的昵称必须与它声称的职责一致"** —— 今天 `tabs.ts:441/461` 的副标题（收藏点赞…/仅取流）直接**声称了职责**，而新模型下职责是可配置的。前两条纪律管的是"这号是谁"，缺的第三条管"这号负责什么"。**这是本次改版最容易被漏掉的纪律缺口。**

## 3. 最危险的 3 条（会骗用户，不是长得丑）

| 排名 | 条目 | 为什么最危险 |
| --- | --- | --- |
| **1** | `src/background/handlers/page.handler.ts:96-100` + `src/shared/types/messages.ts:129` | **静默失效**：`same-account` 直接返回 `activated:false`，而 `reason` 的**消费方为零**（全仓 grep `same-account` 只有定义处），界面**完全看不到**。单账号模式下用户会撞上它，得到一个"开关开着、什么都没生效、也没有任何提示"的局面。这比说错话更糟：**它什么都不说。** |
| **2** | `src/content/panel/tabs.ts:342`（总开关 hint「收藏 / 点赞 / 历史不受影响」）+ `src/content/panel/tabs.ts:461`（「仅取流」） | **两条关于"职责边界"的承诺**，是新模型成立的前提被推翻的直接受害者。用户会据此做出决定（"那我就用大会员号取流，反正历史还是记在主号上"），而新模型下**这个保证不再成立**。它不是显示错误，是**对用户决策的误导**。 |
| **3** | `src/core/ui/popup-state.ts:206-216`（`hasCredential` → 「已接管」）+ `src/core/ui/popup-state.ts:218-224`（「凭据失效，需要重新扫码」） | **两端的谎**：一端把"有密文"当成"在代理"（S2 下取流号更弱也说已接管），另一端在单账号模式（**没有密文**）下**100% 命中**"需要重新扫码"，引导用户去扫一个不存在的号。用户在两个方向上都得到假结论。 |

> 补充第 4 条（不算进前三，但同样会骗人）：`src/shared/types/errors.ts:11` 的 `CREDENTIAL_EXPIRED` 与 `popup-state.ts:279` 的「播放账号登录已过期」—— 失效的是记录号时，用户会去重扫取流号，**扫了也不会好**。这是"重复劳动型误导"，比直接报错更耗人。

## 4. 单账号退化模式的结论（必读）

**「只有一个账号、取流与记录同号」在现有界面上能不能活：不能。**

不是"文案要说 5 处"，是**取流功能整个不工作**，而且界面会**不报错**：

| 断点 | 位置 | 后果 |
| --- | --- | --- |
| 1 | `src/background/handlers/page.handler.ts:97-100` | `primaryMid === credential.dedeUserId` → 拒绝装标签页规则。**而这一条对全局规则无效**（注释 `page.handler.ts:109-112` 自己写着"拒绝并不能真的不代理"），所以真实后果是**代理照做、规则不装、界面不知情** |
| 2 | `src/core/ui/popup-state.ts:164-172` | 无密文 → 永判「未配置」→ 引导扫码 |
| 3 | `src/content/isolated/page-state.ts:140-149` | 取流号 = 页面身份 → `__playinfo__` 必被覆写 → `usable` 恒 `false` → 锚点常驻「主账号基线不可用」 |
| 4 | `src/platform/diagnostics/collect.ts:566-568` | 主账号基线 `ok:false` → `tipFor()` **最先**返回「主账号基线不可用」。若同时有 DNR 规则问题，**被它盖住**（它 return 在最前面） |
| 5 | `docs/decisions/0014-...md` 验证门 | ADR 0014 的验证门（"SSR 高度 **低于** playurl 高度"）在 S1 下**恒假**，等于把 ADR 0014 的整个观测手段废掉 |
| 6 | `src/core/playinfo/rank.ts:158` | `diffCapability` 会得到 `improved:false`，因为两侧同一份数据 → 「无提升（源限制）」 |

**所以单账号模式不是"界面文案要适配"，而是需要一条独立的产品路径**：不代理、不做对比、不显示总开关、只显示"当前取流身份 = 你登录的号"和真实画质徽章。**这条路径今天完全不存在，且 `AGENTS.md` §3 决策 2（请求级代理）与决策 4（主账号不归扩展管理）的边界需要用户重新裁决。** 见 §5。

## 5. 我没法自洽的地方（**说不可能，不硬凑**）

以下三条，按题面纪律**直接说不可能**，不提供"改法"：

1. **「任意账号可记历史/进度/评论/收藏/点赞」与决策 4（主账号不归扩展管理）不能同时成立。** 记录行为发生在页面自己的 fetch 上，要换成另一个号就必须对这些接口做请求级代理 —— 而那是 `AGENTS.md` §3 决策 2 与决策 4 的直接扩张。**UI 层无解**，必须先有架构决策。
2. **`incognito: 'split'` 下，"记录身份"不可能是扩展托管的号。** 无痕分区的 cookie 只活在无痕窗口里，而记录行为发生在**普通窗口**的页面上。所以"记录身份"**只能**是浏览器登录态（今天的设计），也就不可能"任意指定"。**要突破就得改隔离方案**，那是 ADR 0012 的层面，不是界面。
3. **画质对比的"基线"在职责可配置后没有唯一含义。** 对比的语义是"取流侧比基线强多少"，而"基线"今天 = 浏览器登录身份（ADR 0014 §决策 1）。若记录身份 ≠ 浏览器登录身份，同一块画质卡会同时涉及**三个**号（取流 / 记录 / 浏览器登录），而数据侧只拿得到两个的来源。**这块要么限定"对比只在基线 = 浏览器登录身份时显示"，要么整块去掉对比只留徽章** —— 二选一，没有第三种自洽写法。
