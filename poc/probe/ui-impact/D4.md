## Q1（修正后）：`tabs.ts:342` 指代范围 → **泛指"所有非取流行为"，在今天成立；在退化形态下 100% 成立，不需要改**

### 1.1 它在哪儿、上下文是什么

`src/content/panel/tabs.ts:92-100`（`qualityTab()` 的总开关）：

```ts
box.appendChild(
  switchRow({
    label: '自动接管取流',
    hint: '只替换取流接口的身份，收藏 / 点赞 / 历史不受影响',   // ← :95，题面说的 :342 在本文之前是行号漂移
    ...
```

> ⚠️ **行号更正**：lead 给的是 `tabs.ts:342`，那是上一版编号。**当前工作区里这句话在 `tabs.ts:95`**；`:342` 现在是 `homeCleanPane()` 里 `OBSERVED_CATEGORIES` 的 `label: cat`，与承诺无关。本文用 `:95`。

**上下文判定（关键）**：

| 判据 | 值 | 含义 |
| --- | --- | --- |
| 它挂在哪个控件上 | 「自动接管取流」开关（`tabs.ts:94`） | 讲的是**这个开关打开后会发生什么** |
| 它什么时候渲染 | 画质 Tab 恒渲染（`tabs.ts:92`，不在任何 `if` 里） | 不是"已接管"时才出现，是**开关旁的常驻说明** |
| 它修饰的对象 | 「收藏 / 点赞 / 历史」——三个**动作名词** | **动作**是写入语义；读取通常说"收藏夹""历史记录列表" |

**结论：它泛指"除取流之外的用户行为"，且默认理解为写入。**

### 1.2 在 D2/D3/阶段6 都不做之后，它是否成立

**所以 `tabs.ts:95` 在新模型下 100% 成立，一个字都不用改。**

### 1.3 lead 的"拆成两层"判断——**在 D2/D3/阶段6 都不做之后，这个判断不再适用**

lead 上一封信的推理是「唯一变假的是范围部分：读取类可配」。阶段 6 砍掉之后**范围也没变假** —— 能换身份的面只剩取流，而原句说的正是"只替换取流接口的身份"。

> **D4 退化为：只剩"术语（主账号 / 播放账号）要不要改"这一个问题。**

### 1.4 唯一可能让这句变假的变量：**推荐流**

如果 D1 决定做"首页推荐流由另一个身份决定"，那么 `tabs.ts:95` 的「**只**替换取流接口」就变假了（推荐流不在"取流接口"里）。此时最小改动是把 `取流接口` 扩成 `取流与推荐`，**其余不动**。这一条挂在 D1 上，不在本文裁决范围。

### 5.4 关于 `not-configured`（`popup-state.ts:164-172`）的判据

**该不该存在：该存在，但判据要改。**

| 现状 | 问题 |
| --- | --- |
| `if (!configured)`（`:164`），`configured = (account?.configured ?? false) \|\| proxy.hasCredential`（`panel-data.ts:314`） | 这个判据只认"有没有托管凭据"。**单账号模式下永远 false** → 落到 `not-configured` + `needsLogin: true`（`:170`）→ 引导用户去扫码 |
| 而单账号模式的**真实状态**是"取流身份 = 浏览器登录态，一切正常" | 把一个完成态说成未完成态 → **P0** |

**判据（不是建议）**：

- `not-configured` 应保留，定义收窄为「**取流身份尚未确定，且没有可用的默认值**」。
- 单账号模式下取流身份**有**默认值（浏览器登录态，可由 `primaryMid` 判定且无需凭据）→ **不应落 `not-configured`**，应落一个"已就绪但未托管凭据"的正向状态（`describePopup` 里对应「已接管」那条的语义位置）。
- 因此 `configured` 的判据要从 `hasCredential` 改成 `hasCredential || primaryMidKnown`。⚠️ 但这会牵动 `popup-state.ts:206-216` 那段踩过坑的顺序（"`hasCredential` 优先于 `ruleCount`"），**改之前必须重读那段注释**。

### 5.5 「仅取流」（`tabs.ts:461`）现在是否仍然准确

**准，但只对"写入"准，对"读取"是过度承诺的镜像（低报）。**

| 理解 | 是否成立 |
| --- | --- |
| "这个号只负责取流，不会用它的身份写你的历史/点赞/评论" | ✅ **完全成立**（D2 + D3 都不做） |
| "这个号只用于取流，其它任何请求都不用它的身份" | ✅ **也成立**（阶段 6 不做，读取也不换） |
| 潜在误读："这个号的会员权益只体现在画质上" | ⚠️ 不准确，但没人在这个位置会这么读 |

**结论：「仅取流」不用改。** 它是本方案里**唯一由裁决直接背书**的说法——比任何"新写法"都稳。

## Q2：三条备选（已缩窄到"只有取流可配"）

> 三条都以「`tabs.ts:95` 原句不动」为基点，因为 Q1 已证它成立。三者的差别只在**要不要额外声明能力边界**。

### 方案 A：保守——原句不动，另加一行说明

| 项 | 值 |
| --- | --- |
| 改法 | `tabs.ts:95` 一个字不改；在画质 Tab 底部加一行 `pane-note`：「本扩展只在取流时换身份，浏览、收藏、点赞、历史始终是你当前登录的号。」 |
| 动几处 | **1 个文件 1 处**（`tabs.ts` 加一行） |
| 误以为"号被切走"的风险 | **最低**。它把"哪些绝不动"说全了（浏览也列进去了），正面回应 ADR 0004 要消除的恐惧 |
| 单账号模式 | 说不通 —— 单账号时"换身份"这件事根本不存在，这行会变成噪音；**但它不会说谎**（"始终是你当前登录的号"在单账号下恰好是事实） |
| 代价 | 面板多一行，`sidebar.ts:83` 的 280px 宽度论证要重新量 |

### 方案 B：拆分——写入归谁 / 读取归谁分两行

| 项 | 值 |
| --- | --- |
| 改法 | `tabs.ts:95` 改成两行 hint：`写入（收藏 / 点赞 / 评论 / 历史）：始终用你当前的登录号` + `读取（推荐 / 播放列表）：按下面的设置` |
| 动几处 | **1 个文件 1 处**（`switchRow` 的 hint 目前是单字符串，要么改组件、要么在下面补一行） |
| 误以为"号被切走"的风险 | **中**。"读取可配"这四个字本身就会引发"那我的推荐是不是别人的"的联想，而**阶段 6 根本不做读取可配** → **这是对不存在的能力做解释** |
| 单账号模式 | **说不通**：两行都在描述一个不存在的选择 |
| 结论 | ❌ **不建议**。它按 lead 上一封信（阶段 6 还没砍）的框架写的，现在前提没了 |

### 方案 C：如实标注——每个"可配置"开关旁就地标注影响范围

| 项 | 值 |
| --- | --- |
| 改法 | 画质 Tab 的总开关旁标「只影响取流」；**若将来有推荐流开关**，那个开关旁标「只影响推荐流；你的点赞 / 历史不受影响」 |
| 动几处 | **现在 1 处**（总开关旁的 hint 已经是这个意思了）；推荐流开关存在时 **+1 处** |
| 误以为"号被切走"的风险 | **最低中的最低** —— 就地标注是"读到哪看到哪"，不制造额外联想 |
| 单账号模式 | **能活**：只有总开关一处标注，单账号下那处恰好也不渲染（无凭据则无该开关语义） |
| 结论 | ✅ **与方案 A 高度重合**。差别：A 是"总说明"，C 是"就地标注"。**C 更省**（复用已有 hint 槽位，不新增行） |

**三方案的关系**：B 已被前提推翻；A 与 C 实质相同，**A 是总说明版、C 是就地版**。若一定要选，**C 更省且更稳**（不改布局、不动 280px 宽度论证）。
