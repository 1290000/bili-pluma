### 🔴 发现：**注释里的 `reason: 'a' | 'b'` 会被误报**（真实缺口）

正则**不区分注释与代码**。三种真实形态全部误报：

```
⚠️ 误报  JSDoc 里描述字段      → reason: 'ok' | 'self' | 'disabled'
⚠️ 误报  块注释内              → reason?: 'a' | 'b'
⚠️ 误报  行尾注释引用          → reason: 'a' | 'b'
```

**已实证**（在真实文件 `src/shared/types/errors.ts` 末尾加一行注释，跑 `check-messages`）：
```
[messages] ❌ 1 处手抄了封闭枚举的取值域：
  src/shared/types/errors.ts:44  reason: 'ok' | 'self' | 'page-identity'
```
随即恢复，`git diff` 核对无残留。

### 为什么这是**高概率**而不是理论风险

**项目自己的注释习惯就是这种写法。** 当前仓库里已有一处：
```
src/shared/types/messages.ts:131
  * 1. **内联字面量断言**：`as { reason?: 'ok' | 'self' | ... }` —— 那是一个
```

它**恰好没报错**，原因有两个（都是偶然）：
1. 它在 `ENUM_DEFINITION_FILES` 白名单里（`messages.ts` 是定义处）
2. 它带反引号包裹

**但这两个偶然条件在其他文件都不成立。** 任何人若在 `popup-state.ts` / `page-snapshot.ts` 的 JSDoc 里写一句"`reason: 'ok' | 'self' | 'disabled'`"，立刻误报。

### 建议（**不是缺陷，是精度问题**；不阻塞交付）

**判据：检查工具误报一次，人就学会忽略它一次** —— 这与 `ROUTES_CHECKED_AT` 那条"假警报会训练用户忽略它"是同一原则。

最小修法（按侵入性排序）：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A（推荐）** | 扫描前**剔除注释**：逐行判断，把 `//` 之后与 `/* */` 之内替换成空白（保留行号） | ~15 行，无新依赖 |
| B | 命中后再判该行是否以 `*` / `//` 开头，是则跳过 | ~5 行，但**多行注释中间行是以 `*` 开头的**，能覆盖；而行尾注释 `// x: 'a' \| 'b'` 需额外判 |
| C | 命中后要求同时存在 `:` 前的字段声明上下文（如不是 `*` 行） | 同 B |

**A 最稳**：剔注释是通用操作，一次剔掉后所有后续检查都受益。

⚠️ **当前仓库扫出 0 假阳性**，所以这条**不阻塞 task-7 交付**。但建议在步骤 6/7 归档时补上 —— 否则下一个写注释的人会撞上它，然后要么加豁免（把白名单越堆越长），要么放宽正则（把真缺陷也放过）。**两条路都通向"检查失去意义"。**
