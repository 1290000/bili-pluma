## ① 截断陷阱：先取总数，再决定怎么展示

### 发生了什么（两次，同一轮，两个人）

**第一次（Lead，handoff §2.1 已记）**：统计「律师函相关处数」时，`grep` 输出被截断在 250 条，
得出「21 处」，实际 **26 处**。三个成员按错数据做了合理补救。

**第二次（verifier，本轮）**：扫描用户可见「播放账号」字符串时用了
`Select-Object -First 20`，得出"6 处遗漏"。实际上 **7 处**——
第 7 处是 `entrypoints/login-window/main.tsx:178` 的登录窗口大标题，
**恰好排在第 20 行之后**，被截断掉了。

> 讽刺的是：verifier 当时**正在批评 Lead"靠印象给清单"**，自己却用同一个工具默认值制造了同一类错误。

### 根因

`Select-Object -First N` / `head -N` / `| Select -First N` 是**展示**操作，
但很多命令把它和**统计**混在一行里写：

```powershell
# ❌ 把"展示多少条"和"一共有多少条"混为一谈
Get-ChildItem ... | Select-String "PATTERN" | Select-Object -First 20

# ✅ 先取总数，再决定要不要展示
$all = Get-ChildItem ... | Select-String "PATTERN"
Write-Output "总命中: $($all.Count)"
$all | Where-Object { ... } | Select-Object -First 20   # 展示可以截断，统计不能
```

### 可执行规则

> **规则 1：任何"有多少处 / 有多少个"的结论，必须先 `Measure-Object` 或 `grep -c` 取总数，
> 再决定怎么展示。`-First N` 只能用于展示，不能用于计数。**
>
> **规则 2：报告里写"N 处"时，附上"总数"和"筛掉了多少"，让别人能复核。**
> 例：「全仓 139 处命中 → 过滤注释后 1 处 → 该处零消费方 → 用户可见归零」。

## ② 并行编辑 vs 竞态：靠"失败项分布"区分，不靠重跑

### 发生了什么

为判定 `assertTestTotals` 是否偶发误红，连续跑 **5 次**全量 verify，结果：
**绿、红、绿、红、绿** → 2/5 失败。

按预设判据「≥2/5 出现 → 是竞态，要修」→ **看起来要改代码**。

**但失败项每次都不一样**：

| 次序 | 失败项 | 具体 |
| --- | --- | --- |
| 1 | `test` | `streaming-pill.test.ts` 期望「取流：取流账号」，实际「取流：扩展账号」 |
| 2 | `format` | prettier 格式 |
| 3 | `typecheck` | `tabs.ts` |

**三个不同检查项各失败一次 ≠ 同一个 bug 的特征**，而是**文件正在被改**的特征。

### 证据：文件在实时变动

```
2:22:43  src/core/ui/streaming-pill.ts
2:22:49  tests/unit/core/ui/streaming-pill.test.ts
2:23:54  src/shared/constants/streaming-identity.ts
2:23:55  src/content/panel/tabs.ts
2:25:24  src/core/ui/popup-state.ts
2:25:31  src/content/panel/tabs.ts   ← 等待 90 秒后仍在改
```

### 根因

**在多人共享工作区里，任何"N 次采样取统计"的验证，采样期间工作区若在变动，
采到的是"编辑活动的足迹"，不是系统行为。**

而且**"重跑即绿"不能作为"是偶发"的证据**——重跑可能只是恰好碰上了一个更完整的中间态。

### 可执行规则

> **规则 3：样本采集必须在工作区静默时进行**（`Get-ChildItem -Recurse | Where LastWriteTime -gt (Get-Date).AddMinutes(-10)`
> 为空，或所有成员报完成之后）。
>
> **规则 4：判定"偶发"看失败项的分布，不看重跑结果。**
> - 同一项反复失败 → 真实缺陷
> - **多项各失败一次 → 工作区在动，停止采样**
> - 同一项偶发且工作区静默 → 才是真的偶发，才考虑改代码

### 附带教训（verifier 自己的判断失误）

第一次报「偶发误红、重跑即绿，判定为 `fileParallelism` 偶发，不是本轮引入」——
**这个结论下得太快**：把"并行编辑产生的中间态"误判成了"本机负载偶发"。
两者处理方式完全不同：**前者等工作区静默即可，后者要改代码**。
**在没确认工作区是否静默的情况下，不应下"偶发"的结论。**

## ③ 变异恢复的定向校验：未跟踪文件的 `git diff` 永远为空

### 发生了什么

做变异测试（改判据 → 断言变红 → 恢复）后，用「全仓 `git diff` 的 SHA256」校验恢复是否完整。

**三次失败，原因各不相同**：

**第一次**：另一成员在我备份之后改了 `messages.ts` 等 5 个文件 → 全仓 diff 哈希不符，
**但不是我的变异残留**。→ 全仓校验在并行环境下无效。

**第二次**：`src/content/feed-boundary/feed-boundary.ts` 是**未跟踪的新文件**
（`git ls-files` 返回空）→ **`git diff` 对它永远为空**。
所以"diff 为空"**根本不能证明我恢复对了**。改用 `git hash-object` 也只对"我自己记录的基线"有效。

**第三次**：用 PowerShell `.Replace()` + `WriteAllText` 写回后，
**内容正确但 prettier 格式被破坏** → `format` 检查红了。

### 根因

| 手段 | 为什么不够 |
| --- | --- |
| 全仓 `git diff` SHA256 | 并行改动会污染 |
| `git diff` 对单文件 | **未跟踪文件恒为空**，等于没校验 |
| `git hash-object` | 只知道"变了"，不知道"变对了没"，且需自己维护基线 |
| 只看内容 grep | 格式可能已坏 |

### 可执行规则

> **规则 5：变异恢复用三重确认**，且**显式记录"我碰过哪些文件"**：
> 1. `git hash-object <文件>` 与变异前记录的值比对（**未跟踪文件也可用**）
> 2. **行为确认**：跑该文件相关的测试 + `tsc`
> 3. **结构确认**：`grep` 关键判据仍在、无变异残留痕迹
> **三者全过才算恢复。**
>
> **规则 6：任何脚本改文件之后必须跑 format。**
> `node_modules/.bin/prettier --write <改过的文件>`，然后 `--check` 复验。
> 用 `.Replace()` + `WriteAllText` 改源码，**几乎必然破坏格式**（缩进/换行/引号风格）。

## ④（新）"证明"而不是"相信"

### 发生了什么

verifier 关闭改名遗漏这一项时，最后一处是 `routes.ts:136` 的 `note` 字段。
它确实是"用户可见"的候选（字段名叫 note，看起来会显示）。

**做法**：`grep '\.note\b'` 全仓 → **0 处消费方** → 证明它不是用户可见字符串，而不是"我觉得它不是"。

### 可执行规则

> **规则 7：判定"某处字符串用户可见/不可见"时，用"有无消费方"证明，不要靠字段名猜。**
> 字段叫 `note` / `label` / `detail` 不代表会渲染；`grep` 消费方是唯一判据。
